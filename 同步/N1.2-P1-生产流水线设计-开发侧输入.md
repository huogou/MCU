**每层职责要点**
- **Source Registry**：来源唯一可信配置源；提供「是否可采集、类型、可信度(tier)、出口URL」。流水线只读投影，不复制第二份来源定义。
- **Collector**：按 transport 取内容→解析→归一化→生成 L0；单源失败不影响批量（fail closed）。
- **L0 Capture**：原始证据落盘，整条逐字节去重（抓取时间不同=不同证据批次）。
- **L1 Candidate**：AI 整理后的候选单位；内容级幂等去重。
- **AI Analyzer（新）**：把「单次 Provider 验证」升级为「生产调用服务」，在已校验的 7 字段之上附加可信度/推荐/置信度，供 Verification 使用。
- **Verification**：基于既有规则 + 可信度门槛做质量校验，决定 approve/reject。
- **Event Merge**：权威的事件级归并（同事件多来源），本期不被去重层取代。
- **Delivery**：产出入库前结构化产物（不写 H5）。
- **H5 Data**：最终展示层，本期只产出「待回流产物」，回流上线留待下一阶段。

## 二、状态追踪设计（pipeline/status/）

**设计原则**：状态追踪是**独立的运行期/运行后视图层**，物理隔离于 L0/L1/L2。它**读取**冻结模块的输出、把状态变化记录到自有 JSON，**绝不回写**任何状态字段进三层（遵守 pipeline README 硬约束 3）。

### 2.1 目录与文件
```
pipeline/status/
  item-status/YYYY-MM-DD.item-status.json    # 条目级状态机
  run-status/run-YYYYMMDD-NNN.status.json    # 运行级状态机
  status-machine.cjs                          # 状态转换引擎（纯函数，无副作用）
```

### 2.2 item 状态结构（一条候选/采集项的生命周期）
```jsonc
{
  "schema_version": "1.0",
  "layer": "STATUS-ITEM",
  "item_id": "cap-<capture_id> | cand-<candidate_id>",  // 关联三层对象 id，不改三层
  "ref_layer": "L0 | L1",
  "current_status": "RAW",
  "status_history": [
    {
      "status": "RAW",
      "at": "2026-09-30T08:00:00Z",
      "by": "status-init",
      "evidence": "source_registry:S002",
      "note": "来源进入采集队列"
    },
    { "status": "FETCHED", "at": "...", "by": "collector", "evidence": "capture:<id>" },
    { "status": "AI_ANALYZED", "at": "...", "by": "news-analyzer", "evidence": "ai:<model>" },
    { "status": "VERIFIED", "at": "...", "by": "gate", "evidence": "gate:approve" },
    { "status": "PUBLISHED", "at": "...", "by": "delivery", "evidence": "delivery:<id>" }
  ],
  "dedup_hint": null   // 语义去重标注（dup_of / similar_to），不删除本项
}
```

### 2.3 run 状态结构（一次流水线执行）
```jsonc
{
  "schema_version": "1.0",
  "layer": "STATUS-RUN",
  "run_id": "run-20260930-001",
  "mode": "dry-run | production-capture | ...",
  "stages": {
    "COLLECT":   { "status": "done", "count": 12, "at": "..." },
    "ANALYZE":   { "status": "done", "count": 10, "at": "..." },
    "VERIFY":    { "status": "skipped", "reason": "mode!=review", "at": "..." },
    "MERGE":     { "status": "pending", "at": null },
    "DELIVER":   { "status": "skipped", "at": null }
  },
  "started_at": "...", "ended_at": "..."
}
```

### 2.4 状态转换规则
| 状态 | 进入条件 | 负责变化的模块 | 证据来源 |
|---|---|---|---|
| **RAW** | 来源被纳入本次采集计划 | `status-machine.init()`（接线层调用） | source_registry 条目 |
| **FETCHED** | Collector 产出 L0 RawCapture | `base-collector` 产出后由 orchestrator 通知 status 层 | capture id |
| **AI_ANALYZED** | NewsAnalyzer 完成 7字段+扩展字段 | `news-analyzer.cjs` 完成后通知 | provider/ai_model |
| **VERIFIED** | Verification(Gate) 通过 | `gate.cjs` approve 后通知 | gate 决策 |
| **PUBLISHED** | Delivery 产物生成并回流 H5 | `delivery-converter` 产出 +（下阶段）回流 | delivery id |

约束：
- 单向推进，不允许回退（PUBLISHED 不可改回）；异常项标记为 `ANOMALY`（独立字段，不进主链）。
- 状态层**不拥有**任何业务字段，只持有 `item_id`/`ref_layer` 引用 + 历史。
- 所有写操作 append-only + 原子写（复用 `capture-store.assertInsidePipeline` 守卫）。

## 三、NewsAnalyzer 设计（pipeline/ai/news-analyzer.cjs）

**定位**：把 N1.2 U1「单次 Provider 验证」升级为「生产调用服务」。它**消费**已校验的 7 字段，并**独立组装**扩展字段，作为 Verification 的输入。

### 3.1 输入
- `candidate`（L1 候选，35 字段，含原始素材引用）
- `provider`（N1.1 注册实例，如 dashscope）
- `registry`（N1.1 createRegistry）
- `opts`：meta（provider/model）、idSpace、seq

### 3.2 处理链路（复用既有、不重写）
```
candidate
  → A.runAdapter(provider, candidate)   # N1.1 adapter：provider.provide → contract-validator 校验
  → 7 字段（title/summary/category/related_*）✅ 经 validator 通过
  → B.injectAiModel(seven, meta)         # 注入 ai_model → 8 字段
  → NM.normalize(candidate, eight)       # G5.5 ai-normalizer：产出增强 L1（只读调用）
  → newsAnalyzer.enrich(seven, candidate, providerMeta)  # 【新增】产出扩展字段
```

### 3.3 输出（基础字段 + 扩展字段）
```jsonc
{
  // —— 基础字段（与 7 字段契约一致，来自 validator 输出，原样透传）——
  "title": "...", "summary": "...", "category": "movie",
  "related_movies": [], "related_series": [], "related_characters": [], "related_phases": [],

  // —— 扩展字段（NewsAnalyzer 在契约之外独立组装）——
  "credibility": "high | medium | low",     // 可信度判断（基于来源 tier + 官方核验 + 多源印证）
  "recommend": true,                         // 是否推荐展示（规则 + 可信度门槛）
  "confidence": 0.0–1.0                      // 模型结构化输出的置信度（如 JSON 解析稳定性/字段完整度）
}
```
- `credibility`：组合信号 = 来源 `tier`（T1 官方最高）、`official_or_media`、是否多来源印证（事件 report_count）、是否与 `officialSources()` 域名吻合。
- `recommend`：规则 = `credibility != low` 且 `confidence >= 阈值(0.6)` 且 category 非空且 related 至少命中一个 MCU 节点。
- `confidence`：由 Provider 返回质量推导（JSON Schema 命中 / 字段非空率 / 有无被 validator 警告）。

### 3.4 为什么不修改 validator（关键）
- **契约稳定性**：`contract-validator.cjs` 是 N1.1 冻结件，7 字段是「Provider 标准输出契约」，被 adapter、bridge、ai-normalizer、交付物全链路依赖。改它等于改全链路语义，违反冻结约束。
- **职责边界**：validator 只回答「Provider 输出是否合法 7 字段」；`credibility/recommend/confidence` 属于**流水线分析层**的判断，不是 Provider 契约的一部分。把它们放在 NewsAnalyzer 内，使二者解耦。
- **可演进性**：扩展字段若未来要纳入契约，走「待决策」流程；本期 NewsAnalyzer 以「7 字段之上附加」方式零侵入落地，不影响任何既有回归断言（411 条）。

## 四、语义去重设计（pipeline/dedup/）

**定位**：在 L1 入库**前**做相似度预筛，产出 `dedup_hint`，**不删除**任何条目、**不覆盖** G4 事件归并。G4 仍是事件级归并的唯一权威。

### 4.1 三类去重
| 类型 | 输入 | 算法 | 阈值（建议） |
|---|---|---|---|
| **标题相似** | 归一化 title | 分词 → n-gram(2-3) 集合 → Jaccard 相似度 | ≥ 0.85 判相似 |
| **内容相似** | summary + 正文摘要 | 字符 3-gram shingling → Jaccard（或轻量余弦） | ≥ 0.80 判相似 |
| **事件相似** | event_key / 关联 MCU 节点集合 | 复用 G4 `event-merger` 的归并键（不重实现） | 交给 G4 权威归并 |

### 4.2 算法选择理由
- 项目工程约束：纯 Node、避免重依赖（无 tfidf/embedding 库）。选 **Jaccard + n-gram shingle**，零依赖、可解释、可单测。
- 标题用短 n-gram（2~3 字），内容用 3-gram shingle，平衡精度与召回。
- 可选增强：若后续引入本地 embedding 再做余弦；本期不引入（控成本、控复杂度）。

### 4.3 防误杀策略（重点）
1. **以 content_hash 精确去重为铁律**（沿用 candidate-store）：完全相同的抓取内容必去重，相似度只用于「疑似」。
2. **相似≠删除**：dedup 层只打 `dedup_hint: { kind: 'title|content|event', similar_to: <id>, score }`，**保留本项**，交由 VERIFIED 阶段人工/规则最终裁定。
3. **事件进展保护**：同一 event_key 但 `publish_time` 跨天或含新增事实（摘要差异 > 阈值）→ 不判重，避免把「同一事件的不同进展」误杀漏发。
4. **不覆盖 G4**：dedup 运行在「候选层预筛」，G4 event-merger 仍在 VERIFIED 之后做权威归并；两者职责分离，dedup 的 `similar_to` 仅作提示，不改变 G4 行为。
5. **阈值保守+可配**：阈值写入配置文件，便于按来源质量调参；误杀风险靠「只标注不删」兜底。

## 五、run-history 增强设计

**目标**：在 G10 既有 10 字段封闭集**之上**追加 `ai_processed_count` 与 `fail_reasons`，且**兼容**历史 10 字段记录。

### 5.1 字段扩展（向后兼容）
- 既有 10 字段：`run_id / start_time / end_time / source_success / source_failed / capture_count / candidate_count / approved_count / rejected_count / delivery_count`
- 新增 2 字段（**可选**，缺失视为默认值）：
  - `ai_processed_count`（非负整数，默认 0）：本次 AI Analyzer 成功处理的条目数（当前 orchestrator.metrics 已有 `ai_normalized_count`，仅未写入记录）。
  - `fail_reasons`（数组，默认 `[]`）：`[{ stage, source, code, message }]`，记录各阶段失败原因，便于监控。

### 5.2 兼容方案（不破 411 断言）
- `FIELDS` 升级为「基础 10 + 已知扩展 2」；`validate()` 改为：**恰好 10 字段（历史记录）或 12 字段（含两个已知扩展）均接受**，未知越权字段仍抛 `FIELD_SET_MISMATCH`。
- 历史 10 字段记录在 `load()` 时**不强制补字段**（读宽容、写严格），新记录写满 12 字段。
- 此改动属于「运行记录层自身演进」，不触碰三层 / 判定器 / 交付物，符合冻结边界。

### 5.3 orchestrator 接线点
- 在 `production-*` 模式写 run-history 的 entry 中，补 `ai_processed_count = metrics.ai_normalized_count`、`fail_reasons = metrics.source_fail_reasons`（及 ANALYZE/VERIFY 阶段异常）。
- dry-run 仍不写 run-history（D1 裁定不变）。

## 六、自动调度方案评估

**当前部署**：H5 = 阿里云轻量应用服务器（Nginx 静态站 + HTTPS，域名 mcuatlas.xyz）；Pipeline = Node 工具链（`workspace/news/pipeline`，未部署，本地/CI 运行）。H5 为纯静态多页，无常驻 Node 进程。

| 维度 | 方案A：GitHub Actions | 方案B：阿里云函数计算(FC) timer | 方案C：服务器 Cron（阿里云轻量） |
|---|---|---|---|
| 实现方式 | 仓库 `.github/workflows` 定时 YAML，跑 Node 脚本，产物 commit/SCP/调 API | FC 函数 + 定时触发器，跑 pipeline，写 OSS/调服务器 API | 服务器上 `crontab` 执行 `node runner` 脚本 |
| 成本 | 免费额度（2000 min/月），超量计费 | 按调用计费，日级运行极低（约 ¥0~几/月） | 已付服务器费用，**零额外成本** |
| 稳定性 | 高（GitHub SLA），但与仓库强绑 | 高（云厂商 SLA），独立部署 | 中（依赖单机 uptime，单点故障） |
| 维护难度 | 低（YAML 即代码） | 中（需打包 Node、配 FC/触发器） | 低（一行 crontab） |
| 未来扩展性 | 中（可触发外部 API、发通知） | 高（可写 OSS、调 API、回流 H5、多源编排） | 低（耦合单机，扩容难） |
| 与现有环境契合 | 需仓库在 GitHub；H5 在阿里云，需跨云回流 | 同属阿里云生态，回流 H5 最顺 | H5 同机，回流最简 |

**评估结论（不绑定，供下阶段决策）**：
- **P1 首选方案C（服务器 Cron）**：H5 已在阿里云轻量，直接在本机 crontab 跑 `node` 脚本，产物落到 Nginx 可访问目录或待回流文件，**零新基础设施、零额外成本、回流路径最短**。风险是单机单点——用「运行日志 + 失败告警」兜底即可满足 P1。
- **演进路线**：P1-C 跑稳后，升级到**方案B（FC timer）**解耦单机依赖、提升可靠性，并天然支持多环境/多源编排；方案A 适合若未来把仓库迁 GitHub 且想要零基础设施的场景。
- 本期**只产出评估与可执行调度草稿（默认不启用）**，具体上线绑定留待下一阶段。
