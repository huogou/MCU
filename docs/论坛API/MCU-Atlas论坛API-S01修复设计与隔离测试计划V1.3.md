## 4. 目标架构与客户端 IP 可信链路

### 4.1 链路

```
公网客户端 ─HTTPS► nginx:443 (location ^~ /api/)
    proxy_set_header X-Real-IP $remote_addr;                 ← 覆盖客户端自带的同名头
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;  ← 客户端值在左、nginx 观测值在右
                        ▼
              127.0.0.1:8787（仅回环，本轮不修改）
                        ▼
    server.js: clientIp(req, {trustProxy, trustedProxies})
      D-N2 信任判定：trustProxy===true 且 canonicalizeIp(peer) ∈ TRUSTED_PROXIES
      D-N3 顺序：X-Real-IP → XFF 最右 → peer → 'unknown'
                        ▼
    ctx.ip → rate.registerByIp(ctx.ip) → key 'reg:<真实客户端IP>'
```

### 4.2 白名单语义（准确表述）

`TRUSTED_PROXIES = ['127.0.0.1','::1']` 的准确含义是：**只对 TCP 对端位于本机回环的请求采信转发头**。它不标识进程身份。

### 4.3 威胁模型与残余风险（P1-D05 闭环）

| 威胁 | 能否成立 | 说明与缓解 |
|---|---|---|
| 公网客户端伪造 `X-Real-IP` / `X-Forwarded-For` | **不能** | nginx `proxy_set_header X-Real-IP $remote_addr` 无条件覆盖客户端值；XFF 为「客户端值 + nginx 观测值」，伪造值只出现在最左，而规则只取最右。叠加应用仅监听回环，公网无法直连 8787 |
| 本机其他进程直连 8787 并伪造转发头 | **能** | 回环可被本机任意进程访问（系统服务、cron、其他 node 进程、root/forumapi 用户的 shell 等）。后果仅限**限流桶粒度被操纵**（可把注册限额转移到某个 IP 名下或规避自身计数），**不影响身份鉴权**（用户 token 为 HMAC、admin token 独立、路由层 `requireUser`/`requireAdmin` 不变） |
| 本机进程伪装成 nginx | **能（无法区分）** | Node 的 TCP socket 不提供对端进程身份（无 SO_PEERCRED 等价能力），本设计**不声称实现进程身份认证** |
| 生产 nginx 配置被改为不下发 `X-Real-IP` | **能（配置回归）** | 若该行被删除，公网伪造将直接生效 → 纳入运维检查清单（§16.5） |
| 新增 CDN / 前置代理 | **能（架构变更）** | 必须把该代理 IP 加入 `TRUSTED_PROXIES` 并确保其覆盖 `X-Real-IP`，且重新评估本威胁模型；未评估前不得上线 |

**已接受的残余风险**：本机进程可操纵限流桶。接受理由：影响面仅限频率限制（不触鉴权、不触数据），利用前提是已具备本机执行能力（此时威胁模型已假定失陷）。若未来需要消除，方向是 unix socket + SO_PEERCRED 或 network namespace 隔离，属架构变更，单独立项。

## 5. IP 解析算法 V2（P0-D01 闭环）

### 5.1 Node 标准库能力边界（明示，不虚构）

| 能力 | 是否提供 | 用法 |
|---|---|---|
| `net.isIP()` | 仅校验 | **仅作 D7 交叉校验**，不代替解析器完整性 |
| IPv6 规范化 / canonicalization | **不提供** | 自研（D6.6） |
| `net.BlockList` 对 `::ffff:127.0.0.1` 与 `127.0.0.1` 的相等语义 | **未文档化** | **不依赖** |

剩余限制：不处理 zone id、前缀长度、带端口/方括号形式（一律判负，不修复）；不支持 NAT64 等非 mapped 的 IPv4 尾段（D6.5 判负）。

### 5.2 `canonicalizeIp(value)` 最终算法

```
D1  非字符串                                                  → null
D2  s = value.trim(); 空或 s.length > 45                     → null
D3  s 必须只含 [0-9a-fA-F:.]                                 → null
    （因此 '[', ']', '%', '/', 空格内部, 引号, '+', '-' 等一律判负；
      '-' 不在白名单内，故 'X-Real-IP: 1.2.3.4-port' 之类直接判负）
D4  结构分流（关键修正：不再因「含点」就判 IPv4）：
      s 含 ':'   → IPv6 分支 D6
      s 含 '.'   → IPv4 分支 D5
      否则       → null
D5  IPv4 分支：
      parts = s.split('.')，长度必须 === 4
      每段必须匹配 ^(0|[1-9][0-9]{0,2})$ 且数值 ≤ 255          （拒绝前导零）
      → { kind:'v4', text:s }
D6  IPv6 分支：
    D6.1  '::' 出现次数 > 1                                  → null
    D6.2  分段：segments = s.split(':')
          - 若最后一个 segment 含 '.'：仅允许它作为嵌入式 IPv4 尾段，
            按 D5 规则解析为 2 个 hextet（高/低 16 位）；解析失败 → null
          - 其余每个 segment 必须匹配 ^[0-9a-fA-F]{1,4}$；
            空串只允许出现在 '::' 位置；否则 → null
    D6.3  组装：
          - 有 '::'：zeros = 8 - (左段数 + 右段数)；zeros < 0 → null；
                     hextets = 左 + [0]*zeros + 右
          - 无 '::'：hextet 总数必须 === 8，否则 → null
    D6.4  mapped 判定（严格）：
          hextets[0..4] 全为 0x0000 且 hextets[5] === 0xffff
          → { kind:'v4mapped', text: 由 hextets[6],hextets[7] 生成点分十进制 }
    D6.5  若存在嵌入式 IPv4 尾段但不满足 D6.4                → null
          （NAT64、'::0.0.0.2'、'1:…:ffff:1.2.3.4' 等在解析器内直接拒绝，
            绝不先产出合法 IPv6 文本）
    D6.6  规范文本（kind 'v6'）：
          hextets 转小写十六进制；
          找最长连续零 hextet 段，长度 ≥ 2 才压缩为 '::'；
          多段等长取**最左**；无 ≥2 的零段则不压缩
D7  自守卫：net.isIP(text) !== 0，否则 null
```

### 5.3 压缩规则（明确）

- 只压缩**连续零 hextet**，长度 ≥ 2。
- 存在多个最长段且长度相等时，压缩**最左侧**那段。
- 长度 1 的零段不压缩。
- 输出全部小写；IPv4 分支保持输入的点分形式（数字无前导零已由 D5 保证）。

### 5.4 一致性说明（对照审查意见）

| 审查指出 | V1.3 算法如何一致 |
|---|---|
| C5 与 C6.1 矛盾 | D4 改为「含 `:` → IPv6；含 `.` 且不含 `:` → IPv4」，点分尾段只可能在 IPv6 分支出现，矛盾消除 |
| 非 mapped 的 IPv4 尾段「先生成合法 IPv6 再期待测试 null」 | D6.5 在产出任何文本之前判负，测试期望与算法同源 |
| 最长零段规则未定义 | D6.6 + §5.3 明确「最长、等长取最左、≥2 才压」 |

## 6. 配置项、路径派生与环境变量优先级

### 6.1 优先级与取值

```
进程环境变量（仅 harness 注入） > config.js 常量默认值
```

| 配置项 | 规则 | 生产实际值 |
|---|---|---|
| `HOST` | `env.FORUM_HOST \|\| '127.0.0.1'` | `127.0.0.1` |
| `PORT` | `env.FORUM_PORT !== undefined ? Number(env.FORUM_PORT) : 8787` | `8787` |
| `DATA_DIR` | `env.FORUM_DATA_DIR \|\| path.join(__dirname,'data')` | `<项目>/data` |
| `DB_PATH` | `path.join(DATA_DIR,'forum.db')` | `<项目>/data/forum.db` |
| `SECRET_PATH` | `path.join(DATA_DIR,'secret.key')` | `<项目>/data/secret.key` |
| `ADMIN_TOKEN_PATH` | `path.join(DATA_DIR,'admin-token.key')` | `<项目>/data/admin-token.key` |
| `TRUST_PROXY` | 常量 `true` | `true` |
| `TRUSTED_PROXIES` | 常量 `['127.0.0.1','::1']` | 同左 |

要点：`PORT` 不得用 `\|\|`（会吞掉 0）；`DB_PATH`/`SECRET_PATH`/`ADMIN_TOKEN_PATH` 必须由 `DATA_DIR` 派生（V1.2 R-05 修正保留）；env 全未设时四个路径与旧代码逐字节相同。

### 6.2 与生产 systemd 的关系

§12 核查结论：unit 无 `EnvironmentFile`/drop-in/`DefaultEnvironment`，进程环境仅 8 个标准变量，无 `FORUM_*`/`DATA_DIR`/`PORT`/`SECRET` 类变量 → 生产恒用常量默认值，设计与实际一致。运维约束：今后若为该 unit 增加任何 `Environment=`/`EnvironmentFile=`，必须重跑 §12 清单并更新 §6.1。

## 7. 隔离测试架构与初始化时序（P0-D02/D03/D04 闭环）

### 7.1 隔离实例形态

```
数据根目录：harness 自建于 os.tmpdir() 下（mkdtemp），DB + secret.key + admin-token.key 全部由应用在其中生成
端口：      FORUM_PORT=0（OS 分配随机可用端口）
主机：      FORUM_HOST=127.0.0.1（字面量，不用 localhost）
请求目标：  由 harness 解析「自己子进程」的监听行生成，不读取任何外部 URL
```

### 7.2 初始化时序图（任何读生产密钥 / 写项目目录 / 发网络请求之前必须完成阶段 0~4）

```
阶段 0  读取 env（无 IO、无网络、无子进程）
  0.1 FORUM_DATA_DIR 已设置                                   → 否则 exit 5
  0.2 原始路径（resolve 之前）不含 '..' 段                     → 否则 exit 7
  0.3 原始路径不含 Windows 盘符/UNC 形式（X:\ 或 \\ 开头）       → 否则 exit 7
  0.4 原始路径不含 '/www/'                                    → 否则 exit 5
  0.5 FORUM_PORT === '0'                                      → 否则 exit 4（禁止固定端口）
  0.6 FORUM_HOST ∈ {'127.0.0.1','::1'} 字面量                  → 否则 exit 3（拒绝 localhost 字面量）
阶段 1  数据根安全判定（只读，不创建）
  1.1 resolved = path.resolve(DATA_DIR)
  1.2 parent = path.dirname(resolved)；parent 必须存在          → 否则 exit 7
  1.3 parentReal = fs.realpathSync(parent)
  1.4 tmpReal = fs.realpathSync(os.tmpdir())
  1.5 parentReal 必须位于 tmpReal 之内                         → 否则 exit 7
  1.6 dataRootReal = path.join(parentReal, path.basename(resolved))
阶段 2  创建并复核（只写临时目录）
  2.1 fs.mkdirSync(resolved, {recursive:true, mode:0o700})
  2.2 fs.lstatSync(resolved)：目录且非符号链接                 → 否则 exit 7
  2.3 fs.realpathSync(resolved) === dataRootReal               → 否则 exit 7
阶段 3  启动子进程（env：FORUM_DATA_DIR=resolved, FORUM_PORT=0, FORUM_HOST=127.0.0.1）
  3.1 spawn 失败 / 立即退出                                   → kill+清理 → exit 9
  3.2 15s 内未输出监听行                                       → kill+清理 → exit 10
  3.3 解析监听行 `[forum-api] listening on http://127.0.0.1:<port>`
        host 必须为 127.0.0.1；port 必须为 1024..65535 且 ≠ 8787 → 否则 kill+清理 → exit 4
      （端口唯一来源；禁止扫描/猜测；解析失败不得回退默认端口）
阶段 4  密钥与数据库落盘复核（应用已自动生成，见 §7.4 证据）
  对 dataRootReal 下 forum.db / secret.key / admin-token.key 逐一：
  4.1 fs.lstatSync：必须存在、普通文件、非符号链接            → 否则 kill+清理 → exit 5
  4.2 fs.realpathSync(file) 必须位于 dataRootReal 之内          → 否则 kill+清理 → exit 5
  4.3 mode & 0o077 必须为 0（无 group/other 位）                → 否则 kill+清理 → exit 5
  4.4 harness 仅从 dataRootReal 内读取密钥（绝不读生产路径）
阶段 5  请求目标绑定
  5.1 BASE = `http://127.0.0.1:${actualPort}`（来自阶段 3 的子进程监听信息）
  5.2 每次请求前 assertTarget(url)：协议 http:、hostname '127.0.0.1'、port === actualPort
                                                                → 否则终止 exit 8
  5.3 fetch 使用 redirect:'manual'；收到 3xx 先检 Location：
      跨源（origin ≠ BASE origin）→ 不请求该地址、记 FAIL、终止 exit 8
  5.4 身份佐证：harness 在子进程 stdout 中回查本次请求的 `[api] …` 日志行，
      确认请求确实到达「本 harness 启动的进程」
阶段 6  清理（kill + rm）；失败显式报告 exit 13/14
```

### 7.3 与 V1.2 的差异（D-02/D-03/D-04 修正点）

| V1.2 | V1.3 |
|---|---|
| 启动前对**尚不存在**的密钥文件 `realpathSync` | 启动前只验**数据根**（阶段 1~2）；密钥生成后才复核（阶段 4） |
| GN-10 把「密钥缺失」定义为拒绝启动 | 密钥缺失是**首次启动的正常预期**（应用自动生成），不再是拒绝条件；GN-10 改为「密钥路径/权限/符号链接越界才拒绝」 |

## 16. 失败处理与回滚方案

### 16.1 回滚触发条件（任一）

`is-active` 非 `active`；`/api/topics` 5xx 上升或新增 `[500]`；L3 探针出现伪造 IP 被采信；注册 429 异常激增；`ip=` 字段缺失/格式错误；白名单之外文件哈希变化。

### 16.2 回滚步骤（逐文件，禁整目录覆盖）

1. `systemctl stop mcu-forum-api`（提前知会）。
2. 从发布前备份**逐文件**恢复 `server.js`、`config.js`。
3. **删除**新增文件 `lib/client-ip.js`（禁止 `cp -a backup/lib`）。
4. 校验：`sha256sum server.js config.js` 回到 `043509ba…` / `86586a22…`；`ls lib/` 与备份清单一致。
5. `systemctl start mcu-forum-api` → 复检 `is-active`、`ss -lntp | grep 8787`、`journalctl -n 20`。
6. 记录回滚时间、原因、恢复后哈希。

### 16.3 配置与数据兼容性

- 配置回滚 = 恢复 `config.js` 常量默认值；**无数据迁移**（schema 未改、DB 不变）。
- `TRUST_PROXY` 回退即回到「仅用 peer」的修复前行为（限流退化，不影响数据与鉴权）。
- 必须重启才生效（`Restart=always` 覆盖）。
- **绝不触碰** `data/`、`forum.db`、`secret.key`、`admin-token.key`。

### 16.4 防覆盖他人在途改动

白名单文件操作；禁 `rsync --delete`、禁整目录覆盖、禁 `git` 类操作；发布前后各跑一次全目录 `sha256sum`，白名单之外任何变化先查清再继续。

### 16.5 运维检查清单（与代码配套，防配置回归）

| 检查项 | 频率 |
|---|---|
| nginx `location ^~ /api/` 中 `proxy_set_header X-Real-IP $remote_addr;` 必须存在 | 每次改 nginx 后 |
| 应用仍仅监听 `127.0.0.1:8787`（`ss -lntp`） | 每次改 unit 后 |
| unit 未新增 `Environment=`/`EnvironmentFile=`（若新增须重跑 §12） | 每次改 unit 后 |
| `TRUSTED_PROXIES` 与实际代理拓扑一致（新增 CDN/代理须先评估 §4.3） | 架构变更时 |
