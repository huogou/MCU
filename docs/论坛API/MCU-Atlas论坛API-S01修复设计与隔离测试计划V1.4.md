## 4. 目标架构与客户端 IP 可信链路

### 4.1 链路

```
公网客户端 ─HTTPS► nginx:443 (location ^~ /api/)
    proxy_set_header X-Real-IP $remote_addr;                        ← 覆盖客户端自带的同名头
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;    ← 客户端值在左、nginx 观测值在右
                        ▼
              127.0.0.1:8787（仅回环，本轮不修改）
                        ▼
    server.js: clientIp(req, {trustProxy, trustedProxies})
      信任判定：trustProxy===true 且 canonicalizeIp(peer) ∈ TRUSTED_PROXIES
      顺序：X-Real-IP → XFF 最右 → peer → 'unknown'
                        ▼
    ctx.ip → rate.registerByIp(ctx.ip) → key 'reg:<真实客户端IP>'
```

### 4.2 白名单语义（准确表述）

`TRUSTED_PROXIES = ['127.0.0.1','::1']` 的准确含义是：**只对 TCP 对端位于本机回环的请求采信转发头**。它不标识进程身份。

### 4.3 威胁模型与残余风险

| 威胁 | 能否成立 | 说明与缓解 |
|---|---|---|
| 公网客户端伪造 `X-Real-IP` / `X-Forwarded-For` | **不能** | nginx `proxy_set_header X-Real-IP $remote_addr` 无条件覆盖客户端值；XFF 为「客户端值 + nginx 观测值」，伪造值只出现在最左，而规则只取最右；叠加应用仅监听回环，公网无法直连 8787 |
| 本机其他进程直连 8787 并伪造转发头 | **能** | 回环可被本机任意进程访问（系统服务、cron、其他 node 进程、root/forumapi 用户的 shell 等）。后果仅限**限流桶粒度被操纵**，不影响身份鉴权（用户 token 为 HMAC、admin token 独立、路由层 `requireUser`/`requireAdmin` 不变） |
| 本机进程伪装成 nginx | **能（无法区分）** | Node 的 TCP socket 不提供对端进程身份，本设计**不声称实现进程身份认证** |
| 生产 nginx 配置回归（删除 `X-Real-IP` 行） | **能** | 纳入运维检查清单（§16.5） |
| 新增 CDN / 前置代理 | **能（架构变更）** | 必须把该代理 IP 加入 `TRUSTED_PROXIES` 并确保其覆盖 `X-Real-IP`，且重新评估本威胁模型；未评估前不得上线 |

**已接受的残余风险**：本机进程可操纵限流桶。接受理由：影响面仅限频率限制（不触鉴权、不触数据），利用前提是已具备本机执行能力。若未来需消除，方向是 unix socket + `SO_PEERCRED` 或 network namespace 隔离，属架构变更，单独立项。

## 5. IP 解析算法 V3（P0-D01/D02 闭环）

### 5.1 Node 标准库能力边界（明示，不虚构）

| 能力 | 是否提供 | 用法 |
|---|---|---|
| `net.isIP()` | 仅校验 | **仅作 D7 交叉校验**，不代替解析器完整性 |
| IPv6 规范化 / canonicalization | **不提供** | 自研（D6.6） |
| `net.BlockList` 对 `::ffff:127.0.0.1` 与 `127.0.0.1` 的相等语义 | **未文档化** | **不依赖** |

剩余限制：不处理 zone id、前缀长度、带端口/方括号形式（一律判负，不修复）；不支持 NAT64 等非 mapped 的 IPv4 尾段（D6.5 判负）。

### 5.2 `canonicalizeIp(value)` 最终算法

```
D1  非字符串                                                  → null
D2  s = value.trim(); 空或 s.length > 45                     → null
D3  s 必须只含 [0-9a-fA-F:.]                                 → null
D4  结构分流（关键：不再因「含点」就判 IPv4）：
      s 含 ':'   → IPv6 分支 D6
      s 含 '.'   → IPv4 分支 D5
      否则       → null
D5  IPv4 分支：
      parts = s.split('.')，长度必须 === 4
      每段必须匹配 ^(0|[1-9][0-9]{0,2})$ 且数值 ≤ 255          （拒绝前导零）
      → { kind:'v4', text:s }
D6  IPv6 分支：
    D6.1  '::' 出现次数 > 1                                  → null
    D6.2  分段：segments = s.split(':')
          ★ 任何**非最后一个** segment 含 '.'                → 立即 null
            （在解析任何段之前先做此判定；因此 '1.2.3.4:5678'、'1.2.3.4::5'、'a.b:c' 全部直接拒绝）
          - 若最后一个 segment 含 '.'：仅允许它作为嵌入式 IPv4 尾段，
            按 D5 规则解析为 2 个 hextet（高/低 16 位）；解析失败 → null
          - 其余每个 segment 必须匹配 ^[0-9a-fA-F]{1,4}$；
            空串只允许出现在 '::' 位置；否则 → null
    D6.3  组装：
          - 有 '::'：zeros = 8 - (左段数 + 右段数)；zeros < 0 → null；
                     hextets = 左 + [0]*zeros + 右
          - 无 '::'：hextet 总数必须 === 8，否则 → null
    D6.4  mapped 判定（严格）：
          hextets[0..4] 全为 0x0000 且 hextets[5] === 0xffff
          → { kind:'v4mapped', text: dotted(hextets[6], hextets[7]) }
    D6.5  若存在嵌入式 IPv4 尾段但不满足 D6.4                → null
    D6.6  规范文本（kind 'v6'）：
          hextets 转小写十六进制；
          最长连续零 hextet 段长度 ≥ 2 才压缩为 '::'；等长取最左；否则不压缩
D7  自守卫：net.isIP(text) !== 0，否则 null
```

### 5.3 压缩规则（明确）

- 只压缩**连续零 hextet**，长度 ≥ 2。
- 多个最长段等长时压缩**最左侧**那段。
- 长度 1 的零段不压缩。
- 输出全部小写；IPv4 分支保持点分形式（无前导零已由 D5 保证）。

### 5.4 输出规则分类（P0-D01 第 4 项要求，明确区分）

| 规则 | 触发条件 | 输出 |
|---|---|---|
| **规则 V4（IPv4）** | D5 通过 | 点分十进制 IPv4，原样（数字规范已由 D5 保证） |
| **规则 M（mapped → IPv4）** | D6.4 成立（`hextets[0..4]`=0 且 `[5]`=0xffff） | **一律**转为点分十进制 IPv4（`dotted(hextets[6],hextets[7])`），**与原始是否含点分尾段无关** |
| **规则 V（IPv6 规范化）** | IPv6 分支通过 D6.1~D6.3 且**不满足** D6.4，且**不含**嵌入式 IPv4 尾段 | 压缩、小写的规范 IPv6 文本 |

> 由此可直接推导：`::ffff:0:0`（无点分尾段）满足 D6.4 → 规则 M → `0.0.0.0`；`::ffff:192.168.1.1` → `192.168.1.1`；`::1`、`2001:db8::1` → 规则 V；`::0.0.0.2`、`64:ff9b::1.2.3.4` → D6.5 → null。

## 6. 配置项、路径派生与环境变量优先级

### 6.1 优先级与取值


| 行为 | 证据 |

### 7.5 文件权限预期（P0-D03 闭环，分文件规定）

| 对象 | 应用是否保证 | 生产实测（本轮只读 `stat`） | harness 断言 |
|---|---|---|---|
| `secret.key` | **是**，0600（write mode + chmod 双保证） | `600` | `mode & 0o077 === 0` |
| `admin-token.key` | **是**，0600（同上） | `600` | `mode & 0o077 === 0` |
| `forum.db`（含 `-wal`/`-shm`） | **否**——`mkdirSync`/`DatabaseSync` 均未设 mode | `644`（服务 umask `0022`，见 §12） | 仅断言：普通文件、非符号链接、realpath 在数据根内；**记录实际 mode 作证据**；**不断言 0600** |
| 数据根目录 | 应用 `mkdirSync` 未设 mode；但 harness 自建时为 0700，且已存在目录时 `mkdirSync` 为 no-op（不改变 mode） | 生产为 `755` | `mode & 0o077 === 0`（0700），这是隔离实例的实际访问边界 |

**说明**：
1. **不假定 umask**：即使 harness 进程 umask 为 0022，`mkdtempSync` 仍强制 0700；而应用对已存在目录的 `mkdirSync({recursive:true})` 不会修改 mode，故 0700 得以保留。
2. 数据库文件的「其他人不可读」由 0700 目录的遍历阻断保证，而非文件位。
3. **若项目要求数据库文件本身为 0600**，需要在 `db/database.js` 的 `init()` 中增加 `fs.chmodSync(config.DB_PATH, 0o600)`——这属于 S-01 范围之外的加固变更，须单独立项与授权；本设计**不假定**其存在，也不因其缺失而阻塞隔离测试（目录 0700 已满足隔离要求）。
4. 权限检查失败的处理（阶段 4.1/4.2）：**立即停止测试、kill 子进程、删除临时目录；若删除失败，报告路径与 errno 并以退出码 13 终止**。

### 7.6 密钥读取最小化（P1-D05）

| 操作 | 是否读取密钥内容 |
|---|---|
| harness 校验密钥文件 | **否**——只用 `lstatSync`/`realpathSync`/`statSync().mode` |

| 任何情况下读取生产路径密钥 | **禁止** |

### 7.7 实例身份关联的可执行方式（P1-D06）

**应用日志现状（只读核查）**：`server.js:31-35` 的 `accessLog` 输出 `[api] <METHOD> <req.url> <status> <ms>ms uid=<uid8>`，**不含请求 ID、不含时间戳到毫秒以下、不含对端端口**。因此无法用「唯一请求 ID」直接关联。

**可执行关联方案（不修改应用）**：
1. harness **串行**发送请求（不使用并发），避免日志行交错；
2. 每个请求的 URL 中附加唯一 nonce 查询参数，例如 `GET /api/topics?probe=<crypto.randomUUID()>`；应用忽略未知参数（`ctx.query` 只取已知键），但 `req.url` 被**原样**写入日志；
3. harness 在**自己启动的子进程** stdout 中查找该 nonce 字符串；命中即证明「该请求到达了本 harness 启动的实例」；
4. 同时校验子进程 PID 仍为 spawn 返回的 PID（排除 PID 复用导致的误判）。

**限制（如实说明）**：① 该方案依赖「串行 + URL 内嵌 nonce」，不能用于并发请求的身份关联；② nonce 会进入日志，故 nonce 必须是随机 UUID（不含秘密）；③ 若未来日志格式改变（不再记录完整 `req.url`），需重新设计。

### 7.8 清理失败行为（P1-D07）

| 场景 | 超时策略 | 可观测结果 | 退出码 |
|---|---|---|---|
| kill 子进程 | 先 `SIGTERM`，宽限 3s，仍存活则 `SIGKILL`，再等 3s | 打印 PID、信号序列、是否仍存活 | 14（仍存活） |
| 删除临时目录 | `fs.rmSync(root,{recursive:true,force:true,maxRetries:3})`，超 5s 视为失败 | 打印目录路径、errno、残留条目列表 | 13 |
| 多项失败并存 | — | 全部报告 | 取**最高**退出码（14 > 13 > 12 > …） |
| SIGINT/SIGTERM 中断 | 立即进入清理，不再启动新请求 | 同左 | 130 / 143 |

**不承诺 OS 无法保证的结果**：若 `SIGKILL` 后进程仍存活（例如处于不可中断的 D 状态），harness 只报告 PID 与状态，不声称已终止。

### 10.2 E2E-A：同一客户端 IP 的注册限流

| 项 | 内容 |
|---|---|
| 前置 | harness 已启动隔离实例并取得 `actualPort`（≠8787）；`BASE=http://127.0.0.1:${actualPort}` |

| 失败判定 | R1~R5 任一非 200；R6 非 429 或错误码不符；任何请求目标 ≠ BASE |
| 证据 | 序号、客户端 IP、状态码、错误码；**不记录 token**；**不读取密钥** |

### 10.3 E2E-B：不同客户端 IP 的桶相互独立

| 项 | 内容 |
|---|---|
| 前置 | E2E-A 已完成（A 桶 5/5） |
| B1 | 客户端 B（`X-Real-IP: 198.51.100.20`）注册 → 预期 `200` |
| B2 | 客户端 A 再注册 → 预期 `429` + `RATE_LIMITED` |
| B3 | 客户端 B 连续再注册 4 次（累计 5）→ 全部 `200`；第 6 次 → `429` |
| 失败判定 | B1 被 429（桶未隔离）；B2 变 200（桶被错误重置/共享）；B 与 A 计数混算 |
| 证据 | 每次请求的客户端 IP、状态码、错误码、时间戳 |

### 10.4 E2E-C：请求目标与实例身份校验

| 项 | 内容 |
|---|---|
| 目标校验 | ① 每个 URL 主机/端口 === harness 实际监听值；② 无请求发往 8787 / 生产域名 / 非预期本地端口 / 外部主机 |
| 身份关联 | ③ 串行请求 + URL 内嵌唯一 nonce（`?probe=<uuid>`），在**子进程 stdout** 中回查该 nonce（§7.7）；④ 校验子进程 PID 未变 |
| 隐私 | ⑤ 日志不记录 Token/Cookie/密钥；nonce 为随机 UUID，不含秘密 |
| 失败判定 | 出现非预期目标 → FAIL 并终止（exit 8）；stdout 无对应 nonce → FAIL |
| 证据 | harness 维护「请求目标集合」与「nonce→日志行」映射，结束时报打印 |

**分层声明**：单测（§9）只验证解析/规范化/键逻辑；端到端（§10）验证真实隔离服务行为。两者互不替代。

### 12.2 文件权限（本轮新增只读证据）

| 层级 | 内容 |
|---|---|
| **原始输出** | `stat -c %a`：`data` 目录 = `755`；`forum.db` = `644`；`secret.key` = `600`；`admin-token.key` = `600`；`/proc/2144097/status` 中 `Umask: 0022` |
| **执行方解释** | 与代码分析一致：`auth/token.js:20-21` 显式设置密钥 0600；`db/database.js:15-16` 未设置目录/DB mode，故按 umask 0022 得 755/644 |
| **最终推论** | 隔离实例中密钥必为 0600（应用保证）；数据库文件不为 0600（无应用保证），隔离访问边界由 harness 自建的 0700 目录提供 → §7.5 分文件规定 |
| **可复核性** | 同上，无法从交付材料独立复核 |

### 12.3 范围外观察（记录，不纳入 S-01 修复）

生产 `data/` 目录为 `755`、`forum.db` 为 `644`，意味着**同主机其他本地用户可读取论坛数据库**（含用户昵称/头像/内容；不含密钥，密钥为 600）。这属于既有的本地权限加固缺口，与 S-01 无关，建议单独立项（例如 `init()` 中 `chmodSync(DATA_DIR,0o700)` 与 `chmodSync(DB_PATH,0o600)`），**本设计不代为修改**。

## 16. 失败处理与回滚方案

### 16.1 回滚触发条件（任一）

`is-active` 非 `active`；`/api/topics` 5xx 上升或新增 `[500]`；L3 探针出现伪造 IP 被采信；注册 429 异常激增；`ip=` 字段缺失/格式错误；白名单之外文件哈希变化。

### 16.2 回滚步骤（逐文件，禁整目录覆盖）

1. `systemctl stop mcu-forum-api`（提前知会）。
2. 从发布前备份**逐文件**恢复 `server.js`、`config.js`。
3. **删除**新增文件 `lib/client-ip.js`（禁止 `cp -a backup/lib`）。
4. 校验：`sha256sum server.js config.js` 回到 `043509ba…` / `86586a22…`；`ls lib/` 与备份清单一致。
5. `systemctl start mcu-forum-api` → 复检 `is-active`、`ss -lntp | grep 8787`、`journalctl -n 20`。
6. 记录回滚时间、原因、恢复后哈希。

### 16.3 配置与数据兼容性

配置回滚 = 恢复 `config.js` 常量默认值；**无数据迁移**；必须重启才生效；**绝不触碰** `data/`、`forum.db`、`secret.key`、`admin-token.key`。

### 16.4 防覆盖他人在途改动

白名单文件操作；禁 `rsync --delete`、禁整目录覆盖、禁 `git` 类操作；发布前后各跑一次全目录 `sha256sum`。

### 16.5 运维检查清单

| 检查项 | 频率 |
|---|---|
| nginx `location ^~ /api/` 中 `proxy_set_header X-Real-IP $remote_addr;` 必须存在 | 每次改 nginx 后 |
| 应用仍仅监听 `127.0.0.1:8787` | 每次改 unit 后 |
| unit 未新增 `Environment=`/`EnvironmentFile=`（若新增须重跑 §12.1） | 每次改 unit 后 |
