### 1.2 必须纠正：本次「复联5提审被驳回」在仓库内没有任何凭证

- 仓库全部文档中，抖音提审历史止于「V2.4 待提审」，且 `project.json` L95-100 明确记载「截至 2026-11-10 仍无提审凭证」「V2.4 从未提交审核」。
- 仓库内**没有**本次复联5版本的单号、驳回通知、客服对话、后台截图。
- 因此本次驳回**只能记为「用户陈述，证据缺失」**：提交动作发生在仓库之外（开发者工具直传），不产生 git 记录。此前「从未提交」的表述应修正为：**V2.4 基线未被提交；而基于 V2.4 的复联5构建是否提交过，仓库无法证明，用户口述为已提交且被驳回**。

### 3.3 逐页要点（线上实际内容）

**① home**
- 影视背景图（`heroBanner`）+ 进度条；旅程卡（海报/中英文名/阶段/年份）；「作品查询」入口卡；「推荐下一部」大卡（含推荐理由与 CTA）；最近观看横滚。
- 可执行：继续观看、标记已看、进查询、进详情。
- 风险点：① 背景图与海报均为影视物料；② 「推荐下一部」+ 理由文案属于**影视推荐**，不是记录功能；③ 英文片名与年份属作品资料。
- 风险：**中**（不含查询检索，但推荐与资料展示明显）。

**② library（作品）**
- 搜索框「搜索作品名称」、类型/阶段/状态三组筛选、排序、重置、`共 N 部 / 全库 59 部 · 已看 · 收藏`、作品卡片（海报/中文名/英文名/类型·阶段·年份/顺序/已看未看）。
- 页面自述定位就是「**MCU 作品信息查询工具**」。
- 风险：**高**——这是「电影相关查询」最直接的落点，与客服口径正面冲突。

**③ movie（作品详情）**
- 海报、中英文名、类型标签、阶段标签、「我的观看状态」（已看/未看/已看时间）、标记已看、收藏、「作品信息」表（含**上映时间**、阶段、篇章、篇幅）、「**作品简介**」（`sf` 剧情一句话）、「相关作品 · N 条」（名称+`why` 关联说明，≤4 条）。
- 页面注释自述「无剧透，作品基础信息」，但 `sf` 本身即剧情概述；`why` 为剧情关联解读（例：「钢铁侠片尾彩蛋里尼克·弗瑞第一次提到复仇者计划…」）。
- 风险：**高**——剧情 + 上映信息 + 关联解读，是 V2.0 被驳回时「影视/文娱作品详情特征」的同源内容。

**④ my-mcu**
- 进度大数字、整体进度%、未看/收藏数；6 张入口卡（含分享）；成就墙；「我的片单进度」（当前路线 + 下一部）；最近观看；作品清单（全部/已看/未看/收藏，可就地取消收藏）；反馈；法务。
- 风险：**中**——以个人记录为主，但列表仍展示海报与作品资料。

**⑤ share**
- 三型 canvas 海报：progress / route / movie，含宇宙渐变背景、品牌盾徽、真实海报异步加载；保存相册、转发。
- 风险：**中**——「movie」型海报本质是影视物料再分发；「route」型海报会呈现观看路线。

**⑥⑦⑧⑨ feedback / about / agreement / privacy**

### 4.1 逐项风险判断

| # | 新增点 | 文件位置 | 可能触发审核的原因 | 风险 |
|---|---|---|---|---|
| 1 | 首页第 4 张卡「复联5准备 / 6 部阵营背景补课」 | `home.js` entries | 明确的**影视专题入口**，指向未上映影片的观影准备 | **高** |

### 4.2 关键判断

1. **不要把专题问题扩大成「整个产品必须删除」**。客服点名的是「复联5准备专题」与「电影相关查询服务」；线上 V1.3.0 仍在架，说明平台并未判定整个小程序不可存在。
2. **但也不能把专题问题当成「只是多了一个入口」**。复联5专项把「作品查询」升级成「为一部未上映电影组织观影路线」，性质从「资料查询」变成「影视专题策划 + 观影推荐」，正是客服口径中风险最高的形态。
3. **冻结决定**：本轮不追加、不修复、不重提复联5。工作区改动保持未提交状态，作为「结构与文案素材」留存，是否复用由产品决策。
4. **8 部/15 部差异**：若客服驳回时看到的确实是 8+15 的专题形态，则被审对象可能是 H5 专题或另一端构建；这一点必须先向平台/提交人核实（第八章 Q1），否则后续整改方向可能一开始就打偏。

## 五、三档精简方案

> 三档均**仅为分析建议，不代表平台允许保留相关服务**；三档都以「线上 V1.3.0」为基线，不涉及工作区代码。
> 共同原则：不以改文案、藏入口、改名称掩盖实际服务内容。

### 5.1 方案 A：最小精简（不改页面结构、不动核心功能）

目标：以最小改动消除「明显越界」的表述，但保留查询与详情能力。

| # | 动作 | 落点 | 预期效果 | 局限 |
|---|---|---|---|---|
| A1 | 首页「推荐下一部」标签与推荐理由改为中性记录口径 | `home.js` `tag` / `reason` | 去掉「影视推荐」语气 | 推荐行为本身仍在 |
| A2 | 关于页去掉「影视资料均来自公开信息整理」等资料供给表述，改为「仅记录个人观影进度」 | `about.wxml` | 消除自述性风险 | 与实际查询能力仍有落差 |
| A3 | 详情页「作品简介」改为**可选折叠/默认不展开**（或删去简介块） | `movie.wxml` | 减少剧情文本暴露面 | 数据仍在包内 |
| A4 | 删除包内已不展示的 `role` 剧情解读字段 | `data/movies.js` | 减少静态审查可发现的剧情文本 | 改动数据文件，需回归 |
| A5 | 详情页「相关作品」的 `why` 改为仅显示作品名+阶段，不显示关联解读 | `movie.js` | 去掉剧情关联说明 | 关联跳转仍在 |
| A6 | 首页背景图改为纯色/数据型背景，不放大图影视物料 | `home.wxml` | 降低「影视内容平台」观感 | 视觉风格变化 |
| A7 | 统一各页对「作品/电影/剧集」的称呼与定位描述 | 各页 `navigationBarTitleText`、注释文案 | 口径一致 | 不改变实质 |

适用：希望「先轻微调整再试一次提审」。风险：客服已明确「需删除电影相关查询服务」，A 档**大概率仍不满足**，属于低成功率尝试。

### 5.2 方案 B：适度精简（内容合并、次要页面收缩、降低影视密度）

| # | 动作 | 落点 | 产品价值变化 |
|---|---|---|---|
| B1 | 合并重复进度：home 只保留一个进度入口，与 my-mcu 进度统一 | `home` / `my-mcu` | 信息更清晰，功能不减 |
| B2 | 合并作品列表：my-mcu 的「我的作品清单」与 library 二选一，保留 library 作为唯一列表 | `my-mcu` 第 ⑥ 段 | 减少重复，入口更少 |
| B3 | 详情页收缩为「名称 + 阶段 + 宇宙序号 + 我的状态」，删除简介、上映时间、英文名、篇章 | `movie` | 观影记录仍可完成，但「查询感」下降 |
| B4 | 作品查询从「全库检索」收缩为「我的片单内检索」（默认只看自己的记录） | `library` | 从「作品库查询」转为「个人片单管理」，方向性变化 |
| B5 | 分享去掉「电影型」海报，只保留进度/成就海报 | `share` | 去掉影视物料再分发 |
| B6 | 成就与路线文案去掉「必看 / 推荐 / 补课」类表述 | `models/achievements.js`、`routes.js` | 语气中性化 |
| B7 | 删除包内未使用的角色、关系、路线数据（若页面不再消费） | `data/characters.js`、`relations.js`、`routes.js` | 包体与内容暴露面双降 |

适用：愿意牺牲一部分「查询」属性，把产品实质调整为**个人观影记录工具**。风险：B4 之后产品与「信息查询」类目已经名不副实，类目是否需调整需与平台确认（第八章 Q3）。

### 5.3 方案 C：较大幅度精简（保留 MCU 定位，舍弃查询型功能）

| # | 舍弃/收缩 | 保留 | 产品价值影响 |
|---|---|---|---|
| C1 | 删除 `library` 作品查询页（Tab2 空出） | 我的片单（从已有记录中选择/添加作品） | 失去「查得到任何一部 MCU 作品」的核心卖点；产品退化为记录器 |
| C2 | 删除 `movie` 作品详情页，改为轻量「记录详情」弹层 | 名称、已看时间、收藏、备注 | 失去资料查询价值，保留记录价值 |
| C3 | 删除 `share` 电影海报型 | 进度/成就海报 | 分享玩法缩水，但保留社交传播 |
| C4 | 删除包内 `characters / relations / routes` 数据 | 59 条作品名作为记录对象 | 包体最小、内容暴露面最小 |
| C5 | 首页改为「进度 + 下一步记录 + 最近记录」，去掉所有影视图片 | 纯数据型首页 | 视觉吸引力下降，审核风险最低 |
| C6 | 保留 `my-mcu`、`feedback`、三张法务页 | 完整工具闭环 | 无影响 |

适用：坚定保留个人主体与 MCU 主题、接受「从导航工具降级为观影记录器」。
代价：MCU 定位仍在（作品名与顺序仍是产品骨架），但「导航/查询」这个差异点基本消失。

## 七、推荐方案与风险

### 7.1 最值得保留的核心功能

1. **个人观影记录与进度**（已看/未看、时间、进度百分比）——与「查询」无关，是最安全的价值。
2. **收藏与片单**（个人数据，无内容供给）。
3. **成就体系**（游戏化激励，纯本地）。
4. **进度/成就海报分享**（社交传播，不含影视物料）。
5. **本地反馈**（产品迭代通道）。

### 7.2 建议精简 / 冻结 / 不再投入

| 类别 | 对象 |
|---|---|
| 建议精简 | 首页影视背景图、推荐理由、关于页「影视资料」表述、重复的进度与清单入口 |
| 建议冻结 | 复联5 全部新增（入口卡、第 12 条路线、路线说明、补课区块、`pendingRoute` 引导点）、8/15 专题的任何抖音移植 |
| 不建议继续投入 | 作品全库查询与详情资料化、角色/关系图/随机探索、影视资讯与专题策划、H5 引流（V2.3 已因此被驳） |

### 7.3 最小修改方案（若仍想再试一次提审）

以**线上 V1.3.0 为基线**，只做 4 件事，不回退到工作区 V2.4 结构、不引入复联5：

1. 关于页与首页去掉资料供给/推荐语气（A1、A2）。
2. 详情页删除「作品简介」与 `why` 关联解读，只留名称/阶段/序号/我的状态（A3、A5）。
3. 首页背景图改数据型，不放大图影视物料（A6）。
4. 删除包内不再展示的 `role` 等剧情文本（A4）。

预期：这是「最小改动 + 明确降低影视内容供给」的组合，但**仍保留作品查询**，因此**不保证能过**，且与客服「需删除电影相关查询服务」的原话存在直接冲突。

### 7.4 是否值得继续以个人主体运营（独立判断）

- **按客服口径字面执行**：个人主体 + 工具-实用工具-信息查询，不允许「电影相关查询」→ 现有产品的**核心卖点（作品库查询 + 详情资料）必然被砍**，剩下的只有记录工具。继续以个人主体运营**只有「观影记录器」这一条路**，且仍需接受「作品名本身即影视信息」的判定不确定性。
- **若坚持保留查询/路线/专题**：客服给出的路径是**企业主体 + 文娱-文娱-资讯**，这不是文案或页面能替代的资质问题。
- **折中判断**：个人主体可继续运营「记录工具」形态（方案 C），但需要产品接受「MCU 导航 → MCU 记录」的定位收缩；如果不接受这个收缩，那么在个人主体下继续投入的性价比很低。
- **不建议**：反复微调文案后反复提审（已有 4 次驳回记录，第 5 次同质提交的边际收益低，且有账号处罚风险）。
