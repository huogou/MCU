【二】A 项裁定 —— event-merger 与 supersedes 的关系

  事实：两套机制**管辖范围不同**，并行存在。
    event-merger：**管道层**，对象=多条报道（不同来源），依据=event_key + 时间窗口，
      结果=归并为一个事件对象，**不改交付数据**
    supersedes 链：**数据层+展示层**，对象=同一发布方的前后两版本，依据=更正声明（R8.5），
      结果=保留两条 + 互链 + 展示合并为一条
  建议条款：
    A1 event-merger 只做两件事：①减少候选条数 ②组装来源证据（reported_by_union）
    A2 **不替代** supersedes_id / superseded_by_id
    A3 **不修改交付数据**（不写文件、不改任何条目的任何字段）
    A4 同时命中两套机制时（010/014 即此情形）→ **以 supersedes 为准**，
       event-merger 不得据此删条、不得压成一条、不得改互链
    A5 G6 落库红线：交付数据**仍须保留 supersedes 双条与互链**；展示层合并照旧
    A6 G6 须有断言证明「supersedes 双条都在且互链成对」，防归并逻辑侵蚀
  ★ 现状代码已符合 A3（reports 不裁剪、records_deleted 恒 0、输出无状态字段）
  ★ 为何必须 G5 前定：不定则实现者可能把归并结果直接落库 → 链式引用丢失、可追溯性破坏

【三】B 项裁定 —— event_key 使用边界

  B1 **不是数据库唯一主键** —— 它是「事件签名指纹」，同一签名可对应多个时间分离的
     occurrence（实测 E2b：同 key 产出 **2 个 hold 事件**）
  B2 **不作为报道实体 ID** —— 报道 ID 是交付数据的 `id`（news-YYYY-MM-DD-NNN），
     两者不可互换：`id` 标识「一条报道」，`event_key` 标识「一个事件签名」（仅管道层用）
  B3 **不得**用于：①写库/落文件主键 ②对外 URL 参数 ③任何展示 ④跨端关联键
  B4 主键方案建议（二选一）：
     **B-i 组合键** `event_key + '@' + first_publish_time` —— 零代码改动，
       但串长、含时间语义易被误用
     **B-ii occurrence（开发侧倾向）** `occurrence` = 同 key 下按 first_publish_time
       升序从 1 编号；主键 = `event_key + '#' + occurrence` —— 稳定、短、语义清晰，
       但需改 merger（**新增 1 个输出字段**）
     ★ B-ii 三个实现要点：①编号必须**在同一批次全量排序后**生成（分两批会冲突）
       ②新字段只出现在输出中，**不得写回输入数据** ③新增 2 条断言（编号连续无重复、
       组合主键在输出内唯一）
     ★ **本轮未实现**（任务只要求建议）；若批准属 **G4.2 小补丁**，
       不触碰 G1/G2/G3，不影响既有 95 条断言
  B5 既知口径限制（非缺陷但须知悉）：不区分状态（刻意，R8.8）｜
     无实体时识别力弱（文本模式）｜窗口 3 天未校准

【四】C 项 —— judged_by 语义两方案比较（**不修改代码**）

  事实基线：
    · 审计字段，必填，3 值枚举
    · 现有 15 条分布：human_confirmed **8**（001/003/008/009/010/011/013/014）｜
      rule_validated **2**（002/005）｜ai_suggested **5**（004/006/007/012/015）
    · 判定器默认派发：Step 1–4 → human_confirmed；Step 5–8 → rule_validated
    · **差异 7 条**：003 / 004 / 006 / 007 / 011 / 012 / 015
    ★ **更正我上一份报告**：G1 报告写「6 条差异」，实际**数据层面是 7 条**；
      测试输出报 6 条，是因为黄金用例 fixture 对 003 显式传了 judgedBy 覆盖。

  方案 a = **最终确认者**（谁最终确认了这条状态）
    优：现有 15 条天然符合（无需改数据）；可直接统计「AI 建议采纳率」「人工介入比例」；
        最贴 R3.5 三层机制原意
    劣：判定器需**新增输入位**（是否 AI 提过建议、是否被改动）→ 依赖管道历史状态 →
        **破坏纯函数与幂等性**（「同输入两次同输出」断言会失效）；
        同一条证据在不同历史路径下得到不同 judged_by → 跨批次审计失去可比性

  方案 b = **判定层级**（本次判定由哪一级做出）
    优：判定器**零改动**（当前实现即此方案）；保持纯函数与幂等；审计可比性强
    劣：需在 **G8** 统一改写 7 条数据；`ai_suggested` 永不被判定器产出 →
        **三值枚举实际退化为两值**；「AI 采纳率」需改用管道字段比对

  **开发侧建议：方案 b**，三条理由：
    ① 审计字段语义应唯一且由本层**确定性产出**，否则同一条证据在不同批次结论不同
    ② 「谁确认的」本质是**运行历史**，已由 status_history（reason/at/evidence_url）
       + 管道字段 ai_suggested_status / reviewed_by / reviewed_at 完整承载，
       不必挤进一个三值枚举
    ③ 方案 a 会让纯函数判定器依赖管道历史状态，破坏 G1 的可重入性与可测性

  若选 b 的配套动作（本轮一律不做）：G8 改写 7 条 judged_by（需批准）+
    采纳率统计改由管道字段比对得出 + 规范补一句「judged_by 表示本次判定层级，
    不表示最终确认者」
