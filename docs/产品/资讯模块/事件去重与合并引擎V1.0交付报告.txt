1. 一、event_key 设计
============================================================

■ 1.1 定位与形态

  用途：识别「同一条新闻事件」，为去重与合并提供**确定性指纹**。
  形态：`evt1-` + 16 位十六进制（sha1 前 16 位），形如 `evt1-ef028cf29e74d90e`。
  性质：纯函数、零网络、零 AI、零副作用、**无时间依赖**。

■ 1.2 ★ 明确禁止「直接 title hash」——本实现如何做到

  事件指纹由**三个可审计成分**合成，再对成分取哈希：

  ┌────┬──────────────┬────────────────────────────────────────────────────────┐
  │ #  │ 成分          │ 构成                                                    │
  ├────┼──────────────┼────────────────────────────────────────────────────────┤
  │ ①  │ entitySig    │ 关联实体集合 → 规范化为 `kind:id`（movie/series/          │
  │    │ **主信号**    │ character），去重 + 排序                                │
  │ ②  │ actionSig    │ 标准化标题命中的「事件动作词」集合（封闭词表，**不含状态词**）│
  │ ③  │ textSig      │ 标题文本指纹（中文 2-gram + 拉丁词 + 数字）——**仅作兜底**  │
  └────┴──────────────┴────────────────────────────────────────────────────────┘

  **模式选择（关键设计）**：
    · `entitySig` 非空 → `mode = 'entity'`，payload **不含标题文本**（textSig 置空）
    · `entitySig` 为空 → `mode = 'text'`  ，退化为文本指纹

  payload 结构（明文可审计）：
    `v=1;cat=<category>;ent=<…>;act=<…>;mode=<…>;txt=<…>`
  → `event_key = 'evt1-' + sha1(payload).slice(0,16)`

  ★ 「不是 title hash」的**反向证明**（已写成断言）：
    两个**标题不同**但实体与动作相同的条目 → `event_key` 相同；
    而这两个标题的 sha1 **不同**。若实现是 title hash，必然得出不同 key。
    测试 E8 同时断言：`key ≠ sha1(title)`、`key ≠ 'evt1-' + sha1(title).slice(0,16)`。

  另提供 `explain(input)` 审计接口，显式暴露三成分、标准化后的标题、
  被移除的日期与括号，以及 `time_participates: false`。

■ 1.3 标准化词表（四类，全部封闭、可回归）

  ┌──────────────┬──────────┬──────────────────────────────────────────────────┐
  │ 词表          │ 条数     │ 作用                                              │
  ├──────────────┼──────────┼──────────────────────────────────────────────────┤
  │ TEMPLATE_WORDS│ 35      │ 媒体模板词（独家/快讯/首发/重磅/深度/据悉/首支…）→ 删除 │
  │ STATUS_WORDS  │ 28      │ 状态与措辞词（官方/正式/官宣/确认/否认/辟谣/传闻/       │
  │              │          │ 网传/爆料/据称/疑似/将/已/可能/计划…）→ 删除            │
  │ FUNCTION_WORDS│ 47      │ 功能词（的/了/在/与/和/是/为/被/把/对…）→ 删除         │
  │ ACTION_WORDS  │ 58      │ 事件动作词（预告/上映/定档/改档/杀青/选角/续集/完结/     │
  │              │          │ 首映/票房/剧照/开发/访谈/联动/更名…）→ **参与 actionSig** │
  └──────────────┴──────────┴──────────────────────────────────────────────────┘

■ 1.4 两条必须说清的设计取舍

  【取舍 1】**publish_time 不参与 key**
    · 依据：需求 E4「日期不同 → 可识别同事件」。
    · 时间只由 merger 用于**时间窗口候选判断**，不进入指纹。
    · 测试 E4b 断言：仅改 publish_time（相差 300 天）→ key **完全不变**。

  【取舍 2】**状态词不参与 key**
    · 依据：R8.8「状态不是永久事实标签」—— 同一条事件会随证据演进改状态，
      事件身份必须**跨状态稳定**；否则每次状态变更都会生成新的 event_key，
      历史归并结果全部失效。
    · 测试 E14 断言：「Marvel 官方确认《雷霆特攻队*》续集进入开发」与
      「网传《雷霆特攻队*》续集可能将进入开发」→ **同 key**。
    · ★ 这意味着：**不能**用 event_key 区分「已确认」与「传闻」两条不同报道
      ——这是刻意行为，状态区分由 G1 判定器负责（见 5.2 待确认）。

2. 二、合并规则（第一阶段：仅规则层）
============================================================

■ 2.1 标题标准化（三步，全部已实现）

  Step 1 **去日期**：中文年月日 / 年月 / 月日 / `YYYY-MM-DD` / `MM-DD-YYYY` /
         英文月份（Jan 5, 2026 / 5th January 2026）共 7 类模式；
         另剔除独立出现的 19xx / 20xx 四位年份。
  Step 2 **去符号**：全角转半角 → 去噪声括号（【】〖〗［］[_]整块删除）→
         去书名号/引号/圆括号等括号符号（**保留其内容**）→
         去除所有非「中日韩文字 / 字母 / 数字 / 空格」的标点符号。
  Step 3 **去模板词**：模板词 → 状态词 → 功能词（长词优先替换，避免短词切碎长词）。

  标准化结果可通过 `explain().normalized_title` 直接查看；
  被移除的日期与括号在 `explain().removed` 中留痕。

■ 2.2 关联对象参与计算

  · `related_movies` → `movie:<id>`
  · `related_series` → `series:<id>`
  · `related_characters` → `character:<id>`
  · 去重 + 排序后作为 entitySig，是**主信号**。
  · 容错：字段缺失 / null / 非数组 / 数组含 null·空白·非字符串元素
    一律跳过（测试 E5 共 7 个变体，全部不抛错）。

■ 2.3 时间窗口（**仅用于候选判断**）

  · 默认窗口 `WINDOW_DAYS = 3` 天（可经 `opts.windowDays` 传入）。
  · 窗口内的同 key 条 → 链式聚为一簇 → `decision = 'merge'`。
  · 同 key 但聚成多簇（跨度超窗口）→ **每簇各自输出，`decision = 'hold'`，
    `hold_reason = 'out_of_window'`**。
  · 缺时间的条（publish_time 与 first_seen_at 均无效）→
    `decision = 'hold'`，`hold_reason = 'missing_time'`（保守：缺数据一律不合并）。
  · ★ 窗口**只决定「能否自动合并」**，不改变任何条目内容、不改变任何状态。

  `decidePair(a, b, opts)` 提供两两比较入口，返回
  `{ same_event, within_window, decision, reason }`。

■ 2.4 输出结构

  ```
  {
    merger_version: '1',
    window_days: 3,
    events: [
      {
        event_key,
        item_ids: [...],  report_count,
        category,
        first_publish_time, last_publish_time,
        within_window: boolean,
        decision: 'merge' | 'single' | 'hold',
        hold_reason: '' | 'out_of_window' | 'missing_time',
        reports: [ { id, publish_time, first_seen_at,
                     source_names, source_urls, owner_groups } ],   ← 不裁剪
        reported_by_union: [ { source_name, source_url, owner_group } ],
        distinct_owner_groups: [...],
        note: '本条目不含任何状态信息；状态须由 G1 判定器按 R8.3 重算'
      }
    ],
    stats: { input_items, output_events, reports_preserved,
             mergeable_events, held_events, records_deleted }
  }
  ```

  ★ `reported_by_union` 的定义与边界：它只是**已有来源证据的并集**，
    作为**输入材料**交 G1 判定器重算；本层不产出、不推导、不缓存任何状态。
    输出结构经 `FORBIDDEN_OUTPUT_KEYS`（6 项状态字段）反向约束，测试做深层扫描。

5. 五、发现与待确认
============================================================

■ 5.1 ★【待裁定】事件归并与 R8.5 的 supersedes 合并**语义交叠**
  · 事实：真实数据跑的 14 个事件中，唯一被归并的正是 010 / 014 这一对
    —— 它们同时受两套机制管辖：
      a) **R8.5 supersedes 合并**（展示层）：保留两条数据、互链，
         **列表展示时合并为一条**，以更正后内容为准；
      b) **event-merger 事件归并**（管道层）：按事件指纹把两条并为一个事件。
  · 两者结论方向一致（都表现为「一条」），但**机制与落点不同**：
    前者已在前端实现（`supersedes_id` / `superseded_by_id` + 合并展示），
    后者属管道层。
  · 风险：若下游把「事件归并」的结果直接写成交付数据，
    会与 R8.5 的「**保留两条**、互链」要求冲突 —— 双条被压成一条，链式引用丢失。
  · 建议（明确指出，非结论）：在规范层写清一句
    「**事件归并只用于管道层减少候选与组装来源证据，不得替换 R8.5 的双条保留 + 互链**；
      交付数据仍须保留 supersedes 双条，展示层合并照旧。」
  · 该问题不阻塞本阶段（本阶段未写任何交付数据），但**必须在落库阶段（G6）之前定案**。

■ 5.2 ★【待确认】event_key 刻意不区分状态，需产品确认是否认可
  · 设计取舍：状态词（官方/确认/传闻/辟谣…）不参与 key，使事件身份**跨状态稳定**（R8.8）。
  · 副作用：**「官方确认」与「传闻」两条不同报道会得到同一个 event_key**。
  · 影响：若下游想按「报道层级」做筛选或统计，不能用 event_key，必须另用
    `reported_by` / tier / 判定器输出的状态。
  · 我方判断：这与 R8.8 一致，且事件身份本就不应随状态漂移。
    但这是产品语义决定，**请负责人确认**。

■ 5.3 ★【工程风险】event_key **不是**事件级唯一键
  · 事实：同 key 在窗口分裂时会产出**多个** hold 事件（如 E2b：2 个事件同 key）。
  · 风险：若下游把 event_key 当主键写库 / 做去重键，会主键冲突或误覆盖。
  · 建议：下游主键改用 `event_key + first_publish_time`，或在输出中引入
    occurrence 序号（本阶段未加，避免超出任务范围）。

■ 5.4 【已知限制】无实体的「同事件不同标题」识别不了
  · 实体模式（有 `related_*`）下，措辞差异不影响 key（E1 成立）。
  · 但**实体为空**时退化为文本指纹 → 「同事件不同标题」**不会被识别为同一事件**
    （宁可不合、不可误合）。
  · 实测影响：真实 15 条中 007（`reported_by: []`、`related_*` 仅 series）
    与 005（`related_movies` 有值）等条目仍能生成稳定 key，未出现误合；
    但真实采集数据中「无实体且标题差异大」的条目会各占一个事件。

■ 5.5 【未校准】时间窗口默认 3 天为工程判断
  · 未用真实数据校准。R2.5 的单日快照显示 MCU 资讯日产出 5–10 条，
    同事件多来源报道通常集中在 1–2 日内；3 天偏宽松。
  · 建议 G5 实测后回调（如 2 天）。
