2. 语义规定（采用方案 b：判定层级）
============================================================

■ 2.1 正式语义（一句话）

  **judged_by 表示「本次判定是由哪一级做出的」，
    不表示「这条状态最终由谁确认」。**

■ 2.2 取值判定规则（可执行）

  ┌────────────────────┬──────────────────────────────────────────────────────┐
  │ 取值                │ 判定条件                                              │
  ├────────────────────┼──────────────────────────────────────────────────────┤
  │ `human_confirmed`  │ 命中判定链 **Step 1 – Step 4**                        │
  │                    │ （受控步骤：官方确认 / 官方否认 / 更正 / 冲突，          │
  │                    │  按 R3.5 第三层必须人工介入）                          │
  ├────────────────────┼──────────────────────────────────────────────────────┤
  │ `rule_validated`   │ 命中判定链 **Step 5 – Step 8**                        │
  │                    │ （纯规则可判：多源 / 单一来源 / 爆料 / 兜底）            │
  ├────────────────────┼──────────────────────────────────────────────────────┤
  │ `ai_suggested`     │ ★ **不由判定器产出**。保留为**管道理历史中间态**：       │
  │                    │  AI 提出建议、但尚未经规则确认或人工复核时的过渡标记。     │
  │                    │  G6 落库后交付数据中**不应出现**该取值（见第 5 节）      │
  └────────────────────┴──────────────────────────────────────────────────────┘

■ 2.3 三条派生规定

  ① **确定性**：judged_by 只由「命中步骤」决定，**不依赖任何历史过程**。
     → 同输入必得同输出；「同输入两次运行输出一致」的断言继续成立。
  ② **可覆盖**：允许调用方通过 `opts.judgedBy` 显式覆盖，
     但覆盖必须**留痕**（在 `status_history[].reason` 中说明覆盖原因）。
     现状用例：003 号条目系人工复核发现「伪多源」，覆盖为 `human_confirmed`。
  ③ **不得由 AI 直接写入**：AI 只能产出建议值（管道字段 `ai_suggested_status`），
     **不得**写入 judged_by。


============================================================
3. 与 status_history 的分工
============================================================

  「谁确认的」这一信息**不由 judged_by 承载**，而由以下字段完整承载：

  ┌────────────────────────────────────┬──────────────────────────────────────────┐
  │ 承载字段                            │ 承载内容                                  │
  ├────────────────────────────────────┼──────────────────────────────────────────┤
  │ `status_history[].reason`          │ 每次状态变更的依据说明（是否人工介入）        │
  │ `status_history[].at`              │ 变更时间                                  │
  │ `status_history[].evidence_url`    │ 证据回链                                  │
  │ `status_change_reason` / `_at` /   │ 最近一次变更的同项信息                      │
  │ `_evidence_url`                    │                                          │
  │ 管道字段 `ai_suggested_status`       │ AI 的建议值（与最终状态分离存放）             │
  │ 管道字段 `reviewed_by` / `reviewed_at`│ 人工复核者与时间（R7.5 已对社交来源强制）      │
  └────────────────────────────────────┴──────────────────────────────────────────┘

  ★ 结论：**judged_by 不必也不应承担「确认者溯源」职责** —— 该信息已有专属字段。


============================================================
4. 统计口径变更
============================================================

  「AI 建议采纳率」等指标**不再**由 judged_by 统计，改由**管道层字段比对**得出：

  ```
  ai_suggested_status  ==  verification_status   →  建议被采纳
  ai_suggested_status  !=  verification_status   →  建议被修正
  ```

  该口径的优点：①不依赖 judged_by 的语义 ②可区分「被规则修正」与「被人工修正」
  （配合 `status_history[].reason` 判断）③与 judged_by 的解耦使两者各自可独立变化。

  ※ 若后续需要「人工介入比例」指标，可由
     `judged_by == 'human_confirmed'` 的占比直接得出（方案 b 下该值语义唯一）。

6. 未采纳方案 a 的理由（记录）
============================================================

  方案 a（judged_by = 最终确认者）未采纳，理由三条：

  ① **审计字段语义必须唯一且由本层确定性产出**。
     否则同一条证据在不同批次会得到不同 judged_by，跨批次审计失去可比性。
  ② **「谁确认的」本质是运行历史**，已由 status_history 与管道字段
     （`ai_suggested_status` / `reviewed_by` / `reviewed_at`）完整承载，
     不必挤进一个三值枚举。
  ③ **方案 a 会让纯函数判定器依赖管道历史状态**，破坏 G1 的可重入性与可测性——
     G1 现有的「同输入两次运行输出一致」断言会失效。

  ※ 方案 a 的唯一显著优势（现有 15 条数据天然符合）不足以抵消上述三项代价。
