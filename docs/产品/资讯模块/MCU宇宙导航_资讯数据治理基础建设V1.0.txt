1. 一、MCU 资讯数据字段规范 V1.0
============================================================

■ 1.1 规范范围与三条总原则

  范围：交付给 H5 的资讯数据（当前载体 h5/data/news.js，`window.MCU_NEWS`）。
  不含：采集原始记录、AI 中间产物、审核流水（均属管道层，见 1.5）。

  原则一 **交付物结构冻结**：交付数据的字段集合 = 前端展示字段 + 审计字段，
        共 33 个。管道字段一律不得进入交付物。
  原则二 **只增不改**：允许新增可选字段（需出增量规范），
        永不允许改名、改类型、改语义、改嵌套键名。
  原则三 **派生字段禁写**：凡可由其他字段计算得出的值，一律不落库为可写字段。

■ 1.2 三类字段总览

  ┌──────────────┬──────┬──────────────────────────────────────────┐
  │ 类别          │ 数量  │ 去向                                      │
  ├──────────────┼──────┼──────────────────────────────────────────┤

  │ 审计字段      │ 7    │ 进入交付物，不渲染，用于追溯与重新判定        │

  │ P12│ rule_version           │ string       │ 判定器版本号。规则升级后，历史结论可复算        │
  └────┴────────────────────────┴──────────────┴──────────────────────────────────────────────┘

  ※ P12 建议同时以只读形式出现在审计字段中（可选），否则无法判断
    「某条历史结论是按哪版规则算出来的」。是否采纳见 Q-4。

■ 1.6 嵌套对象结构定义

  reported_by[]（每项）
    source_name   string  必填   来源展示名（**须与 source_registry.source_name 完全一致**）
    source_url    string  必填   文章级 URL（fail 时不得用栏目/feed 级替代）
    owner_group   string  必填   所属集团；未确认一律写「待核」（禁凭来源名填空）

  status_history[]（每项）
    from          string|null   变更前状态（首次入库为 null）
    to            string        变更后状态（8 态之一）
    at            string ISO    变更时间
    reason        string        变更依据（须可对应判定链某一步）
    evidence_url  string        证据 URL（可为 ''，但引入证据的变更必须填）

  report_corrections[]（每项）
    source_name          string   发布更正的来源
    corrected_at         string ISO 更正时间
    original_statement   string   原文表述
    corrected_statement  string   更正后表述
    evidence_url         string   更正声明回链

  conflict_statements[]（每项）
    source_name  string   持该表述的来源
    statement    string   该来源的具体表述
    source_url   string   回链

■ 1.7 枚举定义

  verification_status（**冻结 8 值，禁止新增**）
    official_confirmed / multi_source_reported / single_source / rumor /
    unverified / conflicting / officially_denied / corrected
    ※ 硬约束来源：components.js 的 NEWS_LABEL 只有 8 个键，
      未知值一律兜底 unverified（第 481 / 611 / 702 行）→ 新增状态会静默显示错标签。

  category（**当前未定义，待补**）
    现有实际取值：movie / series / character
    待定候选：movie / series / special / short / character / industry / event
    ※ 定义前不得新增取值（新值无渲染位、无筛选位，仅会增加口径分歧）→ 见 Q-1

  judged_by（3 值）
    ai_suggested（AI 建议，尚未规则确认）
    rule_validated（判定链计算得出）
    human_confirmed（人工复核通过）

  crawl_policy（用于 source_registry，见 2.3）
  tier（用于 source_registry，见 2.3）
  health（用于 source_registry，见 2.3）

■ 1.8 命名与格式约定

  1. id 格式固定 `news-YYYY-MM-DD-NNN`，NNN 为当日三位序号。
     ★ 已知局限：**跨天重复入库无法通过 id 识别**（见 P1 event_key）。
  2. 日期：publish_time 用 `YYYY-MM-DD`；其余时间戳用 ISO8601 带 UTC（如 2026-09-22T01:10:00Z）。
  3. 空值：字符串缺失一律 `''`，**禁止 null 与 undefined 混用**；
     数组缺失一律 `[]`；仅 supersedes_id / superseded_by_id /
     pinned_until / conflict_resolved_at 等「有明确空语义」的字段允许 null。
  4. URL：必须 http(s)。`javascript:` / `data:` 等会被前端 safeUrl() 置空，
     表现为「链接消失」而非报错。
  5. 所有字符串字段在渲染前均经 esc() 转义 → **不得承载 HTML 或 Markdown**。
  6. 来源展示名（reported_by[].source_name）与 source_registry.source_name
     必须逐字符一致，否则详情页星标与来源卡会与登记表脱节。

■ 1.9 硬约束 8 条（新增数据前必照，全部来自实测）

  ┌──┬────────────────────────────────────────────┬──────────────────────────────────────┐
  │# │ 约束                                        │ 违反后果                              │
  ├──┼────────────────────────────────────────────┼──────────────────────────────────────┤
  │1 │ summary 必须纯文本                           │ HTML/MD 原样显示成乱码                  │
  │2 │ publish_time 与 first_seen_at 至少一个非空    │ **条目静默消失**（无报错、无告警）        │
  │3 │ 日期只展示到日，禁止时分与实时性措辞           │ 违反 R4.1 措辞红线                     │
  │4 │ source_url / official_source_url 必须 http(s) │ 链接被置空，来源卡失去回链                │
  │5 │ 不得引入图片 / 视频类字段                     │ 卡片无图片区域，**新增字段不会被渲染**     │
  │6 │ related_* 必须命中真实 id，未命中一律丢弃      │ 节点静默少一个（不报错）                 │
  │7 │ owner_group 为「待核 / unknown / 未确认 / 空」 │ 不计入独立组 → 状态会被误降级             │

  └──┴────────────────────────────────────────────┴──────────────────────────────────────┘

2. 二、source_registry 数据结构设计

■ 2.1 定位

  · 载体：**管道层数据文件**（建议 JSON，存于管道侧，不进 h5/data/）。

  3. owner_group 未确认时必须显式写「待核」，**不得凭来源名填空、不得默认自成一组**（R6.1）。
  4. 同一 owner_group 下的多个来源，无论多少家，**只计 1 个独立证据**（R3.1）。
  5. crawl_policy = ai_ban_named / ai_ban_notice 的来源，**禁止任何形式的自动抓取**，
     仅允许人工阅读后录入（R6.3）。
  6. 连续 3 次抓取失败 → 自动置 paused 并告警，**不得继续空跑**（R6.2）。


============================================================
3. 三、资讯状态判定器规则 V1.0
============================================================

■ 3.1 设计目标与边界

  做什么：把 R8.3 的 8 步判定链**形式化为可执行规则**，
        输入证据 → 输出唯一状态。本文件只写规则，不写实现。
  不做什么：不采集、不抓取、不生成摘要、不写文案、不自建来源。
  性质：纯确定性规则（同输入必得同输出），**不含任何 AI 判断**。

■ 3.2 输入定义

  ┌────┬────────────────────┬──────────────────────────────────────────────────────┐
  │ #  │ 输入                │ 定义与要求                                            │
  ├────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ I1 │ 来源证据            │ reported_by[]：每项含 source_name / source_url /     │
  │    │                    │ owner_group。owner_group 须经 source_registry 校准     │
  ├────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ I2 │ owner_group 映射     │ 来自 source_registry。**判定器只认已确认的组，        │
  │    │                    │ 「待核 / unknown / 未确认 / 空」一律视为不可用**       │
  ├────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ I3 │ 官方声明            │ official_source_url **且必须通过 R7.4 的 Step 1–3    │
  │    │                    │ 机器校验**（可访问 → host 命中 → path 命中）。        │
  │    │                    │ ★ 媒体转述「官方确认」不构成该输入                     │
  ├────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ I4 │ ★ **独立证据组数**   │ **不是「媒体数量」**。口径纠正见下方 ※                │
  ├────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ I5 │ 更正记录            │ report_corrections[]：发布方更正声明                   │
  ├────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ I6 │ 冲突记录            │ conflict_statements[]：互斥表述                        │
  ├────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ I7 │ 原始来源            │ original_source + original_source_url                 │
  ├────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ I8 │ 关联 id 集合         │ MCU_CONTENT / MCU_CHARACTERS 的真实 id（用于入库前校验）│
  └────┴────────────────────┴──────────────────────────────────────────────────────┘

  ※ **口径纠正（重要）**：任务描述的输入写作「媒体数量」。
    R3.1 已明确重定义：**multi_source_reported 的判定不再基于「报道网站数量」**，
    改为基于 `independent_group_count`（reported_by 按 owner_group 去重后的组数）。
    反例（现有 003 号用例）：Variety + Deadline + THR 三家报道，
    但三家同属 Penske Media Corporation → 独立组数 = 1 → 只能判 single_source。
    若判定器接收「媒体数量 = 3」为输入，会得出错误的 multi_source_reported。
    → **判定器接口必须接收 I2（owner_group 映射）并自行去重，不接受外部传入的计数。**

■ 3.3 派生计算规则（独立证据组数）

  以 reported_by 为输入，计算 `independent_group_count`：

    Step A 逐项取 owner_group
    Step B 丢弃 owner_group 为「待核」「未确认」「unknown」或空白的项
    Step C 对剩余项按 owner_group 去重计数
    Step D 输出计数结果

  约束：
    · 该值**禁止人工填写**，也禁止由 AI 提供（R3.1 / R8.3 约束 a）
    · 交付数据中的 independent_group_count 必须与该计算一致，
      由 test-news-rules.cjs 逐条断言（现有断言已覆盖）
    · 边界：reported_by 为空数组 → 0；全部 owner_group 待核 → 0

■ 3.4 判定链（8 步，按顺序短路执行）

  执行方式：从 Step 1 开始，**首个条件成立即输出该状态并终止**；
  全部不成立则落到 Step 8。每一步都必须记录 chain_steps_hit。

  ┌──────┬────────────────────────────────────────────────┬────────────────────┬────────────┐
  │ 步骤  │ 条件（判定器可执行判据）                          │ 输出状态            │ 依赖输入    │
  ├──────┼────────────────────────────────────────────────┼────────────────────┼────────────┤
  │Step 1│ 存在 official_source_url 且通过 R7.4 六步校验      │ official_confirmed │ I3 + 人工   │
  │      │ （Step1 可访问 / Step2 host 命中 / Step3 path 命中│                    │ 复核        │
  │      │  / Step4 内容对应当前事件 / Step5 人工复核通过）   │                    │            │
  ├──────┼────────────────────────────────────────────────┼────────────────────┼────────────┤
  │Step 2│ 存在官方**明确否认**，且该否认可回链到登记的官方    │ officially_denied  │ I3 + 人工   │
  │      │ 来源 URL（媒体转述否认不算）                      │                    │ 复核        │
  ├──────┼────────────────────────────────────────────────┼────────────────────┼────────────┤
  │Step 3│ 该事件的**全部有效报道**均已被其发布方发布更正，     │ corrected          │ I5 + 人工   │
  │      │ 且不存在其他仍有效的证据                          │                    │ 复核        │
  │      │ ★ 注意：Step 3 只施加于「被更正的该条报道」；      │                    │            │
  │      │ 若仍有其他有效证据，事件级**不得**在 Step 3 终止， │                    │            │
  │      │ 必须继续执行 Step 4 及后续（R8.5 事件级语义）      │                    │            │
  ├──────┼────────────────────────────────────────────────┼────────────────────┼────────────┤
  │Step 4│ 两个及以上**可靠来源**对**同一要素**给出互斥表述    │ conflicting        │ I6 + 人工   │
  │      │ （如 A 说延期、B 说按期）                        │                    │ 复核        │
  ├──────┼────────────────────────────────────────────────┼────────────────────┼────────────┤
  │Step 5│ 独立证据组数 ≥ 2，且各来源表述一致，且来源质量不低   │ multi_source_      │ I1 + I2     │
  │      │                                                │ reported           │            │
  ├──────┼────────────────────────────────────────────────┼────────────────────┼────────────┤
  │Step 6│ 独立证据组数 = 1，且该来源为可靠媒体               │ single_source      │ I1 + I2     │
  ├──────┼────────────────────────────────────────────────┼────────────────────┼────────────┤
  │Step 7│ 原始来源属于爆料 / 消息人士 / 社交爆料类            │ rumor              │ I7          │
  ├──────┼────────────────────────────────────────────────┼────────────────────┼────────────┤
  │Step 8│ 以上全部不成立                                    │ unverified         │ —           │
  └──────┴────────────────────────────────────────────────┴────────────────────┴────────────┘

  Step 4 置于 Step 5 之前的理由：存在互斥表述时，「各来源表述一致」这一前提
  已被破坏，必须先判 conflicting（R8.3 原文）。

■ 3.5 状态优先级与「可靠来源」的判定输入

  · 判定链的短路顺序**即优先级**，不得调换：
    official_confirmed > officially_denied > corrected > conflicting
    > multi_source_reported > single_source > rumor > unverified
  · Step 4 / Step 6 中的「可靠来源」需要可执行定义，建议采用：
      tier ∈ {T1, T2, T3} 视为可靠；**T4 一律不构成「可靠来源」**
      （T4 只能在 Step 7 作为 rumor 的原始来源出现）
    ※ 该定义依赖 source_registry.tier 落地，属本规范的**前置依赖**。
  · 排序中的并列打破（R5.2 Step 4）使用的状态序号与本优先级不同，
    以 components.js 的 NEWS_STATUS_RANK 为准（现状：official_confirmed 0 …
    corrected 7），本规范不改排序。

■ 3.6 输出契约

  判定器每次运行对每条候选输出：

    verification_status          8 态之一（必填）
    chain_steps_hit              命中的步骤（如 'Step 5'，必填）
    judged_by                    'rule_validated'（判定器直接得出时）
    status_changed_at            本次判定时间（必填）
    status_change_reason         变更依据说明，须与 chain_steps_hit 对应（必填）
    status_change_evidence_url   证据 URL，必须可回链（必填）
    status_history[]             追加一条 {from, to, at, reason, evidence_url}
                                 （首次入库 from = null；**禁止覆盖写**）

  兜底：任一必填输出缺失 → **不得入库**。

■ 3.7 重新判定原则（R8.2 / R8.4 / R8.5 的机器化）

  1. 任何状态变更都必须**从 Step 1 重跑完整判定链**，不得局部改字段。
  2. 人工**不得指定目标状态**；人工只有两项职责：
     a. 提供证据（官方链接、更正声明、撤稿记录等）
     b. 复核判定链输出是否符合证据事实
  3. 人工若认为判定有误，唯一合规做法是**补充或修正证据后重新触发判定**。
  4. conflicting 的解除（R8.4）：满足①官方就冲突要素表态 / ②一方更正或撤稿 /
     ③新增证据使一方表述失效 之一 → 落库 conflict_resolved_at 与
     conflict_resolved_by_evidence_url（均必填）→ **从 Step 1 重跑**。
     明确禁止 conflicting → single_source / multi_source_reported 的人工硬编码转换。
  5. corrected 不阻断后续演进：更正后内容若通过 R7.4 校验获得官方确认，
     仍按 Step 1 重判为 official_confirmed（R8.5）。
  6. officially_denied 后若出现新证据反转，同样从 Step 1 重跑（R8.6）。

■ 3.8 缺数据与异常处理（保守降级矩阵）

  原则：**任何数据缺失都导致降级，绝不导致升格。**

  ┌──────────────────────────────┬──────────────────────────────────────────┐
  │ 缺失情形                      │ 处理                                      │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ owner_group 缺失或「待核」      │ 该项不计入独立组；组数为 0 时 → unverified  │
  │ official_source_url 无法访问    │ Step 1 不成立，回落后续步骤                 │
  │ official_source_url 未命中      │ Step 1 / Step 2 均不成立 → 回落             │
  │ path（R7.4 Step 3）           │ 状态最高只能到 multi_source_reported（R7.4）│
  │ report_corrections 为空数组     │ Step 3 不成立，继续后续步骤                 │
  │ conflict_statements 为空数组    │ Step 4 不成立，继续后续步骤                 │
  │ reported_by 为空数组            │ 组数 0 → 落到 Step 7 或 Step 8              │
  │ original_source = 'unknown'    │ Step 7 不成立 → unverified                 │
  │ related_* 未命中真实 id         │ 丢弃该关联（不影响状态，仅影响关联节点数）    │
  └──────────────────────────────┴──────────────────────────────────────────┘

■ 3.9 判定器红线（10 条禁止）

  1. 不得接受外部传入的独立组数（必须自行按 owner_group 去重计算）。
  2. 不得因「来源权威 / tier 高」而破格升格（R7.4 明示）。
  3. 不得因多家网站转载而判为 multi_source_reported。
  4. 不得在 owner_group 未确认时假设来源独立性。
  5. 不得自行制造来源或补齐不存在的事实。
  6. 不得输出真实性 / 可信度百分比（R4.1）。
  7. 不得新增第 9 种状态（前端只有 8 个标签位）。
  8. 不得覆盖写 status_history。
  9. 不得在证据不足时以主观判断覆盖判定结果。
  10. 不得跳过判定链直接改 verification_status。

■ 3.10 与 AI 的边界（三层机制，R3.5）

  ┌────────┬──────────────────────────────────────┬──────────────────────────────┐
  │ 层      │ 可以做                                │ 不可以做                      │
  ├────────┼──────────────────────────────────────┼──────────────────────────────┤
  │ 第一层  │ 抽取 reported_by / original_source、  │ 自行认定 official_confirmed、 │
  │ AI 整理 │ 判断疑似转载与同集团、抽取关联实体、    │ 制造来源、把传闻写成事实、    │
  │        │ 生成纯文本摘要、提出**建议值**          │ 在 owner_group 未确认时假设   │
  │        │（写入管道字段 ai_suggested_status）    │ 独立性                       │
  ├────────┼──────────────────────────────────────┼──────────────────────────────┤
  │ 第二层  │ 判定链计算状态、R7.4 机器校验、        │ 被人工或 AI 覆盖输出          │
  │ 规则    │ 独立组去重计数                        │                              │
  ├────────┼──────────────────────────────────────┼──────────────────────────────┤
  │ 第三层  │ 提供证据、复核判定结果                 │ 指定目标状态、跳过判定链      │
  │ 人工    │                                      │                              │
  └────────┴──────────────────────────────────────┴──────────────────────────────┘

  必须人工介入的状态：official_confirmed / officially_denied / conflicting /
  任何 original_source 无法确定的 multi_source_reported / 任何涉及 supersedes 链的记录。

■ 4.3 需补充 / 修正项（按阻塞级别）

  【S 级 · 阻塞真实接入】

   N1 **文章级 URL 缺失（15/15）**
      现状：source_url / official_source_url 多为栏目页、feed 或站点首页，例如

        · `https://www.marvel.com/news`（栏目页）
        · `https://www.marvel.com/articles/live-events/`（目录页）
        · `https://thedirect.com/rss`（feed）
      影响：R7.4 的 Step 3（path 命中）**无法真正生效**；详情页「查看原文」
            点进去是栏目而非报道，用户体验与可追溯性都受损。
      要求：source_url 与 official_source_url **一律文章级**；
            feed / 栏目级入口只允许出现在 source_registry.feed_url。

   N2 **owner_group 待核（影响 4 条）**
      现状：The Direct（S002）与 ComicBook（S003）归属未证实，涉及 005 / 008 / 010 / 014。
      影响：这 4 条的独立组数被强制计 0 → 状态持续停在 unverified / corrected。
      要求：真实接入前必须确认归属并写入 source_registry（见 S-2 决策）。

   N3 **publish_time 与 first_seen_at 语义未分离**
      现状：publish_time 只到「日」；first_seen_at 采样值形如 `2026-09-22T01:10:00Z`，
            语义接近采集时间，但规范未定义。
      要求：明确
        · publish_time = **来源文章的发布时间**（到日即可，前端只展示日期）
        · first_seen_at = **系统首次见到该内容的时间**（ISO8601，用于排序回落与延迟统计）
      否则 R1.3 的「延迟以天计」无法测量，排序口径也不稳定。

  【A 级 · 重要，不阻塞】

   N4 **category 无枚举定义，且当前无任何渲染位**
      现有实际取值 movie / series / character；实测无渲染函数读取该字段。
      要求：先定枚举与用途（分类展示？筛选？统计？），否则真实数据会出现

   N5 **reported_by 内每篇报道缺独立发布时间**

   N7 **状态变更缺判定器版本号**
      现状：status_history 只有 at / reason / evidence_url，无法判断历史结论
            是按哪一版规则算出的。规则升级后不可复算。
      建议：引入 rule_version（管道字段 P12），可选同步进审计字段。→ 见 Q-4

      现状：related_movies 只能命中 MCU_CONTENT（已上映作品）；
            复联5 等未来作品在 MCU_UPCOMING 中 → 001 号用例的关联被丢弃。
      影响：真实资讯大量涉及未来未上映作品，**关联能力结构性受限**。
      说明：是否扩展关联目标域到 MCU_UPCOMING 会触及前端 relatedNodes 渲染逻辑
            （等于改 UI）→ 属跨角色决策，见 Q-3

  【B 级 · 优化】

   N9 **未激活字段的期望值未定义**
      conflict_resolved_at / conflict_resolved_by_evidence_url 全为 null
      （008 是唯一 conflicting 条目且尚未解除）。
      要求：明确这些字段在「无冲突 / 未解除」时的期望值为 null，避免真实接入后
            一部分写 ''、一部分写 null 造成口径分裂。

   N10 **测试夹具须在真实数据替换时移除**
      · `news-2026-09-17-015` 的 `related_movies: ['avengers-5']`（负向用例）
      · 上条的 `publish_time: null`（日期回落用例）
      要求：切换为真实数据前，按「归档确认报告」给出的 6 处依赖点精确迁移
            （news.js 1 处 + test-news-rules.cjs 4 处 + regression-news.cjs 2 处），
            **不得直接删除后不管**，否则会连带 4 条断言失败。

■ 4.4 ★ 本次体检新发现的规范内部口径差（两处，须先统一再施工）

  ① R7.3 的 allowed_paths 与测试断言的 path 判定不一致
     · 规范 R7.3：Marvel 官方 allowed_paths = `/news/*`（要求 /news/ 之后还有内容）
     · 测试 L182：`/\/news\/?$|\/articles\/(movies|tv-shows|live-events)\//`
       → 允许 URL 恰好是 `/news` 或 `/news/`（后面没有内容）
     实测数据：001 与 009 的 official_source_url 都是 `https://www.marvel.com/news`
     → 在规范原生 allowed_paths 下**不命中**，在测试断言下**通过**。
     后果：R7.4 Step 3 的「path 命中」校验在真实接入时会形同虚设
           （栏目页就能构成官方确认）。
     建议统一（二选一，见 Q-5）：
       a) allowed_paths 显式增列 `/news`（承认栏目页可作为确认入口），或
       b) 强制文章级路径（与 N1 一致），并把测试断言收紧为要求文章级 slug。

  ② 任务书输入「媒体数量」与 R3.1 的重定义冲突
     见 3.2 ※：判定基准必须是独立 owner_group 数，不是站点数。
     现有 003 号用例即是「3 家 → 计 1」的反例，若判定器按媒体数量取输入会算错。

■ 4.5 体检总结

  现有 15 条数据作为「**协议样本**」是合格的（字段齐、类型稳、枚举合规、
  派生一致、审计留痕完整），可直接作为 V1.0 协议的参考实现。
  但作为「**真实数据的前置准备**」尚缺三件：文章级 URL、owner_group 归属、
  双时间语义。三者均为 S 级，是真实接入的**硬前置**。

5. 五、下一阶段开发拆分建议（不写代码）
============================================================

■ 5.1 拆分原则

  1. 按**依赖顺序**拆，不按功能面拆；上游未闭环不得启动下游。
  2. 每个阶段必须**独立可验收**，且**一律不触碰 H5 生产代码**（仅 G8 替换数据文件）。
  3. 先做「可离线验证」的部分（判定器、校验器、去重），后做「有网络副作用」的部分（采集）。
  4. 每阶段的验收基线 = V2.2 的 78 + 55 + 11 条断言继续全绿。

■ 5.3 依赖关系与并行建议

  G0 ──┬─→ G2 ──┬─→ G3 ──┐
       │        │        │
       └─→ G1 ──┴─→ G4 ──┴─→ G5 ──→ G6 ──→ G8
                              └─→ G7 ──┘

  · **G1 可与 G0 并行**：判定器不依赖 owner_group 补齐——
    输入「待核」时按规则计 0 组，现有 15 条即可回归。
  · G3 与 G4 可并行（互不依赖）。
  · G8 是唯一触碰 H5 的阶段，且只替换数据文件，**不改任何接口与结构**。
  · 全链路**不触碰**：h5 页面、CSS、组件、app.js、其他 13 个 data 文件、
    shared/、wechat/、douyin/。

■ 5.4 每阶段的可独立验收性

  8 个阶段全部可独立验收，理由：每阶段的产出都是**可离线运行并输出确定性结果**的
  资产（判定器输出状态、registry 加载成功/失败、校验器输出轨迹、去重输出合并结果、
  采集器输出候选条目数、闸门输出阻断证明、health 输出状态迁移、G8 输出断言全绿）。
  不存在「必须等全部做完才能验收」的阶段。

■ 5.5 明确不在本拆分范围内的内容

  · 后台管理界面（审核后台 / 采集监控页）—— 属方案 ③ 的范畴，本次不拆。
  · 数据库与云端存储迁移 —— 维持静态通道（V3.0 方案第四节结论）。
  · 小程序端资讯展示 —— 需先做跨端决策（Q-6），且抖音端有类目风险。
  · 图片 / 视频素材接入 —— 现有卡片无图片区，触碰 UI，不在范围。

■ 客观事实（已实测，可复核）
  1. 现有 news.js 为 15 条、33 顶层字段，逐条齐备（实读 + 测试断言）
  2. 8 态全覆盖，independent_group_count 与运行时计算逐条一致

  4. related_* 无法命中 MCU_UPCOMING（001 号用例实测丢弃）
  5. category 无任何渲染函数读取（Grep components.js 命中 0）
  6. publish_time 与 first_seen_at 的语义在封版规范中**未被定义**（查 R1–R8 全文）
  7. R7.3 的 `/news/*` 与测试断言的 `/\/news\/?$/` 存在口径差（两侧逐行对照）

■ 工程判断（有理由，非事实）
  1. tier 分 4 级、crawl_policy 分 5 类：为便于机器判定而设计的粒度，可调整
  2. 「T4 不构成可靠来源」：为让 Step 4/6 的「可靠来源」可执行而提出的定义，
     需产品确认
  3. event_key 的构造方式（标题指纹 + 实体 + 时间窗）未做实验验证
  4. G0→G8 的拆分顺序基于依赖关系推导，未经过工期评估

■ 信息有限 / 未覆盖（不猜测）
  1. The Direct 与 ComicBook 的真实 owner_group —— 探活未证实，仍为「待核」
  2. Marvel Studios 是否存在独立于 marvel.com 的数据出口 —— 未证实
  3. 抖音小程序对 CloudBase 的支持度 —— 未核实
  4. 告警通道选型（邮件 / 企微 / 待办）—— 未定
  5. 版权授权边界 —— 属法律判断，本规范只做工程层控制，不出法律结论

■ 结论置信度

  **高（约 88%）**：
    · 字段规范 V1.0（1.3 / 1.4 / 1.5）—— 字段清单、类型、必填性、渲染位
      全部来自逐行读取与 Grep，可复核
    · 15 条数据体检（第四节）—— 逐条核对，含一处新发现的规范口径差
    · source_registry 字段结构（2.2 / 2.3）—— 由 R2/R6/R7 已有定义整理，
      无新增猜测

  **中（约 65%）**：
    · source_registry 种子数据的 tier 赋值（2.4）—— T1/T2 无争议，
      The Direct / ComicBook 的 T3 与 THR/EW 的 T2 属工程判断，需产品确认
    · 判定器规则（第三节）—— 主体是 R8.3 的机器化，但「可靠来源 = T1–T3」
      与 Step 4 的「同一要素」判定粒度需实际数据校准
    · 开发拆分（第五节）—— 依赖顺序可靠，工作量与工期未评估

  **低（约 30%）**：
    · event_key 的实际去重准确率 —— 未做实验，MCU 资讯标题模板化严重，
      纯标题指纹可能不足，必须实测后调参
