2. A 组条款：event-merger 与 supersedes 链的边界
============================================================

■ A0 事实基线（双方机制管辖范围不同，并行存在）

  ┌──────────────┬──────────────────────────────────┬──────────────────────────────────┐
  │ 维度          │ 事件归并（event-merger）           │ supersedes 链（R8.5）             │
  ├──────────────┼──────────────────────────────────┼──────────────────────────────────┤
  │ 所在层级      │ **管道层**                        │ 数据层 + 展示层                    │
  │ 处理对象      │ **多条报道**（来自不同来源）         │ **同一发布方的前后两个版本**         │
  │ 判定依据      │ event_key + 时间窗口              │ 发布方更正声明                     │
  │ 触发原因      │ 同一事件被多家报道                  │ 某条报道被其发布方更正              │
  │ 处理结果      │ 归并为一个「事件对象」（管道内部）     │ 保留两条数据 + 互链 + 展示合并为一条 │
  │ 是否改交付数据 │ **否**                            │ 是（新增一条 + 写入互链字段）        │
  │ 是否改状态    │ 否                                │ 否（状态由判定器重算）              │
  └──────────────┴──────────────────────────────────┴──────────────────────────────────┘

■ A1（定位与唯一用途）
  event-merger 是**管道层事件聚合机制**，**唯一允许**的用途两项：
    ① 减少候选条数（把同一事件的多条报道聚成一条候选）
    ② 组装事件级来源证据（`reported_by_union`）
  **不得**用于任何其他目的。

■ A2（不替代）
  event-merger **不替代** `supersedes_id` / `superseded_by_id` 机制。
  两套机制**并行存在、互不替代**，各自按 A0 的管辖范围工作。

■ A3（不修改交付数据）
  event-merger **不修改交付数据**：
    · 不写文件、不产出 `news.js`
    · 不修改任何条目的任何字段
    · 不决定任何条目是否进入交付数据
    判定依据（现状实现已符合）：`reports` 不裁剪、`records_deleted` 恒为 0、
    输出不含任何状态字段。

■ A4（优先级：以 supersedes 为准）
  当同一对条目**同时命中两套机制**时（现有 `news-2026-09-19-014` 与
  `news-2026-09-20-010` 即此情形）：**以 supersedes 链为准**。
  event-merger 只做归并标注，**不得**：
    · 据此删除任何一条
    · 把两条压成一条
    · 修改 `supersedes_id` / `superseded_by_id`
    · 以「已归并」为由阻止两条同时进入交付数据

■ A5（落库阶段红线 · 约束 G6）
  交付数据**仍须保留 supersedes 双条与互链**；
  展示层的「合并为一条」照旧由前端按 R8.5 处理，**语义不变**。
  事件归并结果**只用于**候选池组织与来源证据组装。

■ A6（可验证性要求）
  G6 引入落库逻辑时，**必须**至少包含以下断言：
    · 「supersedes 双条都在交付数据中」——给定互链对，两条都存在于交付数据
    · 「互链成对」——A.superseded_by_id = B.id 且 B.supersedes_id = A.id
  用以防止事件归并逻辑侵蚀 supersedes 链。

■ A7（输出隔离与职责分离，新增）
  · event-merger 的输出**不得**包含任何状态字段：
    `verification_status` / `judged_by` / `chain_steps_hit` /
    `status_change_reason` / `status_change_evidence_url` / `status_changed_at`
  · event-merger **不得**承担语义裁决：不判断「哪条更权威」「哪条更可信」
    「哪条应优先展示」，也不得据此排序或淘汰条目
  · event-merger 的输出**不得**写入 h5/ 目录

3. B 组条款：event_key 使用边界
============================================================

■ B1（不是数据库唯一主键）
  `event_key` **不是数据库唯一主键**。
  它是「事件签名指纹」——**同一签名可对应多个时间上分离的 occurrence**。
  实测证据（G4 用例 E2b）：标题与实体完全相同、时间相距 79 天的两条
  → 同一 event_key 产出 **2 个 hold 事件**。
  该行为是「不自动合并不同事件」的正确结果，同时证明 key 不具备唯一性。

■ B2（不作为报道实体 ID）
  `event_key` **不作为报道实体 ID**。
    · 报道实体 ID = 交付数据的 `id`（`news-YYYY-MM-DD-NNN`），标识**一条报道**，
      进交付数据、可进 URL 参数；
    · `event_key` 标识**一个事件签名**，**只在管道层使用**。
  两者**不可互换、不可互相替代**。

■ B3（禁止使用场合 · 四类）
  `event_key` **不得**用于：
    ① 写库 / 落文件的主键
    ② 对外 URL 查询参数
    ③ 任何用户可见的展示内容
    ④ 跨端（H5 / 微信 / 抖音）数据关联键

■ B4（主键方案 · 规定 B-ii，待 Z-3 最终确认）
  需要事件级稳定键时，**规定采用 B-ii（occurrence 序号）**：

  ```
  occurrence = 同 event_key 下，按 first_publish_time 升序，从 1 开始编号（整数）
  事件级稳定键 = event_key + '#' + occurrence
  ```

  **实现要点三条（必须先明确）**：
    ① 编号必须**在同一批次内全量排序后**生成 ——
       occurrence 依赖「同批处理里该 key 的全部条目」；
       若分两批处理会产生编号冲突。→ **要求单批次全量输入**。
    ② 新增字段只出现在 merger 的**输出**中，**不得写回输入数据**。
    ③ 需同步新增断言：同 key 下 occurrence 从 1 连续编号、无重复；
       且 `event_key + '#' + occurrence` 在输出内唯一。

  **备选 B-i（组合键）**：`event_key + '@' + first_publish_time`
    —— 若 Z-3 改选 B-i，本条款同步改为 B-i；因其不含新增字段，
       Candidate Schema 无需变更（schema 已含 `first_publish_time`）。
    —— B-i 的已知缺点：字符串较长；含时间语义，**易被误当作「事件时间」对外使用**。

  ★ **本轮只出规范、不落码**。occurrence 的实现列为 G5 前置建议项（见 B7）。

■ B5（既知口径限制 · 三条）
  · **不区分状态**（刻意设计）：依据 R8.8「状态不是永久事实标签」，
    事件身份必须跨状态稳定；副作用是「已确认」与「传闻」两条**不同报道**
    会共享同一 `event_key` → **不能**用 event_key 做报道层级筛选/统计。
  · **无实体时识别力弱**：`related_*` 为空时退化为文本指纹，
    「同事件不同标题」**不会被识别为同一事件**（宁可不合，不可误合）。
  · **时间窗口 3 天未校准**：G4 默认值，建议 G5 实测后回调。

■ B6（版本与兼容，新增）
  · `event_key` 前缀 `evt1-` 即**算法版本标识**。
  · 算法或词表发生**任何改变**（成分构成、词表增删、标准化步骤）→
    必须**升版本号**（`evt2-`…），**不得**在同版本内改变成分构成。
  · 升级版本时：旧 key 不作废但须标注所属版本；
    跨版本 key **不保证可比较**，不得混用做去重。

■ B7（可复现性与登记，新增）
  · `event_key` 必须可由 `explain()` 完整解释（暴露三成分 + 标准化标题 + 被移除项）。
  · 算法与词表每次变更，须同步更新回归断言（当前 95 条）并记录变更。
  · `occurrence` 的实现（B4）列为 **G5 前置建议项 G5-7**，
    在批准前**不得**在任何产出中出现该字段。

4. 违规判定与检查方式
============================================================

  以下情形一律判为**违规**，须在代码评审或回归中拦截：

  ┌────┬──────────────────────────────────────────────┬──────────────────────────────┐
  │ #  │ 违规情形                                      │ 检查方式                      │
  ├────┼──────────────────────────────────────────────┼──────────────────────────────┤
  │ 1  │ 交付数据中出现任一管道层字段                     │ 交付数据字段集比对（应恰为 33）│
  │ 2  │ 交付数据中出现 `event_key` / `occurrence`       │ 字段名扫描                    │
  │ 3  │ 交付数据中出现 `capture_id` / `candidate_id`    │ 字段名扫描                    │
  │ 4  │ supersedes 双条缺一，或互链不成对                │ 成对断言（A6）                │
  │ 5  │ event-merger 输出含状态字段                     │ 递归深扫（现有 95 条断言已含） │
  │ 6  │ event-merger 输出写入 h5/                       │ git status / 目录扫描         │
  │ 7  │ 以 event_key 作主键、URL 参数、展示内容或跨端键    │ 代码扫描 + 评审               │
  │ 8  │ 在同一 `evt1-` 版本内改变 key 成分构成            │ 版本号与算法变更记录比对        │
  │ 9  │ occurrence 在批准前出现在任何产出中              │ 字段名扫描                    │
  └────┴──────────────────────────────────────────────┴──────────────────────────────┘

  ※ 第 1 / 2 / 3 条自 G6（落库阶段）起生效；第 5–9 条**即日起生效**。

6. 附：未采纳的替代方案与理由
============================================================

  【方案 α】让事件归并直接产出交付条目（归并结果即交付数据）
    未采纳理由：与 R8.5 的「保留 supersedes 双条 + 互链」直接冲突（A4/A5），
    会导致链式引用丢失、可追溯性破坏（违反 R8.3 / R8.8 精神）。

  【方案 β】用 event_key 作为候选条目的文件主键
    未采纳理由：event_key 非唯一（B1 实测），作主键会冲突或误覆盖。
    改用 B4 的组合键。

  【方案 γ】把「哪条报道更权威」的裁决交给 event-merger
    未采纳理由：越权。权威性判断属 G1 判定器（依据 tier / owner_group）与
    人工审核层；event-merger 只做机械聚合（A7）。
