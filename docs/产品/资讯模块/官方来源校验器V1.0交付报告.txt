1. 一、校验器设计
============================================================

■ 1.1 定位

  R7.4「official_source 判定六步校验」中**可在离线环境完成的那一部分**，
  实现为一个**纯函数验证层**：给定一条官方来源声明，输出它是否成立，以及
  六项检查各自的通过情况。

  ┌────────────┬──────────────────────────────────────────────────────────┐
  │ 属性        │ 实现方式                                                  │
  ├────────────┼──────────────────────────────────────────────────────────┤
  │ 纯函数      │ 无状态、无时间依赖；同输入必得同输出                          │
  │ 零网络      │ 不做任何 HTTP 请求、不抓取任何页面                           │
  │ 零副作用    │ 不写文件、不改全局                                          │
  │ 数据外部化  │ 域名事实全部取自 source-registry.json，**代码中零域名字面量**  │
  │ 策略单一源  │ path 策略复用 G1 的 PATH_POLICY，**不另建第二套**             │
  └────────────┴──────────────────────────────────────────────────────────┘

■ 1.2 输入

  ```
  {
    source_url        待校验的官方来源 URL（必填）
    source_name       来源名称（用于与登记表条目复核，防伪造条目）
    registry_entry    登记表条目（须来自 source-registry.json）
    claimed_event_id  本条声称对应的事件 id
    official_confirm  { reviewed: boolean, event_id?: string }
  }
  ```

■ 1.3 输出契约（**恰为 4 个顶层键**，已由测试断言）

  ```
  {
    valid:        boolean,   // 六项全部通过才为 true
    checks:       object,    // 6 个检查项，每项 { pass: boolean, detail: string }
    reason:       string,    // 结论说明
    rule_version: "V1.0"
  }
  ```

  ★ 契约取舍说明：任务书写 `checks:[url_scheme, domain_allowed, ...]`。
  该写法在 JS 语境下通常表示「checks 是含这些键的映射」。
  本实现取 **checks 为对象**（键即六项检查名，值含 pass 与 detail），
  理由是：① 调用方需要按名取用某一项；② detail 需要承载证据；
  ③ 顶层键严格保持 4 个、不额外增加字段。六项顺序由导出常量
  `CHECK_ORDER` 显式给出，测试已断言键位顺序与任务书一致。

  六项检查的语义：

  ┌──────────────────┬──────────────────────────────────────────────────────────┐
  │ 检查项            │ 判据                                                      │
  ├──────────────────┼──────────────────────────────────────────────────────────┤
  │ url_scheme       │ URL 非空 且 协议为 http / https                            │
  │ domain_allowed   │ host 命中 registry_entry.allowed_domains                  │
  │ path_allowed     │ path 命中 allowed_paths、且不落在 excluded_paths            │
  │                  │（策略 legacy / article-level，默认 legacy）                 │
  │ domain_blacklist │ host **不在** non_official_domains（命中即失败）             │
  │ registry_match   │ 官方来源资格：official_or_media = official **且**           │
  │                  │ allowed_domains 非空；另加条目真实性复核                     │
  │                  │（source_name / registry_id 与登记表一致，且在派生官方清单内）│
  │ review_required  │ 人工复核要求是否已满足：official_confirm.reviewed = true，   │
  │                  │ 且 claimed_event_id 与 official_confirm.event_id 一致（若成对提供）│
  └──────────────────┴──────────────────────────────────────────────────────────┘

■ 1.4 ★ 级联语义：六项全部计算，**不做短路**

  校验器一次性算完六项，`valid` 要求六项全通过。
  因此当 URL 本身不可用（空 / 非 http / 非法格式）时，依赖它的
  `domain_allowed` / `path_allowed` / `domain_blacklist` 会**一并失败**。

  · 这是**刻意设计**：让调用方与审计一次看到全貌，而不是被第一个失败项遮住。
  · `reason` 只报「按固定顺序最早失败的那一项」，其余失败项由 `checks` 全量呈现。
  · 首轮测试曾因此出现 5 项 FAIL —— 是**夹具期望清单写漏了级联项**，非实现缺陷；
    已修正夹具为「完整失败清单」，并在夹具内写明该语义（详见 3.4）。

■ 1.5 三项关键设计决策

  【决策 1】域名零硬编码，全部来自登记表
    · 校验器源码中**不含任何域名样式字面量** —— 由测试对源码做正则扫描自证（0 命中）。
    · allowed_domains / allowed_paths / excluded_paths / non_official_domains
      四类事实全部经 `news-registry.cjs` 读取 `source-registry.json`。

  【决策 2】复用 G1 的原语与策略常量，不复制逻辑
    · URL 解析复用 `judge.parseUrl`；path 判定复用 `judge.pathAllowed`；
      path 策略复用 `rules.PATH_POLICY.mode`。
    · 这样「legacy / article-level 开关」在全项目只有一个权威定义。
    · 为防止两者将来漂移，测试专门做了**交叉一致性断言**：
      8 组 URL × 策略下，本校验器的前五项结论必须与 G1 `checkOfficialUrl` 完全一致。
      ※ 这条断言的价值：若将来有人只改了一边，测试会立刻失败。

  【决策 3】黑名单是**独立守卫**，不是 domain_allowed 的副产物
    · 现实的失败顺序是「host 未命中 allowed_domains」先失败，
      黑名单往往被掩盖。为单独验证黑名单本身有效，
      测试用例 C5 使用**合成条目**：故意把 disneyplus.com 写进 allowed_domains，
      使 domain_allowed 通过，从而把 domain_blacklist 隔离出来单独验证。
    · 这正是「即使有人把黑名单域名误登记进 allowed_domains，也拦得住」这一守卫的验证方式。

■ 1.6 本层**未覆盖**的 R7.4 步骤（必须知悉）

  ┌──────┬────────────────────────────┬──────────────────────────────────────────┐
  │ 步骤  │ 内容                        │ 未覆盖原因 / 现由谁承载                    │
  ├──────┼────────────────────────────┼──────────────────────────────────────────┤
