## 5. 新门禁与旧链路关系

- **当前正式发布入口**：`news-append-writer.cjs`（其文件头自述“生产闭环的唯一发布动作”）。行为：缺 `--manifest` → 退出码 2；缺 `--operator` → 退出码 2；写入前调用 `pub.loadApprovedIds(manifest, allowlist)`，不通过则 `APPROVAL_REQUIRED`（退出码 1）；任一预览 id 不在批准集合则整批拒绝（`APPROVAL_ID_MISSING`）。另做 SHA/`--expect-sha`、双备份、vm 校验、幂等。
- **备选入口**：`publish-news.cjs --publish`（P2-A），同样要求 `--manifest`；源=`build h5/data/news.js`、目标=`live h5/data/news.js`（同一文件，经符号链接），本质是 copy-onto-self，与 `news-append-writer` 冗余；真正落盘者是 `news-append-writer`。
- **--manifest / 白名单 / 证据要求**：manifest 必填，需 `reviewer_trust='allowlist'`、逐条 `reviewer`（须在 `trusted-reviewers.json` 内）/ `reviewed_at(ISO)` / `source`；纯 id 列表或缺失信任声明一律拒绝。
- **历史发布是否绕过新门禁**：**是**。10-12~14 发布用的是方案 A 之前（无 `--manifest` 门禁）的 `news-append-writer`；且 `trusted-reviewers.json` 至今缺失。新门禁在彼时不存在，故历史发布天然“绕过”它。
- **历史运行记录能否证明符合现行门禁**：**不能**。现行门禁要求 manifest + 白名单 + 逐条证据，历史记录既无 manifest、白名单也缺失，且审核账本格式 ≠ approved-manifest 格式。不得以历史发布成功推断其符合新门禁。
