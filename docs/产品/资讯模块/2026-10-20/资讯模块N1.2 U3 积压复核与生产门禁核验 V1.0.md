## 4. 白名单、manifest 与历史审核账本的证据映射

### 4.1 trusted-reviewers.json（白名单）
- 预期路径：`pipeline/review/trusted-reviewers.json`（见 `publish-news.cjs` L24 `DEFAULT_ALLOWLIST`、L28-39 `loadPublishAllowlist`）。
- 格式：数组，或 `{reviewers:[...]}` 或 `{entries:[...]}`；按 trim 后字符串**精确成员匹配**（`isTrustedReviewerAtPublish`，L40-44）。
- 当前状态：**文件不存在**（实测 `TRUSTED_EXISTS=false`）。`loadPublishAllowlist` 在缺失时返回 `{set:空, missing:true}`，`isTrustedReviewerAtPublish` 对任何审核人返回 **false**。
- 其他正式授权来源：**未发现**（唯一白名单来源即此文件）。

### 4.2 approved-manifest.json（批准清单）
- 真实 schema（`publish-news.cjs` L128-170 `loadApprovedIds`）：
  - **必须**声明 `reviewer_trust: 'allowlist'`，否则整体拒绝（L138-140）。
  - 必须提供 `entries[]`（数组或 `{entries}` 或 `{approved_ids}`）；**纯 id 列表 `approved_ids` 因无 per-entry 证据被拒**（L147-150）。
  - 每条须含：`reviewer`（非空 **且**在白名单内）、`reviewed_at`（ISO，经 `ISOT_RE` 校验）、`source`（非空）；任一缺失则整批拒绝（L158-167）。
- 形式兼容性：数组 / `{entries:[...]}` / `{approved_ids:[...]}`（后者被拒）。

### 4.3 「产品负责人」身份映射
- 历史账本 9 条 `operator` 均为 `"产品负责人"`。
- 但 `trusted-reviewers.json` **缺失** → 无法将"产品负责人"与系统可识别的授权身份建立可靠映射；当前任何审核人在门禁侧均判为"不可信"。
- **结论**：历史账本中的"产品负责人"**不能**被现行门禁自动认定为合法授权身份，须由负责人显式将其实名/身份写入 `trusted-reviewers.json` 后方可生效。

### 4.4 历史审核账本对候选 ID / 审核人 / 时间 / 来源 / 理由的追溯性
- 可追溯字段（存在原始证据）：`candidate_id`、`action=approve`、`operator=产品负责人`、`created_at=2026-10-16T02:16:43Z`。
- **缺失/歧义字段**：`reason=""`（空）、`source=""`（空）。即审核决定记录本身**不带来源与理由**，来源 URL 仅存在于候选文件 `20261016.json`，不在审核记录内。

**结论：当前门禁不具备安全执行条件。** 代码与单测层面门禁逻辑完备，但授权证据层（白名单 + 合格 manifest）缺失，任何发布尝试都会被门禁**拒绝（fail-closed）**——即门禁本身安全，但"可放行发布"的前提（白名单与 manifest）尚未齐备，须由负责人先行建立。
