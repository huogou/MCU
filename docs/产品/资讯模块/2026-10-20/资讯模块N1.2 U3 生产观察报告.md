→ 通过条目均高度 MCU 相关，可信度分级使用恰当（官方公告类正确标注 `official_confirmed`）。

### 2.4 质量风险点
1. **单源为主**：通过条目 `verification_status` 多为 `single_source`，缺乏交叉验证（与历史遗留项「credibility 未传 sourceInfo 恒 low」一致）。建议后续补齐来源交叉校验。
2. **剧透/争议需人工**：AI 无法可靠判定「剧透/争议性表达」，此闸门必须保留人工。
3. **噪声比高**：57% 候选为非 MCU，提示采集源 S006 噪声偏大，可考虑源级预筛（见第 4 节）。

## 3. 人工成本

### 3.1 自动化 vs 人工分布
| 环节 | 自动化程度 | 人工介入 |
|---|---|---|
| 采集（cron 08:00） | 全自动 | 0 |
| AI 生成（桥接） | 全自动 | 0 |
| 发布写入 + SHA + 双备份 | 全自动 | 0 |
| **G6 审核** | 人工 | **必须**（54 条候选） |
| **delivery 触发** | 手动 | **必须**（3 次发布 + 1 次官方追加） |

### 3.2 人工耗时与步数估算
- **审核**：周期内人工审核 **54 条**候选（4 批次）。按每条读题+判断 ~1–2 分钟估算，总审核人工约 **80 分钟**（分散在 4 个工作日）。
- **发布**：3 次 pipeline 发布 + 1 次官方条目追加，每次需人工触发 `news-append-writer` / delivery 流程，约数分钟/次。
- **记录生成**：`daily-observation.cjs` 已脚本化（cron 调用），但「读记录、做判断」仍需人。

### 3.3 人工断点（最关键的待办）
> **10-16 审核通过 9 条，但从未执行 delivery** → 截至 10-20，存在 **9 条已审核通过却未发布的积压条目**（如「漫威官宣第九位权游演员加盟MCU」「布丽·拉尔森被排除在末日之外」「X战警欧米伽级变种人」等）。
> 人工成本的最大损耗不在「审核」本身，而在「审核后→发布」的**手动交付断点**：审核完成即停滞，需有人专门触发发布。

## 4. 自动化程度建议

### 4.1 可进一步自动化（保留/增强）
| 建议 | 预期收益 | 风险 |
|---|---|---|
| **修复 daily-observation 快照时机**：改为在审核窗口之后（如 UTC 04:00）运行，或改为「周期 diff 报告」而非点快照 | 消除当日审核/发布系统性漏报（见第 5 节） | 低 |
| **候选预筛分类器**（基于标题/源的 MCU 范围初筛规则） | 当前 57% 驳回多为明显非 MCU，预筛可削减 50%+ 人工审核量，让人聚焦「质量/剧透/争议」判断 | 低（仅辅助，不替代 G6） |
| **审核通过 → 自动生成 delivery-preview 并置为「待发布队列」** | 减少手动步骤，避免 10-16 式积压 | 低 |
| API 耗时自动记录 | 补全 observability 缺口 | 低 |

### 4.2 必须保留人工闸门
| 闸门 | 理由 |
|---|---|
| **G6 范围/质量/剧透/争议判断** | AI 不可靠：已有 1 条「剧透+争议」需二次确认案例；非 MCU 边界（如 MCU 联动 DC 的擦边球）需人判 |
| **最终 delivery 发布** | U3 明确不开 delivery cron；涉及线上 `news.js` 三端即时生效，须人工一键确认 |

> 推荐维持「**AI 预筛 + 人工审核 + 人工确认发布**」的两段式结构。

### 4.3 流程改进待办（按优先级）
1. **【紧急】清理 10-16 积压**：对 9 条已审核通过条目执行一次人工 delivery 决策（发布或延期），解除线上内容滞后。
2. **修正观察工具时机**：daily-observation 快照改到审核窗口后，或改为 diff 报告。
3. **补全来源可信度**：解决 `credibility/sourceInfo` 遗留项，提升单源条目的质量分级。
4. **文档一致性**：`runtime/README.md` 索引与实际漂移（见第 5 节），建议改为由权威源自动生成索引。

## 5. 工具与文档缺陷发现（Observability）

> 本节揭示本地 `runtime/*.md` 为何不能直接采信——属观察机制自身缺陷，非业务故障。

1. **daily-observation 点快照时机缺陷（系统性）**
   - 该工具在每日 00:00 UTC 采集后不久即生成记录，而**人工审核窗口在 ~02:xx UTC**。
   - 结果：10-14 / 10-15 / 10-16 / 10-19 的记录**系统性漏报当日审核与发布**；10-12 / 10-13 因审核早于快照而「侥幸命中」。
   - 例：10-14 本地记录写「候选/审核/发布均为 0」，但服务器 `run-20261014-002` 显示当日审核 20、发布 7。

2. **真实审核账本位置隐蔽**
   - `pipeline/candidates/review-history.json` 才是真实账本；`pipeline/review/review-history.json` 是 09-23 模拟器冻结件（12 条 simulated），二者不互通。

3. **10-17 / 10-18 记录缺失**
   - 本地 `runtime/` 无这两日记录，README 标「待生成」；但服务器 `run-history` 显示两日均正常采集 130 条。记录未生成 ≠ 采集失败。

4. **API 耗时未被自动记录**
   - 10-13 / 10-14 记录标「待人工补充」；仅 10-12 有实测（10.7–13.6s）。

5. **README 索引自身失真**
   - 索引行将 10-14 标为「0」、10-17/18 标「待生成」，与实际不符（见上）。
