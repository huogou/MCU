■ 2.1 G5-1 / G5-2 说明（最重要的两条）

  · 事实：S002（The Direct）与 S003（ComicBook）是**主力发现器**
    （出口分别 `/rss` 与 `/category/marvel/feed/`，MCU 命中约 52% / 90%），
    但二者 owner_group 至今「待核」。
  · 为何是硬门禁：owner_group 为「待核」→ 判定器**不计入独立证据组**
    → 即便二者报道同一事件，也只能落 `unverified`。
    **采集一旦开始而此缺口未关，逐条数据的过程正确、结论系统性偏悲观**，
    人工审核成本上升，且会污染后续所有统计。
  · 关闭动作：确认归属 → 更新 `registry/source-registry.json` 的
    `owner_group` 字段（并把 `note` 中的「★ owner_group 待核（E-2）」移除）
    → 重跑 `test-registry-validate.cjs`（38 条须保持全绿）。
  · ★ **连带影响（须批准）**：关闭后，现有 4 条数据的状态会变化
    （005 / 008 / 010 / 014 的独立证据组计数由 0 变为 ≥1 → 状态可能升级）。
    **属数据变更**。建议二选一：
      (a) 与 G8 的 URL 修正合并处理（推迟）
      (b) 在 G5 前单独批准一次数据更新（立刻）
    开发侧倾向 **(a)**：理由是与 G8 的数据整改属于同一批动作，
    且可避免两次改动同一份数据。**但若选 (a)，则 G5 开工时该缺口仍未关，
    与 G5-1/G5-2 的门禁性质冲突** —— 因此需要明确：
      要么「先关归属、暂不改数据」（推荐：先改登记表，数据留待 G8）
      要么「推迟归属确认」（不建议：会让 G5 全程产出偏悲观的结论）
  · ★ **本清单推荐**：**G5 前只更新登记表（改 owner_group），
    现有 4 条数据的整改留到 G8**。这样门禁可满足，且不产生两次数据改动。
    → 请负责人在 Z-5 中确认此拆法。

■ 2.2 G5-6 说明（本轮新增的门禁）

  · 事实：G0 冻结件登记「管道字段 12 个，冻结为『不进交付物』」，
    而 Candidate Schema 需要在管道层新增 8 个字段（capture_id / candidate_id /
    url_level / title_raw / published_at_raw / capture_refs / gate_status / occurrence）。
  · 两种读法：
    **读法 a（封闭清单）**：管道层只能有 12 个 → Candidate Schema 须裁剪 8 个字段，
                            代价见《Candidate Schema V1.0》1.3 节对照表
    **读法 b（禁止清单）**：12 个是「不得进入交付物」的清单，管道层可新增并登记
                            → 管道层字段扩为 20 个
  · 开发侧倾向 **读法 b**，理由：真正的硬约束是「33 字段交付物不变」；
    按读法 a 将丧失采集证据追溯（capture_id）、Q-5 合规状态暴露（url_level）、
    原始标题留痕（title_raw）与**审核闸门的机器可读状态（gate_status）**。
  · **裁定为 a 或 b 均不影响 33 字段交付物与 8 态体系**。

7. 不满足硬门禁时的处理
============================================================

  · **不得开工 G5**，不得「先写采集、后补归属」——
    理由：owner_group 未确认会让采集产出全链路带上系统性偏差，

  · 若负责人决定在归属未确认的情况下先开工，须**显式书面确认**，
    并接受：①S002 / S003 的条目全部不计入独立证据组；
    ②由此产生的状态结论**不得**作为长期统计基线。
  · 已完成的前置件（A/B 条款、Candidate Schema、judged_by 草案）
    **不因门禁未开而失效**，可先归档。
