============================================================
R1｜运行架构
============================================================

■ R1.1 最终选型

采用 C：AI 半自动静态产出。
A（独立采集服务）与 B（CloudBase 云函数）本期不予采用。


■ R1.2 选型理由

1) 为什么选择 C
   a. 数据纪律：C 是唯一不破坏「h5/data/*.js 单一可信源 + file:// 可直接打开」的方案。
   b. 量级匹配：实测各来源 MCU 相关日产出很低（见 R2.5），C 的处理能力有充足冗余。
   c. 风险可控：每个环节都可人工拦截，符合「宁可少展示一条，也不把未验证消息当事实」。
   d. 与现有部署形态一致：项目为 Nginx 静态托管，无后端运维负担。

2) 为什么不选 A
   需要 Node 常驻进程 + 数据库 + 后台管理页，把项目从「纯静态站」变成「有后端的站」；
   运维责任、故障面、安全面同时上升，与现有部署条件与项目治理铁律不匹配。

3) 为什么不选 B
   虽然可复用现有 CloudBase 环境（mcu-d6gw0brqoa9521b58），但存在两处硬冲突：
   a. H5 取数需改为异步 fetch，直接破坏「file:// 可本地直接打开」这条现有特性；
   b. 数据源从「仓库里的 js 文件」变成「云上数据库」，与「数据单一可信源、可被 git 追溯」的纪律冲突。
   保留 B 作为后续升级目标（见 R1.2-9）。

4) 对现有 H5 架构的影响（穷举）
   新增：
     - h5/data/news.js（与 content.js 同构，挂 window.MCU_NEWS）
     - h5/news.html（资讯列表页，第二阶段）
     - h5/news-detail.html（详情页，第二阶段，可延后）
   修改：
     - index.html 增加 1 行 <script src="data/news.js">（加载顺序：content.js 之后、app.js 之前）
   不改动：
     - 任何既有数据文件（movies/series/special/short/relations/routes/upcoming/community 等）
     - 任何既有页面结构与样式基线
     - 不新增任何运行时依赖、不新增网络请求

5) 数据如何进入 h5/data/news.js
   唯一入口是「人工提交 git」。
   - 产线在仓库之外运行，产出候选文件（候选 news.js）
   - 人工复核通过后，覆盖 h5/data/news.js 并提交
   - H5 运行时只读静态 js，不发任何请求
   由此保证：线上内容 100% 经过人工放行，且每次变更都有 git 记录可回溯。

6) 谁负责抓取
   由 AI 管线执行抓取与信息提取，不部署常驻爬虫。
   - 有真实 feed 的来源：轮询 feed（R2 已逐个实测）
   - Marvel 官方：无 feed，改为解析 /news 列表页 HTML（实测有效，见 R2.3-1）
   - 抓取节奏：每日 1 次（见 R1.2-7）

7) 谁负责审核
   三层机制（详见 R3.5）：
   第一层 AI 出建议值 → 第二层 规则硬校验 → 第三层 项目负责人人工复核
   必须人工确认的状态：official_confirmed、officially_denied、conflicting，
   以及任何 multi_source_reported 但 original_source 无法确定者。

8) 更新频率
   建议每日 1 次，建议时点为北京时间 09:00 前后；必要时由负责人手工触发。
   ★ 必须写明：这不是实时资讯系统。从事件发生到 H5 可见，延迟以「天」为单位。

9) 是否需要后端
   不需要。无服务器、无云函数、无数据库、无定时服务。

10) 是否保持 file:// 可运行
    保持。此条列为硬验收项，任何方案变更不得破坏。

11) 规模扩大后如何升级
    升级触发条件（满足任一条即启动评估）：
      a. 单次人工复核耗时稳定超过 30 分钟；
      b. 待审候选稳定超过 40 条/日；
      c. 出现「日级延迟不可接受」的产品需求（如首映实时追踪）。
    升级路径：C → B（数据通道改为 fetch 读取云数据库）→ A（独立采集服务 + 后台监控页）。
    为降低升级成本，news.js 的字段结构从第一版起即按最终结构设计：
    升级时只替换数据通道，不更换数据结构，H5 展示层零改动。


■ R1.3 更新延迟与人工复核成本（必须明确，不得回避）

更新延迟：
  每日一跑 → 平均延迟约 12 小时，最坏延迟约 24 小时。
  任何文案不得暗示实时性，不得使用「刚刚」「最新更新于 N 分钟前」类表述。

人工复核成本估算（需以连续 7 天实测校准）：
  每日候选条目：5–20 条（依据 R2.5 实测推算）
  单条复核耗时：状态判定 30–60 秒 + 关联 id 校对 20–30 秒 + 文案检查约 10 秒 ≈ 1–2 分钟
  合计：约 10–30 分钟/日
  ★ 前置依赖：必须启用分类 feed。若仍用主 feed，候选噪音上升 3–5 倍（实测 ComicBook 主 feed
    MCU 命中仅 9/52，分类 feed 为 47/52），人工复核成本同比例上升。

■ R2.1 探活方法与基准
  时间：2026-09-22 上午 GMT+8
  方法：对每个候选出口发起真实 HTTP 请求，记录状态码、Content-Type、字节数、

  声明：以下结论具有「当日快照」性质，来源随时可能变化。建议产线每次运行前先做健康度复核；
        任一来源连续 3 次抓取失败即自动降级为「暂停」并提示人工确认。


■ R2.2 来源登记表字段定义（按 §五 建立，此表为必填）

  source_name                来源名称
  source_type                官方 / 权威媒体 / MCU 垂直媒体 / 公告平台
  official_or_media          official | media
  owner_group                所属集团（必填；无法确认时填 unknown，禁止猜测）
  official_domain            官方域名（用于 R3.5 白名单校验）
  feed_type                  rss | atom | html-parse | none
  feed_url                   实际可用的抓取出口（必须是实测通过的 URL）
  structured_output_available  是 / 否（RSS/Atom/JSON-LD 之一即为是）
  crawl_available            robots.txt 是否允许（允许 / 具名封禁 / 注释反对）
  stability                  高 / 中 / 低
  source_quality             高 / 中 / 低（权威度）
  notes                      备注（陷阱、解析细节、待核项）

【1】Marvel 官方（marvel.com）
  owner_group        : Disney / Marvel
  source_type        : 官方
  feed_type          : html-parse（无可用 feed）
  feed_url           : https://www.marvel.com/news
  structured_output  : 部分（页面含 1 处 application/ld+json）

■ R2.4 合规待决项（须项目负责人拍板；本规范不下结论，只列事实与双方论据）

涉及来源：THR【6】、EW【8】、Collider【11】

客观事实：
  a. THR：robots.txt 对具名 AI 爬虫（含 GPTBot / ClaudeBot / CCBot / ChatGPT /
     DeepSeek / Google-Extended / Meta-ExternalAgent 等）使用真正的 `Disallow: /` 指令，
     机器可读、语义明确。
  b. EW（People Inc.）与 Collider（Valnet）：在 robots.txt 中以**注释**形式声明禁止自动抓取
     与 AI 使用（含 RAG），但其 Disallow 指令列表中**未封禁**文章路径与 feed 路径。
     注释是使用条款立场的表达，不具备 robots 协议的机器强制力。
  c. 三站的 `User-agent: *` 通配规则均**未封禁**文章与 feed 路径。

支持「可继续使用」的论据：
  · 本方案只保存标题、来源名、原文 URL、发布时间与自撰摘要，不复制全文（符合原 §20 版权策略），
    详情页回链原文，实际效果是导流而非替代；
  · 事实性信息（谁出演、何时上映）本身通常不受版权保护；
  · 通配规则未禁止，注释不构成技术拒绝。

支持「应移除或降级为人工」的论据：
  · People Inc. 与 Valnet 的声明文本明确点名 AI 与 RAG，而我们的产线正是 AI + RAG 形态，
    落入其明确排除的行为描述；
  · THR 的具名黑名单包含同类 AI UA，继续抓取在事实层面违背其明确声明；
  · 违规后果是域名级封禁乃至法务交涉，而收益仅为「多 1–3 个信噪比很低的来源」
    （实测 MCU 命中 0–1/10~12），收益/风险比明显不利。

建议（供拍板，非结论）：
  第一阶段将 THR、EW、Collider 移出自动抓取清单。
  如需保留其权威性，改为**人工录入通道**：人工阅读 → 手工新增一条 news 条目 →
  official_source 留空、状态最高只能到 media 级。
  待负责人对合规边界给出明确意见后再调整。

■ R3.1 判定输入字段（新增 / 重定义）

新增字段：
  owner_group                   来源所属集团（来源登记表必填项）
  original_source               原始消息源名称（无法判断时填 unknown，禁止猜测）
  original_source_url           原始消息源 URL
  reported_by                   报道方数组（每项含 source_name 与 source_url）
  independent_group_count       派生字段：reported_by 去重 owner_group 后的数量
  official_source               官方来源名称
  official_source_url           官方来源 URL
  official_domain_whitelisted   布尔：URL 是否命中官方域名白名单
  status_changed_at             最近一次状态变更时间
  status_change_reason          状态变更依据说明
  status_change_evidence_url    状态变更证据 URL（必须可回链）
  supersedes_id / superseded_by_id   更正与辟谣的链式引用
  pinned / pinned_until / pinned_order / pinned_reason   置顶控制字段（见 R5）

重定义：
  ★ multi_source_reported 的判定**不再基于「报道网站数量」**，
    改为基于 `independent_group_count`。

核心原则（写入规范正文，不可协商）：
  1. 同一 owner_group 下的多个媒体，无论多少家，一律只计 1 个独立证据。
  2. 无法确认 owner_group 或无法确认 original_source 时，
     **不允许 AI 自行假设其独立性**，一律降级为 single_source 或 unverified。

真实案例（本次探活即捕获，可直接作为验收样例）：
  2026-09-21/22，「Daredevil: Born Again 将在第三季完结」一条消息同时出现在
  Variety、Deadline、THR 三家。THR 标注 Exclusive。
  按原规则（站点计数）→ 会被判为 multi_source_reported（3 家）。
  按本修订规则 → 三家同属 Penske Media Corporation，independent_group_count = 1，
  只能判为 single_source。

  ⚠ 待核（置信度中/低，未采信）：ComicBook 归属（疑 Paramount 旗下）、
    The Direct 归属。二者均为「未确认」状态，请策划核实后补入登记表。

■ R3.3 完整状态转换规则

【升级路径】（依据增强时）

  unverified            → single_source         条件：出现 1 个可靠媒体来源
  unverified            → rumor                条件：确认原始来源为爆料类
  single_source         → multi_source_reported 条件：independent_group_count ≥ 2
                                                且各来源信息一致
  single_source         → official_confirmed   条件：找到官方来源且通过白名单校验 + 人工复核
  rumor                 → multi_source_reported 条件：爆料被多家**不同 owner_group**的
                                                可靠媒体独立证实
  rumor                 → official_confirmed   条件：官方确认
  multi_source_reported → official_confirmed   条件：官方确认
  conflicting           → 任一非冲突状态      条件：冲突被消除（官方表态或一方更正）

【降级路径】（依据减弱或反转时）

  official_confirmed    → officially_denied    条件：官方明确否认（官方信息此后仍可能变更）
  official_confirmed    → corrected            条件：官方自身发布更正
  official_confirmed    → conflicting          条件：官方与其他官方来源表述互斥（如不同地区
                                                官方口径不一致）
  multi_source_reported → single_source        条件：复核发现 reported_by 实际同属 1 个
                                                owner_group（伪多源被识别）
  multi_source_reported → rumor                条件：追溯发现原始来源为同一爆料人
  multi_source_reported → corrected            条件：主要来源发布更正
  single_source         → corrected            条件：该来源发布更正
  single_source         → rumor                条件：追溯发现原始来源为爆料类
  任一状态              → conflicting          条件：出现互斥的可靠来源
  任一状态              → unverified           条件：来源被删除/撤稿且无其他依据

【六个必须回答的问题】

  1) 什么情况升级？
     见上述升级路径。统一门槛：新增独立 owner_group 或出现可回链的官方来源。

  2) 什么情况降级？
     见上述降级路径。统一门槛：独立证据减少、来源更正、或出现官方否认 / 互斥表述。
     ★ 特别注意「伪多源」降级：复核发现多家媒体同属 1 个 owner_group 时必须降级。

  3) 官方确认后是否仍可能变更？
     **会。**官方信息会改档、改口、更正。因此 official_confirmed 的语义是
     「截至当前已获得官方层级的确认」，而不是「此事永远不会变」。
     该状态可转往 officially_denied、corrected 或 conflicting。

  4) 官方否认后如何处理旧新闻？
     **保留，不删除。**状态改为 officially_denied，保留原有 reported_by 与历史状态记录；
     卡片与详情页显著展示「官方已否认」。旧新闻不得静默消失，否则用户会失去判断依据。
     默认不进首页列表（见 R5），但保留全文可访问。

  5) 媒体发布更正后如何处理旧数据？
     保留原记录，新增更正后记录，二者以 supersedes_id / superseded_by_id 互链；
     H5 以最新记录为准，并在卡片与详情页显示「该报道已被来源更正」及更正方向。
     corrected 状态最高只能到 media 级，**不得因更正而升级为 official_confirmed**。

  6) corrected 是否保留原始报道？
     **保留**。理由：用户需要看到「原来怎么说、后来改成什么」，这正是可追溯性的核心价值。
     但两条记录**不作为两个独立条目在列表中重复展示**，须合并到同一事件下。

  7) 状态变化是否记录时间和依据？
     **必须记录，缺一不可。**三个字段强制填写：
       status_changed_at（时间）
       status_change_reason（依据说明）
       status_change_evidence_url（证据 URL，必须可回链）
     缺失任一项的状态变更不得入库。同时保留完整状态变更历史（不做覆盖写）。

■ R3.5 判定执行机制（三层，替代原 §14 的单层表述）

【第一层：AI 提取与建议】
  AI 可以做：
    · 提取 reported_by 与候选 original_source
    · 判断是否疑似转载 / 转引
    · 判断来源关系（是否同集团、是否互相引用）
    · 提取报道对象（影片、角色、剧集、阶段）
    · 识别相似新闻并给出合并建议
    · 提出 verification_status **建议值**
    · 生成摘要与提醒文案
  AI 不可以做（硬禁止）：
    · 自行认定 official_confirmed
    · 自行制造来源、补充不存在的事实
    · 把传闻写成确定事实
    · 因多家网站转载而认定为真实
    · 在 owner_group 未确认时假设来源独立性

【第二层：规则硬校验】
  · official_confirmed 的硬门槛：official_source_url **必须命中预先登记的官方域名白名单**，
    否则无论 AI 如何建议，一律不得置为该状态。
  · 媒体写「Marvel confirms...」**不能**单独构成 official_confirmed 依据。
  · 建议白名单（需负责人确认后生效）：
      marvel.com、disney.com、thewaltdisneycompany.com、d23.com、disneyplus.com
  · 官方社交账号（X / Instagram / YouTube 等）无法做域名白名单校验，
    因此**不得单独构成 official_confirmed**；如需采信，必须由人工附上原始发布链接作为证据。
  · independent_group_count 由 reported_by 按 owner_group 去重自动计算，
    禁止人工直接填写该数值。
  · 校验不通过时，状态自动回落至 multi_source_reported 或 single_source。

【第三层：人工复核】
  必须人工确认的状态：
    · official_confirmed
    · officially_denied
    · conflicting
    · 任何 multi_source_reported 但 original_source 无法确定者
    · 任何涉及 supersedes / superseded_by（更正、辟谣）的记录
  人工复核动作：核对 official_source_url 可访问且确为官方；核对关联 id 有效；
  核对提醒文案与状态一致；确认后方可写入 news.js。

  Step 0  过滤
          剔除 status = officially_denied 的条目（除非 pinned = true）
          剔除 publish_time 与 first_seen_at 皆缺失的条目
          剔除 status = archived 的条目

  Step 1  置顶有效性判定
          有效置顶 = (pinned = true) AND (pinned_until 为空 OR pinned_until > 当前时间)
          失效置顶视为 pinned = false

  Step 2  分层排序
          第一层：有效置顶条目排在最前
          第二层：其余条目按 publish_time 降序

  Step 3  置顶组内排序
          先按 pinned_order 升序；pinned_order 相同时按 publish_time 降序；
          仍相同则按 id 升序（保证排序稳定、可复现）

  Step 4  并列打破
          publish_time 完全相同时，按 verification_status 优先级：
            official_confirmed > multi_source_reported > single_source
            > rumor > unverified > conflicting > officially_denied > corrected
          再相同则按 id 升序

  Step 5  截取
          首页取前 5–8 条；不足 5 条时按实际数量展示，**不得为凑数纳入低质量条目**


■ R5.3 六个必须明确的问题

  1) pinned 是否优先于时间排序？
     是。有效的 pinned 条目无条件排在任何非置顶条目之前。
     但它不改变条目自身的 publish_time，卡片仍显示真实发布时间。

  2) 置顶是否有有效期？
     有。pinned_until 为必填项，默认建议 72 小时。
     如需长期置顶，须显式填写更长的 pinned_until 并在 pinned_reason 中说明理由。
     过期后自动回到时间序，无需人工干预。

  3) 多条置顶如何排序？
     严格按 pinned_order 升序。pinned_order 为必填整数，由人工指定，禁止留空。

  4) 官方确认是否自动置顶？
     **不自动置顶。**理由：自动置顶会造成旧新闻长期压顶，
     直接违反原 §18「不能因为可信度高就让旧新闻一直排在最新新闻前面」的精神。
     如确需突出某条官方消息，由人工设置 pinned 并填写理由与有效期。
     （备选方案，默认关闭：official_confirmed 的**新增**条目可在发布后 24 小时内获得一次性
      时效加权。此方案会引入更复杂的排序状态，建议一期不做。）

  5) verification_status 在排序中的角色？
     仅作并列打破器（Step 4），不参与主排序，不产生跨时间的压顶效果。

  6) 已被官方否认的条目如何处理？
     默认不进首页列表（Step 0 已剔除），但保留全部可访问性；
     如需在首页警示，由人工 pinned 并填写理由。
