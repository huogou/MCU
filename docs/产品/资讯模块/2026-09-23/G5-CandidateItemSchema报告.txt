  · 两者均为**交付物字段**（不是管道字段）→ **不在**禁止清单内，
    会在 G6 转换时直传交付物。

4. ★★ 与 L2（merger）的接线：发现并修复一处字段名不通
============================================================

  【实测发现】`event-merger`（G4）读取条目主标识的字段名是 **`id`**；
    而候选层字段名是 **`candidate_id`**（`id` 在 L1 属禁止字段）。
    → 直接把候选对象喂给 merger：`reports[].id` 全为空 → `report_count` **恒为 0**，
      `item_ids` 为空 → 表现为「报道记录全部丢失」（**实为字段名不通，非数据丢失**）。

  【处理】在**调用侧**加适配器，**不改冻结件**：
    ```js
    CI.toMergerInput(candidate)   // → { ...candidate, id: candidate.candidate_id }
    CI.toMergerInputs(list)       // 批量
    ```
    约定：适配后的 `id` = `candidate_id` 的值（**不是**交付物 id）。

  【测试双向锁定】
    · 正证：经适配后 merger 的 `reports_preserved` = 输入条数、`records_deleted` = 0；
    · **反证**：未适配直接喂入 → `reports_preserved = 0`（证明适配器必要）。
    两条断言均 PASS（见 out-pipeline.txt 第 6 节）。

  ★ 这正是 Candidate Schema §4.1 所写「candidate_id（作为 item id）」的落地形态；
    建议在 G6 的落库流程中沿用同一适配器，不得绕过。

5. ★ 管道侧的接线点：`owner_group` 以登记表为权威来源
============================================================

  · L1 的 `reported_by[0].owner_group` **取自 `news-registry.cjs`**：
    已登记来源 → 登记表的 `owner_group`；未登记来源 → `'unknown'`。
  · 实测：C1（S001）= `Disney / Marvel`；C2（S004）= `Penske Media Corporation`；
    C3（未登记）= `unknown`。
  · ★ 意义：这闭合了 G4.3 登记的「登记表未接入判定链」缺口在**管道侧**的那一半 ——
    此前判定器读的是**交付数据**里的 `owner_group`，登记表的值无人使用；
    现在 G5 的候选层**以登记表为准**产出该值，未来落库后即可让两侧口径一致。
  · ★ 但请注意：**该缺口在交付数据侧仍未闭合** ——
    现有 005 / 008 / 010 / 014 的 `reported_by[].owner_group` 仍为「待核」，
    须按 G4.3 的 **NB-8** 在 **G8** 同步（清单已扩容为 4 项）。
