【1】建立 Gate 层（任务书 §一）
────────────────────────────────────────────────────────────────────
  pipeline\gate\gate.cjs：
  · 规则唯一且刚性：**只有 gate_status==='approved' 才能进入
    DeliveryItem 转换**；pending/rejected/非法候选一律进 rejected 桶。
  · Gate 不产生审核决策（批准是人的职责，绝不自动升级 pending）；
    纯过滤不改候选；两道独立防线（状态值枚举 → 候选整体合法性）。
  · supersedes 关系显式输入（{new, old}，candidate_id 体系）；
    引用未获批 → SUPERSEDES_REF_NOT_APPROVED（fail closed，双条必须
    同时在场，不允许只批准其一）。
  实测（T1/T2）：approved 1→转换 1 条；pending/rejected→0 条；
  非法候选/未知状态值全部拒绝。

【2】DeliveryItem 转换（任务书 §二）
────────────────────────────────────────────────────────────────────
  pipeline\delivery\delivery-converter.cjs，输出**恰 33 字段**（封闭集，
  逐键对齐 h5\data\news.js 现网条目）。六项硬规则全部落实：
  · id 重新生成：news-YYYY-MM-DD-NNN。★ 语义定案（实测发现）：id 的
    日期与序号是**落库时刻的事实记录**——现网 005 的 id 日期与
    publish/first_seen 均差一天，无法纯规则复现 → 设计为「默认规则
    （first_seen 优先日期 + 顺序 NNN）+ opts.idById 显式覆盖（承载
    落库事实）」。T1.6 验证默认规则、T6.2a 验证覆盖复现。
  · verification_status **必须计算**：唯一来源 = G1 判定器 judge()
    （冻结件只消费不修改）；候选 ai_suggested_status 结构上到不了
    状态字段（T5.3：AI 建议 official_confirmed ≠ 交付状态）。
  · independent_group_count 同样取 judge 输出，禁手填。
  · official_source：reported_by 官方组来源行直通 + G3 校验器离线
    六项校验（3 条官方行全部 valid）；URL 活性探测维持不在自动链路。
  · supersedes 链保护：id 分配后回填互链；双条保留不合并；
    引用未知 → SUPERSEDES_REF_UNKNOWN。现网形态对齐：无链 = null。
  · 管道字段禁入：21 项管道字段（含 event_key、gate_status、ai_model、
    candidate_id）+ 判定器诊断字段，深扫 0 命中（T5.2）；
    reported_by / report_corrections / conflict_statements 三个子树
    内的 source_name(source_url) 为交付物规范内结构（现网形态），
    深扫按子树豁免。
