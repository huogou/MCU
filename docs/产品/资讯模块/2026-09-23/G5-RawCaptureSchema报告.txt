2. 派生规则（全部为纯函数，零网络）
============================================================

  【P-06 url_level】`classifyUrlLevel(url)`
    · 末段为 `feed` / `rss`，或路径含 `/feed` → `feed`
    · 路径段数 ≤ 1 → `section`
    · 其余 → `article`
    实测：`/news` → section｜`/news/some-slug` → article｜`/feed/` → feed｜
          `/rss` → feed｜`/category/marvel/feed/` → feed
    ★ **已知边界**：形如 `/articles/live-events/` 的**目录页**会被判为 `article`
      （仅凭 URL 无法区分目录与文章）→ 须靠人工审核识别。
      该边界与 Q-5（文章级 URL）的 G8 整改相关，已登记。

  【P-09 published_at】`normalizeIso(raw)`
    · 支持 RFC822（RSS pubDate，如 `Mon, 22 Sep 2026 23:40:00 +0000`）与 ISO8601
    · 输出统一为无毫秒 ISO（如 `2026-09-23T01:10:00Z`）
    · 无法解析 → `null`（**不抛错**，交由 L1 走日期回落逻辑）

  【P-13 content_hash】默认 `sha1(source_url | title_raw | published_at)`；
    采集器若已算正文指纹，可通过入参 `content_hash` 覆盖。

  【P-15 event_key】
    · 调用**冻结的** `engine\dedup\event-key.cjs`（算法未改）
    · 入参：`title = title_raw`、`category = 'unknown'`、`related_* = []`
    · ★ 因此 L0 的 key 必然是 `mode=text` 的**临时指纹**（见第 3 节）

  【P-16 first_publish_time】= `published_at`（同一值；用于窗口判断与主键组合）


============================================================
3. ★★ 两条必须知悉的事实
============================================================

■ 3.1 L0 的 `event_key` 是**临时指纹**，L1 会重算

  · 原因：L0 只有 `title_raw`，**没有** `category` 与 `related_*`；
    event-key 算法在有实体时用 `mode=entity`（不含标题文本），
    无实体时退化为 `mode=text` → L0 必然走 text 模式。
  · 后果：**L1 重算后 key 通常会变**（实测 C1：L0=`evt1-061cd904677047fd`，
    L1=`evt1-d4…`，两者不同，测试已断言）。
  · 纪律：**禁止**用 L0 的 event_key 做跨层主键、跨层比较或跨层去重。
    它在 L0 层内有效（用于同批次原始去重），**跨层必须用 L1 的值**。
  · 模块已导出常量 `EVENT_KEY_IS_PROVISIONAL = true` 以便调用方自检。

■ 3.2 `registry_id` 允许保留值 `unregistered`

  · 用于「来源不在登记表」的情形（如未具名社交爆料）。
  · 采集器**不得**凭来源名猜 registry_id（G2 维护规则第 3 条）。
  · 未登记来源在 L1 的 `owner_group` 会回落为 `unknown`（登记表查不到）。
  · 该保留值属本阶段对 Candidate Schema 的**补充约定**，已登记。
