============================================================
1. 定位、四层数据模型与一条须负责人知悉的口径问题
============================================================

■ 1.1 定位
  本规范定义**管道层数据的三段结构与一段边界**：
    L0 采集器输出 → L1 候选条目 → L2 事件候选 → （边界）→ L3 交付物
  目的：让「采集器产出什么 / merger 吃什么 / judge 吃什么 / 什么能进交付数据」
  这四个此前**各自空白**的问题，有唯一答案。

■ 1.2 四层数据模型

  ```
  ┌─────────────────────────── 管道层（不进 h5/，不进交付数据）───────────────────────────┐
  │                                                                                    │
  │  L0  RawCapture（原始条目）          采集器产出，**单源单条**，未经 AI 整理            │
  │        │  ×N（同一事件的多个来源各自产出）                                            │
  │        ▼                                                                            │
  │  L1  CandidateItem（候选条目）        AI 整理后；按 event_key 聚合前的候选单位         │
  │        │                                                                            │
  │        ▼  由 G4 的 event-merger 归并                                                  │
  │  L2  EventCandidate（事件候选）       同一事件的多条候选被聚成一个事件对象               │
  │        │                                                                            │
  └────────┼────────────────────────────────────────────────────────────────────────────┘
           │  ★ 转换边界（第 6 节）：只在 G6 人工审核闸门之后发生，且**单向**
           ▼
        L3  DeliveryItem（交付条目）      33 字段，写入 h5/data/news.js
  ```

  ★ 关键性质：
    · **L0/L1/L2 一律不进入 h5/**，也不进入交付数据；
    · 每层都有明确的「上一层给的字段 + 本层新增字段」，不得跨层越权写入；
    · 交付物字段共 33 个，**四层结构不改变它**。

■ 1.3 ★★ 管道字段清单的口径（**已裁定：禁止清单模式 B**）

  **裁定**（2026-09-23，G4.3）：采用**禁止清单模式（B）**。

  【正式定义】
    · **Candidate 层**：**允许增加管道字段**，总量不设上限。
    · **DeliveryItem 层**：**严格限制为 33 字段**（前端展示 26 + 审计 7），不增不减。

  【冻结规则】任何新增管道字段**必须同时满足以下 4 条**，缺一不得新增：
    1. **不进入 h5**（不得出现在 h5/ 目录下的任何文件）
    2. **不进入 33 字段交付物**（不得出现在 h5/data/news.js）
    3. **不影响 8 态判定**（不得参与 verification_status 的计算；不得被判定器读取）
    4. **不改变审核闸门逻辑**（不得改变 gate_status 的语义与「未审核不得入库」的约束）

  【口径的准确表述】
    Candidate Schema **不限制管道字段总量**；
    它只限制「**禁止进入 DeliveryItem 的字段集合**」。
    即：管道层的字段**数量是开放的**，交付层的字段**集合是封闭的（33）**。

  【为什么取 B 而非 A（封闭清单）】
    ① 「33 字段交付物不变」是真正的硬约束；G0 冻结件对那 12 项的立法措辞是
       「冻结为**『不进交付物』**」——属**禁止性约束**，不是枚举上限。
    ② 若按封闭清单执行，候选层将无法留存采集证据与闸门状态，等于放弃可追溯性，
       而可追溯性属本项目治理铁律的核心。

  【存档：若按封闭清单执行将丢失的能力（仅作立法记录，不构成待决项）】

  ┌──────────────────┬──────────────────────────────────────────────────────────┐
  │ 被裁掉的字段       │ 丢失的能力                                                │
  ├──────────────────┼──────────────────────────────────────────────────────────┤
  │ `capture_id`      │ 无法把交付条目回溯到**具体哪一次采集抓到的原始条目**          │
  │ `capture_refs`    │ 无法证明「一个事件的多个来源」各自来自哪次抓取                │
  │ `candidate_id`    │ 候选层失去稳定标识，审核记录无法与候选对应                   │
  │ `url_level`       │ **Q-5 文章级 URL 的合规状态无法被暴露与统计**（重要）          │
  │ `title_raw`       │ 无法核对 AI 改写是否偏离原文（文案纪律的可审计性下降）         │
  │ `published_at_raw`│ 时间解析失败时无法回溯来源原始时间字符串                     │
  │ `gate_status`     │ **人工审核闸门失去机器可读状态**（"未审核不得入库"难以强制）   │
  │ `occurrence`      │ 事件级稳定键（B4）无法实现（可退回 B-i 组合键）               │
  └──────────────────┴──────────────────────────────────────────────────────────┘

  ★ 登记：按模式 B，管道层字段由 12 个扩充为 **20 个**（清单见 6.4 节），
    并登记为 **P-01 – P-20**。**该裁定不影响 33 字段交付物与 8 态体系。**

  └──────────────────────────────────────────┴────────────────────────────────────────┘

  ★ **merger 不得读取**（已由 G4 的 95 条断言覆盖）：
    `verification_status` / `judged_by` / `chain_steps_hit` /
    `status_history` / `ai_suggested_status` / `gate_status`
  → 即 merger **不做任何状态或审核判断**，只做机械聚合。

■ 4.2 merger 的**输出结构**（EventCandidate，继承 G4 实现）

  ```
  {
    event_key, occurrence（条件字段，见 4.3）,
    item_ids: [], report_count, category,
    first_publish_time, last_publish_time,
    within_window: boolean,
    decision: 'merge' | 'single' | 'hold',
    hold_reason: '' | 'out_of_window' | 'missing_time',
    reports: [ { id, publish_time, first_seen_at,
                 source_names, source_urls, owner_groups } ],   ← 不裁剪
    reported_by_union: [ { source_name, source_url, owner_group } ],
    distinct_owner_groups: [...],
    note
  }
  ```

■ 4.3 `occurrence` 的条件性

  · 若 G4.1 的 Z-3 采纳 **B-ii**（occurrence 序号）→ 本字段**必填**，
    编号规则与实现要点见同批《资讯事件归并与 event_key 边界规范 V1.0》B4。
  · 若采纳 **B-i**（组合键）→ 本字段**不出现**，事件级稳定键由
    `event_key + '@' + first_publish_time` 组成（本 schema 已含 first_publish_time，无需变更）。
  · ★ 在 Z-3 裁定前，该字段**不得**在任何产出中出现。

5. L2→L3 之间的判定输入：judge 输入契约
============================================================

■ 5.1 judge 的三个入参（继承 G1 实现）

  ```
  judge(item, input, opts)
  ```

  【item】— 判定器只允许读取以下 **6 个字段**：

  ┌──────────────────────────────────────────┬────────────────────────────────────────┐
  │ 读取字段                                  │ 用途                                    │
  ├──────────────────────────────────────────┼────────────────────────────────────────┤
  │ `id`（或 candidate_id）                   │ 结果标识                                │
  │ `reported_by`                            │ 独立证据组计算、来源证据                  │
  │ `report_corrections`                     │ Step 3 判据                             │
  │ `conflict_statements`                    │ Step 4 判据                             │
  │ `original_source`                        │ Step 7 判据（**唯一允许文本匹配的字段**）  │
  │ `original_source_url`                    │ Step 7 证据                             │
  └──────────────────────────────────────────┴────────────────────────────────────────┘

  ★ **judge 不得读取** `title` / `summary`（已由 G1 断言覆盖）——
    判定器**不读文本、不做语义判断**。

  【input】— I9 语义标记（由第一层 AI 建议 + 人工复核后以结构化形式传入）：

  ```
  {
    official_confirm:  { url, reviewed, event_id? },   // Step 1
    official_denial:   { url, reviewed },              // Step 2
    conflict_verified: { verified }                    // Step 4
  }
  ```
  三项均可缺省；缺省时对应步骤**不成立**（一律降级，绝不升格）。

  【opts】— `{ now, pathPolicy, previousStatus, judgedBy }`
    · `pathPolicy` 默认 `legacy`（E-1 冻结）
    · `judgedBy` 覆盖须留痕（见同批 judged_by 规范 2.3②）

■ 5.2 输出（7 项必填，缺一不得入库）

  `verification_status` / `chain_steps_hit` / `judged_by` / `status_changed_at` /
  `status_change_reason` / `status_change_evidence_url` / `status_history_entry`
  另附诊断字段（不进交付物）：`rule_version` / `path_policy` /
  `independent_group_count` / `reliable_group_count`

■ 5.3 官方 URL 校验的接入点（G3）

  判定器在 Step 1 / Step 2 需要 host / path 校验时，
  应调用 G3 的 `validateOfficialSource(input, opts)`，其输入为：
  `{ source_url, source_name, registry_entry, claimed_event_id, official_confirm }`。
  ※ G3 的校验器**尚未接线**到判定器（两套实现并存，已用交叉一致性断言控住漂移）；
    接线方案待立项，不属本规范范围。

■ 6.3 必须**重算或生成**的字段（不得从候选直接搬运）

  ① `id` —— 由 **G6 落库时生成**，格式 `news-YYYY-MM-DD-NNN`（当日三位序号）。
     ★ 候选层**不得**预先占用该格式（故候选用 `candidate_id`）。
  ② `verification_status` —— **必须由判定器按 R8.3 重算**。
     候选层 `ai_suggested_status` **仅供参考，不得直接采用**。
  ③ `official_source` / `official_source_url` —— 来自 I9 标记 + 人工登记，
     **且必须通过 R7.4 校验**（G3）；否则留 `''`。
  ④ `independent_group_count` —— 由 `reported_by` 按 owner_group 去重**运行时计算**
     （与 components.js 口径一致）；**禁止人工填写、禁止从候选搬运**。
  ⑤ `supersedes_id` / `superseded_by_id` —— 由人工或 G6 依据更正声明写入；
     ★ 受 A4/A5 约束：**不得**因事件归并而合并两条（见同批边界规范）。
  ⑥ 审计 6 项 + `status_history` —— 全部来自判定器输出；
     `status_history` **只追加、禁止覆盖写**。

■ 6.4 禁止进入交付数据的字段（**管道层 20 项，全量禁止**）

  【G0 冻结件原有 12 项】
    `event_key`｜`registry_id`｜`ingested_at`｜`raw_excerpt`｜`content_hash`｜
    `crawl_evidence`｜`ai_suggested_status`｜`ai_model`｜`pipeline_run_id`｜
    `reviewed_by`｜`reviewed_at`｜`rule_version`
  【本规范新增登记 8 项（按第 2 / 3 节的 P 编号）】
    `capture_id`(P-01)｜`candidate_id`(P-17)｜`gate_status`(P-18)｜
    `url_level`(P-06)｜`title_raw`(P-07)｜`published_at_raw`(P-08)｜
    `capture_refs`(§3)｜`occurrence`(条件字段，见 4.3)

  ★ 合计 **20 项**（含 1 项条件字段），**任何一项出现在交付数据中即为违规**。
  ★ 违规检查：交付数据的字段集合必须**恰为 33 个**（见第 4 节违规表第 1–3 条）。
  ※ 说明：第 2 / 3 节的 P-01 – P-18 是**候选层字段编号**，用于本规范内部引用；
    与 G0 冻结件的「12 项管道字段清单」是两套编号，不可混用。
  ※ `first_publish_time`(P-16) 不属禁止项之外的新增——它等价于既有的
    `first_seen_at` 语义的稳定形式，二者在交付物中为 `first_seen_at`；
    候选层保留 P-16 仅用于窗口判断与主键组合。

■ 6.5 单向性

  转换是**严格单向**的：`候选 → 交付物`。
  交付数据**不得**反向写回候选层；候选层**不得**读取交付数据作为输入。
  两者的唯一交集是「同一事件」的语义对应，**不是数据依赖**。

■ 6.6 转换后校验清单（G6 落库后必须全绿）

  ┌────┬──────────────────────────────────────────────────────┬──────────────────┐

  ├────┼──────────────────────────────────────────────────────┼──────────────────┤

8. 版本与变更流程
============================================================

  1. 本规范版本号独立演进（V1.0 → V1.1 …）；字段增删均须升版本。
  2. **不得**在 V1.x 内改变任何字段的**语义**；仅可新增可选字段并登记编号。
  3. 任何变更须同步更新：本规范 + 关联的回归断言 + G5/G6 的任务书。
  4. 与冻结件的关系：本规范**不得**改变 33 字段交付物、8 态体系、
     12 项既有管道字段的语义。管道层新增字段须在第 6.4 节登记。
  5. **管道字段总量开放**（1.3 节裁定 · 禁止清单模式 B）：
     新增管道字段**不受数量限制**，但必须**同时满足**以下 4 条，缺一不得新增：
       ① **不进入 h5**
       ② **不进入 33 字段交付物**
       ③ **不影响 8 态判定**
       ④ **不改变审核闸门逻辑**
     → 约束的对象是「**禁止进入 DeliveryItem 的字段集合**」，
       而不是「管道层字段的个数」。
