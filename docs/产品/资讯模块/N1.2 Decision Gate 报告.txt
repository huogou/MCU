§一 Decision Gate：S001 人工 HTML 通道形态
----------------------------------------------------------------
【当前代码现状】S001 被 collectLive 白名单排除（F3/F4）；无任何自动取数代码路径；G5.3 实测 S001 全站 403。
【可选方案】
  A. 文件投递型：运营把抓取的 HTML/JSON 放入指定 inbox 目录，接线读取 → 转 RawCapture(L0)。
  B. 粘贴 HTML/文本型：小脚本/接口接收粘贴内容写入 inbox（需后台入口，违背「不增加复杂后台UI」）。
  C. 本地目录监听型：fs.watch 常驻监听 inbox 自动触发（引入常驻进程，违背「默认不自动」+ 最小化）。
  D. 复用现有最小方案：人工直接产出符合 L0 结构的 RawCapture（JSON），复用 base-collector 的 NM.toCaptureInput + RC.create 接入，与自动采集同构后续链路。
【推荐方案】D 为主 + A 为辅。即新增轻量 manualCaptureLoader：读 inbox 下的 L0 JSON（或 HTML→同一 parser 解析为 L0），输出与 collectLive 同构的 captures，直接进入 capture→candidate→adapter→normalizer。B/C 不推荐。
【推荐理由】最小改动、零新依赖、可审计（文件留痕）、可回放（重放 inbox 文件）、复用既有 RawCapture 契约不破坏 G5.2。
【对 D1/D2/G1–G10 影响】仅新增 manualCaptureLoader（新文件）；不影响 D1/D2 矩阵（manual 走 production-capture 的 opts.captures 注入路径，已支持）；不修改 G 模块。
【实施复杂度】低（复用 RC.create / NM.toCaptureInput）。
【风险】中低——S001 列表 75% 非影视需过滤，但过滤逻辑归属 G5.2 parser，人工通道只喂 HTML 原文，过滤规则沿用不新增。
【是否需要我拍板】是（确认选 D+A；inbox 目录位置/命名/投放责任人；S001 过滤是否需在人工通道额外加严）。

§二 Decision Gate：S002 调度频率与默认自动性
----------------------------------------------------------------
【当前代码现状】orchestrator.runPipeline 支持 dry-run / production-capture / production-review / production-delivery-preview，全手动 CLI 触发；无 scheduler/cron。
【可选方案】
  A. 维持全手动（现状）。
  B. 加 scheduler 脚手架（runner/scheduler.cjs）+ cron 模板，默认禁用自动生产，仅 manual 触发。
  C. 默认自动定时 production-capture。
【推荐方案】B，且默认禁用自动生产：scheduler 脚手架可建，但默认不启用；若启用，默认走 dry-run 或 capture-only（不 --persist），人工 review 后才 delivery。符合「不要因为存在 cron 就启用自动生产」「默认可控、可回滚、可审计」。
【默认频率建议】若启用：每日 1–2 次（资讯时效中等），且首轮仅 capture-only。
【失败后重试】采集层当前无重试；建议明确「采集失败不自动重试，仅记入 run-history + 失败表」，避免雪崩/被封。
【是否允许真实生产自动运行】默认否，需你批准（见 §三 S003）。
【对 D1/D2/G1–G10 影响】scheduler 为新文件，调用 runPipeline 时须遵守 D1/D2 矩阵（尤其 dry-run 不写、--persist 才落盘）；不修改 G。
【实施复杂度】低（脚手架）。
【风险】中——若误启用自动 --persist 会落未审数据；以「默认禁用 + 默认 capture-only」缓解。
【是否需要我拍板】是（是否要 scheduler 脚手架；频率；是否允许自动）。

§三 Decision Gate：S003 是否现在执行首次真实 live 采集
----------------------------------------------------------------
【方案 A：立即执行】
  风险：高——可能触发 S001(403)/S003(403)/S005(ECONNREFUSED)；S002/S004/S006 成功会产生真实 captures。
  对 news.js：无影响（采集层只产 L0 capture，不碰 news.js）。
  是否产生真实数据污染：仅当 --persist 且未审才会落 captures 目录（capture 非 delivery，需 review/gate 才进 news.js；且 capture 幂等去重）；不 --persist 则零持久化。
  是否触发 AI Provider：否（采集层不调 adapter）。
  是否进入持久化：取决于是否 --persist（默认不 --persist 则不落盘）。
  回滚：不 --persist 则无持久化，直接丢弃；--persist 则删除对应 captures 日期文件（幂等可控）。
【方案 B：暂不执行（推荐）】仅完成 dry-run / fixture / capture-only 验证。
  理由：治理红线（真实 live 需人工显式触发）、S001/S003/S005 已知失败、N1.2 仍处 Gate 阶段。
【结论】推荐 B；未经你明确批准不得执行（指令亦明确）。
【是否需要我拍板】是（是否批准 A）。

§四 Decision Gate：S004 S003/S005 失败处理
----------------------------------------------------------------
【当前代码现状】S003/S005 在白名单内但结构性失败（F5）；collect 单源 fail-closed（F6）；失败写入 run-history source_failed/reasons（F7）；无重试、无独立 failure 表、无降级决策（F8/D3）。
【哪一步失败】fetch 阶段（403/ECONNREFUSED）→ result.errors 记 stage:'fetch'。
【是否重试】当前否；建议对 403/ECONNREFUSED 不重试（环境层失败，重试无意义且可能加剧被封）。
【是否进入 failure state】当前无；registry 有 consecutive_failures 但采集不更新。
【是否写 run-history】是（source_failed + reasons 已写）。
【是否写 persistence】否（失败 item 不入 candidates/deliveries；若 --persist 仅落成功的 captures）。
【单条 vs 整批】源级失败=source_failed++；源内单条失败=result.errors 带 index + stats.rejected++，不影响同/他源其他条。
【如何保证不污染正式数据】失败仅留痕 run-history；不进 candidates/deliveries/news.js；capture 幂等去重。
【可选方案】
  A. 维持现状（失败留痕 run-history，不重试，不持久化失败 item，继续其他）——最小。
  B. 加轻量失败表（pipeline/failures/ 落 source_failed reasons 供排查），不重试——利于审计，低风险。
  C. 加重试（指数退避 N 次）+ failure state 标记 consecutive_failures。
【推荐方案】A 为 N1 基线；B 建议纳入 N1.2 实施（失败表，低风险）；C 暂不推荐（对 S003/S005 无意义且增风险）。
【对 D1/D2/G1–G10 影响】B 为新文件，不修改 runPipeline；run-history 已含 source_failed（不改）；无 G 修改。
【实施复杂度】A 零 / B 低 / C 中。
【风险】C 重试有被封风险。
【是否需要我拍板】是（选 A/B/C；S003/S005 是否降级为「暂弃/人工」）。
