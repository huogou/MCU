## 2. 发布文件边界

### 2.1 `news.js` 数据结构（G9 写入前后一致）
- 文件头部定义 `window.MCU_NEWS_META = {...}`（`h5/data/news.js:39`，含 `stage` 等元信息）与 `window.MCU_NEWS = [...]`（`:47`）。
- 每条记录为 **33 字段封闭集**（delivery-converter.cjs:39-48）：`id, title, summary, publish_time, first_seen_at, verification_status, category, reported_by, independent_group_count, original_source, original_source_url, official_source, official_source_url, related_movies, related_series, related_characters, related_phases, pinned*, status_history*, supersedes_id, superseded_by_id, report_corrections, conflict_statements, judged_by, chain_steps_hit, conflict_resolved_at, conflict_resolved_by_evidence_url`。
- **G9 写入方式**：先读取现有 `news.js`，文本级追加新审核通过的 `DeliveryItem`（`run-g9-write.cjs`，幂等守卫防重复）。故"发布前"= 现有 52 mock；"发布后"= 现有 + 新真实记录，结构不变。

### 2.2 生产 H5 是否只更新 `data/news.js` 即可
- **是（对纯资讯更新而言）**：`MCU_NEWS` 完全由 `data/news.js` 提供，页面仅引用该文件。只要待发布记录**不引入新实体 ID**，仅复制 `data/news.js` 即可生效。
- **例外**：若某条资讯 `related_*` 指向**新增实体**（如本轮暂缓的 `avengers-doomsday` 等），则对应的 `content.js`/`characters.js` 也必须同步更新并发布，否则跨链断裂。当前发布边界内不新增实体，故**仅需 `data/news.js`**。

### 2.3 依赖 `MCU_NEWS` 的页面/脚本（verify2.js 实测）
- `index.html`（1 处引用，`:182`，`V2.sortNews`）、`news.html`（`:55`）、`news-detail.html`（`:49`，按 id 查详情）、`assets/js/components.js`（`:377` 注释、`:801` 渲染）。
- `special.html`、`community.html` **明确不加载** news.js（引用数 0）——不受影响。

### 2.4 发布时是否必须同步其他文件
- **默认不必**：仅 `data/news.js` 单文件。
- **禁止全量覆盖**：不得因两目录结构相似就把 `mcu-atlas-news/h5` 整体复制到 `mcu-h5`——`mcu-h5` 是独立生产目录，全量覆盖会连带覆盖生产态页面/备份，且引入不可控差异。发布脚本**只复制明确指定的单文件**。

### 2.5 其他可能影响发布的线上配置/备份/脚本
- `mcu-h5/data/` 含 `news.js.bak-*` 历史备份与 `*.js` 数据文件（与 workspace 镜像一致）。发布脚本**不得**触碰这些 `.bak-*`，并应**自行生成带时间戳的生产备份**。
- 现有 `news.js.bak-*` 是 G9 自身在工作区生成的备份；线上备份由发布脚本独立管理。
- 无自动同步脚本、无 git、无 CI——发布动作目前只能由"受控脚本 + 人工确认"或"面板手动"完成。

## 3. 发布方式比较及推荐方案

| 方式 | 复杂度 | 覆盖风险 | 可回滚性 | 缓存影响 | 维护成本 |
|---|---|---|---|---|---|
| **A. 仅手工 cp 审核后 news.js** | 极低 | 高（无备份/校验/确认） | 差（需手动先备份） | 未处理（7d 缓存） | 低但易出错 |
| **B. 受控脚本发布指定文件**（备份+校验和+失败保护） | 低（单脚本） | 低（只动单文件） | 强（自动备份+一键回滚） | 配合缓存规则可控 | 低 |
| **C. 现有面板/已有机制** | — | — | — | — | — |

- **C 评估**：可读证据中**不存在**自动化部署脚本（仅历史 `deploy-diff-20260923.json`）；宝塔面板虽在，但无证据表明其配置了针对本项目的发布流程。故 **C 视为"未确认"，不作为主方案依赖**。
- **推荐：方式 B**，并叠加一次性的**定向缓存规则**（见 §5）。理由：最小改动、无需付费服务、无需新构建系统；单文件复制风险最低；自带备份/校验/回滚满足安全边界。

**推荐发布脚本设计（仅设计，本轮不执行）**：
```
publish-news.sh / publish-news.cjs 逻辑：
  1. 入参：源 = mcu-atlas-news/h5/data/news.js；目标 = mcu-h5/data/news.js
  2. 预检：源文件存在且可被 JS 解析；记录数 / 字段 / 重复 id 校验（见 §3 检查清单）
  3. 差异：diff 工作区 vs 生产当前 news.js，生成可审阅差异（不自动应用）
  4. 备份：复制生产 news.js → news.js.bak-<ISO时间戳>（不覆盖既有 .bak-*）
  5. 写入：仅复制源到目标（单文件）
  6. 校验：重读目标，确认记录数/首尾 id 与源一致（CRC/字节比对）
  7. 回滚：失败时 cp 备份回目标
  8. dry-run 模式：只做 1-4 与报告，不写目标
```
> 不引入新依赖；可用 Node 自带 `fs`/`crypto` 完成校验与备份。

## 5. 缓存更新策略及依据

### 5.1 现状（verify2.js 实测）
- 三个 vhost 均含 `location ~* \.(css|js|json)$ { expires 7d; add_header Cache-Control "public"; }`（行 79/37/71）。
- 由于 `news.js` 匹配该正则，**浏览器/代理会缓存 7 天**；而 `.html` 为 `no-cache`，页面本身会重验证，但引用的 `news.js` 仍按 7d 缓存 → 发布后最长 7 天用户可能看到旧资讯。
- **无 CDN**（vhost 无 `upstream/cdn/proxy_cache`；仅本地论坛 API 反代）。

### 5.2 方案比较
| 方案 | 改动 | 可靠性 | 评价 |
|---|---|---|---|
| (1) `news.js` 加版本查询参数 `?v=...` | 需改 3 个 HTML 的 `<script src>`，**每次发布都要同步 HTML** | 高 | 每次发布多同步 3 个页面，覆盖面扩大，维护成本高 |
| (2) **定向 nginx 规则** `location = /data/news.js { add_header Cache-Control "no-cache"; expires -1; }`（置于通用 `.js` 正则之前） | 一次性改 3 个 vhost，需 `nginx -s reload` | 高（nginx `=` 精确匹配优先级高于 `~*` 正则） | **推荐**：最小、作用域精确（只影响该数据文件，不动全站 JS），发布后无需改 HTML |
| (3) CDN 刷新 | 不适用 | — | **不存在 CDN**，排除 |

### 5.3 推荐
- **采用方案 (2)**：在三个 vhost 中、通用 `.js` 正则 location **之前**新增 `location = /data/news.js { add_header Cache-Control "no-cache, must-revalidate"; expires -1; }`。`=` 精确匹配优先级最高，仅命中该文件，不改变其他 `.js`/`.css` 缓存策略。
- 实施时需对 nginx 配置做语法校验（`nginx -t`）并 `reload`（非 restart）。
- 作为补充保险，发布脚本可在复制后输出"建议强制刷新提示"，但核心靠 no-cache 保证。

## 6. mock 切换为真实资讯的前置条件

从当前 52 条 mock 切换到真实资讯**之前**必须满足（任一不满足则维持 mock 或暂缓）：

1. **数据来源真实**：G9 输入来自经采集/审核的真实候选，而非 mock 生成器。
2. **人工审核完成**：所有待发布记录 `gate_status==='approved'`（GATE.review 过滤通过）。
3. **字段校验通过**：33 字段齐全、`verification_status` 8 态合法、无重复 id（§4 发布前清单）。
4. **去重**：与现网已发布记录（含 `news-2026-10-15-001` Endgame Encore 等）无重复事件（delivery-converter supersedes 链保护）。
5. **剧透标识**：高剧透内容（如前序 #14）已正确标注，默认不发布或受控展示。
6. **关联实体已就绪**：`related_*` 指向的实体在 `content.js`/`characters.js` 中**已存在**（或随本次一并同步发布）；缺实体不得强行发布空关联冒充完整资讯。
7. **线上验证**：按 §4 发布后清单，三页面与详情页实测通过。
8. **备份/回滚已验证**：发布脚本 dry-run 与回滚路径在本环境实测可用。
9. **缓存策略已就位**：§5 定向 no-cache 规则已生效，避免 7 天陈旧窗口。

> 本轮**不**删除 mock、不写入真实资讯、不改变实体库（严格遵守禁止项）。

## 7. 回滚方案

- 每次发布由脚本在写入**前**自动生成带时间戳的生产备份：`mcu-h5/data/news.js.bak-<ISO时间戳>`（不覆盖既有 `.bak-*`）。
- **回滚动作**：`cp` 该备份覆盖回 `mcu-h5/data/news.js`，必要时 `nginx -s reload`（若缓存规则变动）。
- G9 自身在工作区也有 `news.js.bak-*`（run-g9-write 历史），可作为二级恢复点。
- 因发布是**单文件复制**，回滚粒度精确到一次发布，影响面仅资讯数据，不波及其他页面/资源。

## 8. 尚未确认的事项与风险

- **自动同步机制是否存在**：可读证据中无脚本/CI/git；当前 `mcu-h5` 与 `mcu-atlas-news/h5` 内容一致（含 52 mock）的达成方式**未确认**（疑似历史手工复制）。→ 发布机制须以"受控脚本 + 人工确认"为基线，不假设已有自动链路。
- **宝塔面板是否具备可用发布功能**：面板存在，但无证据表明其配置了本项目发布流程 → 不依赖（方式 C 排除）。
- **CDN**：证据显示不存在 → 无需 CDN 刷新；若未来接入 CDN 须重评 §5。
- **nginx reload 权限**：实施需 `nginx -t` + `reload`（或面板操作），属服务器配置变更，须由有权限者执行；本轮未做。
- **全量覆盖风险**：若未来有人为"省事"整体复制 `h5/` → `mcu-h5`，会覆盖生产态页面与备份，须在流程文档中明确禁止。
- **缺口**：当前"schema/重复 id 自动校验"需发布脚本实现（非既有独立工具），列为实施任务而非已具备能力。

## 9. 后续实施任务及顺序

1. **编写受控发布脚本**（publish-news.cjs/sh）：单文件复制 + 预检 + diff + 自动备份 + 校验 + dry-run + 回滚（§3）。

5. **（可选）面板发布动作**：若策划确认宝塔可用，将其作为方式 C 补充，但主流程仍以脚本为准。
