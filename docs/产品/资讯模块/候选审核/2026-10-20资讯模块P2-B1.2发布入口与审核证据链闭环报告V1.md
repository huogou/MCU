## 1. 审核身份校验边界（§一）

### 1.1 复核对象
- `gate-review.cjs` / `review-actions.cjs` / `gate.cjs`：`operator` 来自运行者任意输入的 `--operator` 参数，**既不是系统身份，也不是可信配置，更非密码学凭据**。
- `export-approval-manifest.cjs`：P2-B1.1 已加入**可信审核人白名单**（`trusted-reviewers.json`，负责人带外维护）；白名单缺失/为空时任何"看似人工但无法核实"的审核人一律阻断（fail closed）。

### 1.2 `--operator` 是否可任意填写？
**可以。** `gate-review.cjs` 直接把 `--operator` 写入审核记录，环境（root 登录 ECS、无 SSO/LDAP）无法提供可靠身份凭据。

### 1.3 白名单校验能否防止冒用白名单名称？（实测证明）
在服务器独立临时目录构造并运行（详见 §5 命令）：

- **白名单内名称 `王审核`**：导出仅被"目标 news_id 不存在于本次待发布数据"拦截，**白名单名称已通过** → 证明只要填白名单内的名字，无需任何真实身份，即可通过白名单校验。
- **白名单外名称 `赵审核`**：被"审核人不在可信白名单"拦截。

> 即：白名单是**基于名称的流程级信任锚**，不绑定真实操作者。任何人若能运行工具并把 `reviewer` 填为白名单内名称，即可让未经可信身份确认的审核记录进入批准清单。本环境无法消除此限制，已如实标记为流程级控制，**未宣称已完成真实身份认证**。

### 1.4 最小可行操作控制方案（§一.5，不伪造凭据）
1. **负责人亲自触发**：`gate-review approve`（带真实 `--operator`）→ `export-approval-manifest.cjs` → `publish-news.cjs --publish` 必须由项目负责人在其可控的 ECS 终端显式执行并复核生成的清单；脚本不得无人值守自动放行。
2. **白名单带外维护**：`pipeline/review/trusted-reviewers.json` 仅含真实授权审核人，存放于受控目录；缺失即阻断全部导出/发布（已落地 fail closed）。
3. **优先用真实审计链路**：真实审核证据优先采用 `--history`（gate-review 追加的 append-only `review-history.json`），而非 `--records`（手工文件可被任意填名称）；`--records` 仅用于负责人自己的内部草稿整理。
4. **可追溯证据留痕**：每次导出生成的 `approved-manifest.json` 含 `reviewer_trust` / `source_data_path` / 逐条 `reviewer + reviewed_at + source`，长期归档；发布入口**独立**复核白名单，形成纵深防御。
5. **不伪造身份凭据**：`operator` 名称仅作流程级标识，已在清单与日志中明确标注 `reviewer_trust: 'allowlist'`，非密码学验证。

## 2. 正式发布入口绕过验证（§二）

### 2.1 加固前风险
`publish-news.cjs` 的 `loadApprovedIds`（原 101–117 行）**仅按 `id + action=approve` 收集**批准 id，**不校验** `reviewer / reviewed_at / source / reviewer_trust`，也**不校验**审核人白名单。手工伪造的极简清单可绕过发布入口。

### 2.2 加固后规则（已实施）
`loadApprovedIds(manifestPath, allowPath)` 现在强制：
1. 顶层必须声明 `reviewer_trust === 'allowlist'`（禁止无身份声明的清单）；
2. 发布侧**独立**加载白名单（纵深防御），缺失即拒绝；
3. 纯 `approved_ids` 列表（无 per-entry 证据）拒绝；
4. 逐条批准须含 `reviewer`（非空且**在可信白名单**）、`reviewed_at`（ISO）、`source`（非空），否则整份拒绝；
5. 最终必须有 ≥1 个有效批准 id。

### 2.3 伪造清单实测接受/拒绝结果（§二.3，服务器独立临时目录）

| 清单类型 | 结果 | 说明 |
|---|---|---|
| 带证据 + 白名单内名称（`王审核`）+ `reviewer_trust` | **接受**（ok=true） | 残留风险=**名称级信任**（非密码学身份），详见 §6.6 |
| 缺 `reviewer_trust` | **拒绝** | "审核证据缺少有效的 reviewer_trust" |
| 白名单外审核人（`赵审核`） | **拒绝** | "审核人不在可信白名单" |
| 纯 `approved_ids` 列表（无 per-entry 证据） | **拒绝** | "纯 id 列表无 per-entry 证据" |
| 交付失败诊断映射（`status:'failed'`）被当作有效映射 | **拒绝** | "映射标记为失败状态，不可作为有效映射" |

> 由导出工具生成的有效清单（含 `reviewer_trust` + 逐条证据 + 白名单内审核人）仍正常解析并通过（回归测试验证）。

### 2.4 版本化批准清单能防止/不能防止什么（§二.5）
- **能防止**：无身份声明、缺证据字段、白名单外审核人、纯 id 列表冒充的伪造清单；以及把"交付失败诊断映射"误当有效映射。
- **不能防止**：在**知道白名单名称**的前提下，手工拼一份带 `reviewer_trust` + 该名称 + 合理 `reviewed_at/source` 的 JSON（本环境无真实身份，普通 JSON 字段本身不是不可伪造的证明）。该残留风险由 §1.4 的操作控制兜底，不假装已消除。

## 3. 候选 ID ↔ 最终 news ID 映射接线（§三）

### 3.1 `id_assignments` 真实调用位置
- `delivery-converter.cjs` 的 `toDeliveries` 返回 `report.id_assignments = [{from_candidate, to_delivery}]`，**仅存于返回值、从未落盘**；`news.js` 记录不含 `candidate_id`。
- 真实消费点 `/ 写入器`：`pipeline/tools/news-append-writer.cjs` 是**参数化发布写入器**，它消费**已转换**的 `delivery-preview.json`（33 字段 items），**自身不调用 `toDeliveries`，亦不含 `candidate_id`** → 无法在写入器内产出映射。
- 真正调用 `toDeliveries` 并内联消费 `id_assignments` 的是 **`run-g9-write.cjs`**（冻结件：硬编码 G8 基线 `589A3934` 与 `20260923` 数据，**不可复用、不可改**）。

### 3.2 映射持久化接线（最小改动，新增非冻结工具）
新增 `pipeline/tools/deliver-and-map.cjs`（纯新增，不碰冻结件）：
1. `DC.toDeliveries(candidates)` → `{items, report.id_assignments}`；
2. 写 `delivery-preview.json`（供 `news-append-writer.cjs` 追加发布）；
3. 持久化 `id-map.json`（标准映射，供 `export-approval-manifest.cjs --map` 读取）；
4. 纪律：仅产出 preview + map 两类工件，**不写 h5、不改 news.js、不发布**；
5. 失败处理：交付失败（`toDeliveries` 抛错）时**不写 preview**，仅写 `status:'failed'` 的诊断映射（明确标记，导出侧 `loadMap` 会拒绝），绝不留下可被误认的有效映射。

> 复用 `delivery-id-map.cjs` 的 `buildMapManifest` / `writeMapFile`（已支持 `status` 字段），并修正 `fromCandidates` 使其同时接受**文件路径或已解析数组**（此前仅接受路径，导致接线时把数组当路径报错，已修）。

### 3.3 是否已接入真实交付流程（§三.6）
**尚未接入现行生产路径**，原因（已如实说明，未修改冻结/生产路径）：
- 真实 G9 入口 `run-g9-write.cjs` 为**冻结/硬编码基线件**，按规则不得改动；
- `news-append-writer.cjs` 仅消费 preview、无 `candidate_id`，无法在写入器内接线；
- 因此 `deliver-and-map.cjs` 作为**安全接线替代点**已就绪并测试，待交付步骤由冻结件重构时采用（届时把"生成 preview + 落盘 map"统一收口到该工具，即可闭环）。

### 3.4 映射目标一致性校验（§三.5）
映射完整性校验已在 `export-approval-manifest.cjs`（P2-B1.1）强制：候选重复、多候选→同 news 冲突、目标 `news_id` 不存在于待发布数据源、缺映射，全部阻断（见导出自检 §5）。
