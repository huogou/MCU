## 二、两条路线比较与结论

| 维度 | 方案 A（保留结构，修最关键写边界） | 方案 B（publish-news 唯一写者） |
|---|---|---|
| 实际改动 | 仅给 `news-append-writer` 加 `--manifest` 门禁（复用已有 `loadApprovedIds`） | 须解决软链（source≡target）：要么断软链分两物理文件再同步，要么让 publish 读 staging 再写生产（又需另一工具填 staging）→ 重构更多 |
| 日常步骤 | 沿用现有工具链，步骤短 | 需新增 staging 概念/同步，步骤更长 |
| 失败恢复 | 复用已 4 次生产实跑验证的双备份+幂等 | 需重新建立 staging→生产 的备份/原子替换，未经实战 |
| 长期维护 | 单一已验证写入器，最少代码 | 双文件/staging 同步，更多出错点 |

**结论：推荐方案 A。** 它用最少改动闭合"未经审核不得入生产"这一唯一硬缺口，且复用已实战验证的备份/幂等机制；方案 B 因软链致 source≡target，需更大重构才能落地，违背"最小改动"原则。

## 三、推荐方案 A：最小修改清单（仅保证流程成立所必需）

1. **`news-append-writer.cjs` 增加门禁（唯一代码改动）**
   - 新增必填参数 `--manifest <approved-manifest.json>`。
   - 写入前 `require('../tools/publish-news.cjs').loadApprovedIds(manifest, allowPath)` 校验：`reviewer_trust==='allowlist'` + 逐条证据（审核人/时间/来源）+ 白名单。
   - 对预览每个 `item.id` 做 `reconcile`：必须全部命中批准集合，否则拒绝（覆盖"预览/映射不同批次"风险，因 id 必在批准清单中）。
   - 可选 `--news-js`（仅测试用，默认生产路径），用于隔离验收。
2. **收敛写入口唯一性（不改代码，仅明确用途）**
   - 正式发布只走 `news-append-writer`（带门禁）。
   - `publish-news.cjs` 保留为**结构校验/门禁逻辑库**（其 `loadApprovedIds` 被复用），其 `--publish` **不再用于真实写入**（软链下门禁失效）。不删除文件。
3. **既有工具保留**：`deliver-and-map.cjs`（preview+map，同源单次转换）、`export-approval-manifest.cjs`（批准清单）、`gate-review.cjs`、`captures-to-candidates.cjs`、`delivery-converter.cjs`、`run-g9-write.cjs`（冻结禁用）。
4. **不新增**任何工具、测试框架、文档或阶段。

## 四、日常更新步骤（使用者视角）

| 步 | 操作 | 人/自动 |
|---|---|---|
| 1 采集 | cron `production-capture`（capture-only） | 自动 |
| 2 生成候选+AI 整理 | `captures-to-candidates` + `delivery-converter` | 可脚本化（自动） |
| 3 人工审核 | `gate-review approve`，**真实 operator 署名** → `review-history` | **必须人工**（不可自动化） |
| 4 预览+映射 | `deliver-and-map --candidates` | 接 2/3 产物（自动） |
| 5 批准清单 | `export-approval-manifest --history --map --allowlist` | 自动 |
| 6 发布 | `news-append-writer --preview --manifest --operator` | **人工触发**（带门禁+双备份） |
| 7 验证 | 比对线上 count/SHA + `curl` 实时 URL 抽查 | 可半自动 |

> 步骤 2/4/5 可由一个编排脚本在"步骤 3 完成后"一键执行；步骤 1 已自动；步骤 3、6 是人工审核与发布授权，不可省略。

## 五、一次性验收方法（隔离测试矩阵，实施后执行）

均使用生产 `news.js` 的**临时副本**（经 `--news-js` 指向），不碰生产：

1. **正常发布**：合成候选 → `deliver-and-map` → `export`（有效白名单+证据）→ `news-append-writer --manifest` 写入副本 → 断言新增条目数正确、生成 `.bak-*`、SHA 变更、vm 结构有效。
2. **未批准拒绝**：`news-append-writer` 不带 `--manifest`（或 manifest 缺该 id）→ 断言退出非 0、**未写盘、无新备份**。
3. **写入失败不破坏原数据**：制造结构非法预览或 `--expect-sha` 不匹配 → 断言拒绝且**不产生新备份、不替换**（依赖已有双备份+SHA 前记录，已 4 次生产实跑 + 自检证明）。
4. **成功后结果可核验**：写后重算 SHA/length + vm 结构校验通过。

## 六、回滚方式

- `news-append-writer` 每次写入自动生成两份备份：`/www/wwwroot/mcu-h5/data/news.js.bak-<ts>`（同目录）与 `…/pipeline/review/backup/news.js.<ts>`。
- 回滚：`cp <备份> /www/wwwroot/mcu-h5/data/news.js`（因软链，写任一侧即生效）。
- 幂等守卫保证同一 `run_id` 重复执行被拒，避免二次污染。
