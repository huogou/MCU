## 1. 当前审核身份来源及可信度结论

- **来源核查**：`pipeline/tools/gate-review.cjs` 的 `operator` 完全来自运行者输入的 `--operator <审核人>` 参数（`gate-review.cjs:156-159`、`review-actions.cjs:55` 仅校验非空），**既不是系统登录身份，也不是可信配置，更不是密码学凭据**——任何人都可填入任意字符串。
- **P2-B1 局限**：原仅"非空 + 黑名单（simulated/ai/rule/system/g7-reviewer）"，不能证明审核人真实存在或确为授权审核者。
- **P2-B1.1 结论**：本环境（root 登录的 ECS，无 SSO/LDAP/审计账号）**无法提供可靠身份凭据**。因此采用**可信审核人白名单**作为带外维护的信任锚：白名单由项目负责人在 `pipeline/review/trusted-reviewers.json` 显式登记授权审核者；导出工具要求审核人必须命中白名单（且仍须过黑名单）。
- **如实标注**：本机制是**流程级信任控制，不是密码学身份验证**。清单与日志均显式标注 `reviewer_trust: 'allowlist'`；本报告明确声明"未声称身份真实性已通过密码学验证"。白名单缺失/为空时，任何"看似人工但无法核实"的审核人一律阻断（fail closed）。
- **现状**：`trusted-reviewers.json` 尚未建立（真实 `--check` 已浮现 WARN），故当前真实导出会被身份校验阻断——这是正确的安全默认。

## 3. 映射持久化方案及示例

### 3.1 缺口
`delivery-converter.cjs:267` 生成的 `id_assignments = [{from_candidate, to_delivery}]` 仅存于返回值，**从未落盘**；`run-g9-write.cjs` 仅内联消费一次；news.js 记录不含 `candidate_id`。故"候选 id ↔ 最终 news id"关系在系统中丢失，审计/发布无法可靠追溯。

### 3.2 方案（最小改动、纯新增）
新增 `delivery-id-map.cjs`，在交付步骤产出 `id_assignments` 后调用，将其持久化为标准映射文件：
```json
{
  "schema_version": "1.0",
  "generator": "delivery-id-map",
  "version": "1.0",
  "generated_at": "2026-10-19T08:02:24Z",
  "source": "delivery-converter.toDeliveries:<candidates.json>",
  "note": "候选↔最终 news 映射持久化；供 export-approval-manifest.cjs --map 读取。",
  "assignments": [
    { "candidate_id": "cand-a", "news_id": "news-2026-10-19-001", "title": "…" },
    { "candidate_id": "cand-b", "news_id": "news-2026-10-19-002", "title": "…" }
  ]
}
```
- 两种输入：`--candidates <approved.json>`（经转换器取 `id_assignments` 并附 `title`）或 `--assignments <file>`（直接落盘既有 `id_assignments`）。
- **可追溯链**：映射 `candidate_id` → `review-history.json` 的同 `candidate_id`（审核记录）→ 审核动作/审核人/时间；映射 `news_id` → 发布数据源中真实存在的记录。三者经此关联。
- 接线位置：后续真实 G9/交付步骤在调用 `toDeliveries` 后追加 `delivery-id-map.cjs`（避免改动冻结的 `run-g9-write.cjs`，本轮未接）。

### 3.3 导出侧强制校验
`export-approval-manifest.cjs` 经 `--map` 读取后：
- 加载即校验：候选重复、一个候选→多 news、多候选→同 news（冲突）→ **阻断导出**并说明原因；
- 每条解析出的 `news_id` 必须格式合法（`^news-\d{4}-\d{2}-\d{2}-\d{3}$`）且**确实存在于本次待发布数据源**（`--source`，默认 `PROD_SOURCE`）→ 不存在则阻断（"目标 news_id 不存在于本次待发布数据"）；
- 缺失映射、模糊匹配一律阻断，无猜测/静默匹配。

## 6. 尚未解决的真实性或追溯限制

1. **身份凭据缺失**：环境无 SSO/审计账号，白名单为流程级信任锚而非密码学身份；白名单本身须由负责人线下维护并妥善保管。

3. **映射未真实落盘**：`delivery-id-map.cjs` 已就绪，但真实 G9/交付步骤尚未接线调用，故真实 `id_assignments` 仍未持久化。
4. **真实上游产物全缺**：真实 G9 候选（当前仍 50 条 mock）、人工审核通过记录（真实 `operator`）、以 `news-` id 为键的批准清单、去重/剧透/关联实体核查、工作区≡生产基线确认、正式发布授权、发布后三页面验证——均缺失，真实首发仍阻塞。
5. **不得伪造**：历史 `review-history.json`（12 条 `simulated-g7-reviewer`）不得转为正式证据；不得生成虚假审批记录或声称已获准上线。

## 附：安全边界复核（P2-B1.1 指令）

- 历史模拟记录不转正式证据；不伪造审核人/时间/动作。✅
- 清单含 `reviewer_trust` 与 "导出≠发布授权" 明示；未声称身份密码学验证。✅
- 不碰生产、不发布、不删 mock。✅
