## 7. 重点检查结论（8 项）

1. **重复执行 / 重复 AI 调用**：❌ 存在。`captures-to-candidates.cjs` 每次运行都对整个 `batch` 串行调用 AI，**无 AI 结果缓存**。本次同日重跑即产生 20 次 AI 调用、16 条 conflict。应在编排层用 `registry_id|content_hash` 比对已有候选，只把未处理的 capture 送入 AI。
2. **同批次重复处理或覆盖**：✅ 候选归档不会覆盖（append-only + 备份实证 `ids_identical=true`）；❌ 但 `export` 的 `writeManifest` 与 `deliver-and-map` 的输出文件可被同名 run_id 覆盖，`news-append-writer` 靠 state 幂等保护，缺统一批次锁。
3. **审核记录路径分裂**：❌ `gate-review` 写 `candidates/review-history.json`（54 条真人记录）；`publish-news.DEFAULT_MANIFEST` 与 `export` 默认 `--history` 指向 `review/review-history.json`（12 条模拟记录）。不显式指定会读错文件。
4. **历史记录污染当前批次**：❌ `--history` 全量读取会把 10 月历史 approve 记录一并校验，因缺本轮 map/news_id 或目标不在合并源而**整批阻断**；当前靠人工构造 `--records` 规避。
5. **每次手动指定参数**：❌ `--records` / `--map` / `--source` / `--allowlist` / `--out` / `--run-id` / `--expect-sha` 全部靠人工拼装，且参数间必须严格对应，是主要人工负担。
6. **多个发布入口与旧 RUNBOOK 误导**：❌ `publish-news.cjs --publish` 仍在 CLI 中（`:403`），但 `PROD_SOURCE`≡`PROD_TARGET`（h5 软链）导致 diff 恒 0、门禁被架空；`run-g9-write.cjs` 为硬编码冻结件；`PUBLISH-RUNBOOK.md` 仍以 `--publish` 与 `.bak-pub-*` 为准，与实际 `news-append-writer`（`.bak-<ts>`）不一致。
7. **输入输出/失败处理一致性**：❌ 不统一。5 个工具有 `require.main === module` 守卫可复用（`captures-to-candidates` / `deliver-and-map` / `delivery-id-map` / `export` / `publish-news`），`gate-review` 与 `news-append-writer` 无守卫（被 require 即执行 main）；错误风格混用 `fail(code)` / `die()` / `exitCode=2` / `log(ERROR)`；`parseArgs` 每个工具各写一份。
8. **重复代码 / 可复用逻辑**：白名单加载（`publish-news.loadPublishAllowlist` 与 `export.loadAllowlist`）、`ISOT_RE` / `NEWS_ID_RE`、`nowIso`、`review-history` 读取与字段映射、`parseArgs`、SHA/备份、审核人真实性判定在多个文件重复实现。

**批次 ID**：`batch-<date>-<输入归档 SHA 前 8 位>`，写入 `status/batches/<batchId>.json`（记录输入/各阶段产物的绝对路径与 SHA、开始结束时间、阶段状态、AI 调用数、错误列表）。

| R0 | 读取批次清单，确认该批次存在真实人工审核记录；**统一从 `candidates/review-history.json` 读取**，按本批次 candidate_id 集合过滤，自动隔离历史记录 |
| R1 | 校验 `isGenuineHuman` + 白名单精确匹配 + `reviewed_at` + `source`；生成 `records-<batchId>.json` |
| R2 | 从 `candidates/<date>.json` 提取 approved 纯数组 → 调 `deliver-and-map` 产出 preview + map（自动分配唯一 run_id） |
| R3 | 构造合并校验源：生产 `news.js` 的 id 集合 + preview 全部 id |
| R4 | 调 `export-approval-manifest`（先 `--check`，通过后正式导出） |
| R5 | 发布前完整性检查：preview 33 字段、manifest 与 preview id 一一对应、`news.js` SHA 基线、run_id 未被使用、白名单/证据齐备 |
| R6 | 输出「发布授权单」`review/release-authorization-<batchId>.json`（含各产物 SHA、基线 SHA、待授权状态） |

**边界**：**绝不自动执行 `news-append-writer`**。最终发布由负责人在确认授权单后显式执行（可提供 `tools/release-news.cjs --batch --authorization <path> --operator <负责人>`，但该命令必须校验授权单存在且未使用，且仍由人触发）。

### 9.6 自动化后实际操作步骤（设计）

1. `node tools/run-news-batch.cjs --date 20261106 --limit 20` → 得到批次 ID 与审核清单。
2. **真人**在审核清单上逐条决策（仍走 `gate-review approve/reject`，operator 为白名单内真实人；此步不可自动化）。
3. `node tools/prepare-news-release.cjs --batch <batchId>` → 产出 preview/map/manifest/授权单。
4. **负责人**确认授权单，显式执行发布命令（不在编排内自动触发）。
5. 统一验证与（必要时）回滚。

### 9.7 每批人工参与次数

**3 次**：① 触发批次生成（1 条命令）；② 真人审核（一次审核流程，逐条决策，不可由 AI 代替）；③ 负责人授权发布（1 条命令）。相比现行约 12 类、且参数需手工传递的命令，人工**指令数**从约 12 降至约 3 条（审核决策条数随候选数量变化，但由统一清单驱动）。

### 9.8 改造成本与潜在风险

- **成本**：中低。新增 2 个编排工具 + 1 个共享配置 + 1 套测试（约 300–400 行），不修改冻结件；文档与旧入口禁用各 1 处。
- **风险**：
  - AI 幂等键若与 `candidate-store` 的 `registry_id|content_hash` 不一致 → 漏生成或重复生成；
  - 批次 ID 只按日期会在重跑/跨批次时混淆（须带输入 SHA）；
  - 审核记录按 candidate_id 过滤时，同 capture 不同 seq 会产生不同 id → 必须以批次审核清单为准并记录批次 ID；
  - 合并源必须包含 preview 全部 id，否则 export 阻断；
  - 新入口若被误加发布动作会绕过授权 → 发布必须与编排物理分离且校验授权单；
  - 旧 `publish-news --publish` 未禁用前仍可能被误用；
  - 统一审核路径迁移若改动 `gate-review` 写入逻辑，可能影响现有 54 条历史记录的可追溯性（建议保持其写入不变，仅统一读取端）。
