## 3. `credibility` 字段定义与推导证据

### 3.1 正式允许值
- **枚举 = `high | medium | low`**（三值），**不是** `official/media/rumor`。
- 证据：`news-analyzer.config.cjs:25,32` 注释与 `credibility:{tierMap,thresholds:{high:3,medium:2}}`；`news-analyzer.cjs:56` `credibility ∈ {high,medium,low}`。

### 3.2 每个值的含义与推导（纯来源分级 + 多源印证，与内容是否官方无关）
- 推导函数 `deriveCredibility(ctx)`：`news-analyzer.cjs:57-68`。
  - `score = tierMap[tier]`（`T1:3 / T2:2 / T3:1 / '':1`）。
  - 若 `source_type==='official'` 或 `is_official` → `score = max(score, officialFloor=2)`。
  - 若 `reportCount >= multiSourceReportCount(2)` → `score = max(score, 2)`。
  - `score>=3→high`；`>=2→medium`；否则 `low`。
- **关键结论**：`credibility` 衡量**来源可靠度/多源印证**，从不因"内容涉及官方事实"而升高；也不建立"官方确认=high"映射（`news-analyzer.cjs:19`）。

### 3.3 来源等级、独立源数量、多源印证如何影响
- 来源分级来自 `engine/registry/source-registry.json` 的 `tier`：`S002 The Direct = T3`、`S004 Variety = T2`、`S006 迪士尼官方 = T1`（source-registry.json:39,83,127）。
- 单源 T3（The Direct）→ score=1 → **low**；单源 T2（Variety）→ 2 → **medium**；官方 T1（S006）→ 3（且 official floor 不影响）→ **high**。
- 多源（`reportCount>=2`）→ 至少抬到 medium。

### 3.4 是否存在"官方公告 → high"规则？**没有。**
- 仅有 `officialFloor=2`（medium）的抬升（`news-analyzer.config.cjs:27,34`）。官方来源不会自动 high，内容是否官方更不进入该字段。

### 3.5 是否存在独立的 `source_type` / 来源类型字段区分官方/媒体/传闻？
- **有 `source_type` 与 `official_or_media`**：`source-registry.json` 每条含 `source_type`（"官方"/"公告平台"/"权威媒体"/"MCU垂直媒体"）与 `official_or_media`（"official"/"media"）。用于来源分级与官方判定。
- **但表达"官方公告/媒体报道/传闻/粉丝推测"的是 `verification_status`（8 态）与 `ai_suggested_status`（8 态建议值）**，二者才承载内容确认度：
  - `ai_suggested_status` 枚举（`candidate-item.cjs:61-64`）：`official_confirmed / multi_source_reported / single_source / rumor / unverified / conflicting / officially_denied / corrected`（AI 仅给"建议值"）。
  - `verification_status`（最终状态，由 `engine/news-judge.cjs:373` 按 R8.3 计算；基线测试确认"全部为 8 态之一"）写入发布记录（见 h5-news.js:56）。
  - `event-merger`/L1/AI 层**禁止产出** `verification_status`（`candidate-item.cjs:19-23,77-84`、`engine/dedup/event-merger.cjs:10`）。

### 3.6 `gate-review` 对不同 `credibility` 的处理
- `gate-review.cjs` **不读取/不依赖 `credibility`**；它只按 `gate_status` 过滤 + `CI.validate` 做 schema 校验（`gate.cjs:27-49`）。`credibility` 仅影响 `recommend` 信号（`news-analyzer.cjs:71-77`，`credibility!='low' && confidence>=0.6 && hasCat && hasRel`），而 `recommend` 不进 H5、不做前端标签（`news-analyzer.cjs:16-19`）。

### 3.7 候选转换/关联约束/持久化之间实际执行的校验
- **候选转换**（`captures-to-candidates.cjs:116`→`CI.fromRawCapture`）：执行 `idSpace` **软过滤**（缺失实体静默丢弃，见 §4）。
- **关联约束**（`id-space.cjs`）：`constrain`/`validateRelated` 在本链路中由 `captures-to-candidates` 调用（非 gate/delivery）。
- **持久化**（`run-g9-write.cjs`）：仅做文本追加与 SHA/VM 重载断言，**不重新校验实体存在性**（缺失实体早已在 L1 被清空）。

### 3.8 对 #5 的建议值（前序报告错误已修订）
- #5 来源 = The Direct（`source_type=MCU垂直媒体`、`official_or_media=media`、`tier=T3`）。
- 若经分析器：`credibility=low`（单源 T3，无多源）。**但 `credibility` 不写入发布记录**。
- 发布记录中应以 **`verification_status`** 表达确认度：海报由漫威官方社媒发布（2026-10-03），但 `source-registry.json:11` 明确"**官方社交账号（X/IG/YouTube）无法做域名与路径校验，同样不得单独构成 official_confirmed**"。因此 #5 **不应**置 `official_confirmed`，建议 `single_source`（若仅有 The Direct 一篇）或 `multi_source_reported`（若有第二独立源印证）；"官方海报发布"这一事实写入 `summary` 与 `official_source` 字段，而非 `credibility` 或谎称 `official_confirmed`。
- **不得**创建 `official` 枚举，也**不得**把媒体来源的某条官方事实自动等同于整条资讯 high/官方确认。

## 4. 真实调用链与硬校验/软过滤矩阵

**实际链路**（代码证实，非套用模板）：
`L0 captures → NA.analyzeCandidate（AI：7 字段 + 扩展 credibility/confidence/recommend；不约束实体、不置 verification_status）→ CI.fromRawCapture（L1：idSpace 软丢弃 + 35 字段 schema 校验）→ CandS.appendCandidates（pending）→ gate-review（人审 approve/reject → GATE.review 按 gate_status 过滤）→ delivery-converter.toDeliveries（33 字段投影）→ run-g9-write（写入 h5/data/news.js）`

| 阶段 | 函数（证据） | 输入 | 关联实体缺失的实际行为 | 是否阻断 | 证据 |
|---|---|---|---|---|---|
| AI 分析 | `NA.analyzeCandidate` | L0+7 字段 | 不校验实体；产出 `credibility`(源分级)/`ai_suggested_status`(8态建议) | 否 | news-analyzer.cjs:57-68；candidate-item.cjs:61-64 |
| L1 构造 | `CI.fromRawCapture`（candidate-item.cjs:128） | raw+AI | `intersect()` 把缺失 id 推入 `discarded`（**静默丢弃，不抛错**）；`related_phases` 过滤 1–6 | **否** | candidate-item.cjs:107-118,166-172 |
| 落盘 | `CandS.appendCandidates`（captures-to-candidates.cjs:134） | L1 | 原样写 pending | 否 | 同上:134-139 |
| G6 闸门 | `GATE.review`（gate.cjs:27） | 候选 | 仅按 `gate_status==='approved'` 过滤 + `CI.validate`（schema）；**不调 id-space、不查实体** | 否 | gate.cjs:27-49；candidate-item.cjs validate 不含实体校验 |
| 交付转换 | `delivery-converter.toDeliveries` | approved | 输入已是清洗后数组，直接投影 33 字段 | 否 | 已读转换器（输入为 L1 已清洗对象） |
| 持久化 | `run-g9-write.cjs:35,199` | DeliveryItems | 文本追加写 `h5/data/news.js`；记录**不含 credibility** | 否（幂等守卫除外） | run-g9-write.cjs:35,93,199 |

**逐项回答任务 3 问题**：
1. 缺失 `related_*` 实体 → **不阻断**整个候选（L1 软丢弃为空数组）。
2. 不存在 → **静默丢弃**进 `discarded` 桶，无报错/警告上抛；非人工审核触发。
3. **空关联数组合法**：`h5/data/news.js:73` 已有 `related_movies:[]` 实例；`CI.validate` 不要求非空（`recommend` 的 `hasRel` 仅影响 recommend 信号，不影响候选合法性与 gate 通过）。
4. `related_phases>6` → 被 `fromRawCapture:170-172` 过滤丢弃，无阻断。
5. `gate-review` **不直接调用**关联校验函数（仅间接触发 L1 已清洗数据）。
6. 转换器**保留**已清洗的关联字段（不恢复、不丢弃）。
7. 持久化**无独立硬校验**（实体存在性）；仅有写入前 SHA 幂等守卫与 VM 重载断言。

**五态区分（务必分清）**：
- `schema 合法`：L1 `CI.validate` 通过（35 字段、category、ai_suggested_status 枚举等）。
- `候选通过审核`：`gate_status==='approved'`（人工）。
- `数据成功写入`：G9 追加写入 `h5/data/news.js` 成功。
- `前端正确显示`：H5 按 `R12.2/12.3` 渲染（空值 UI 规则）。
- `线上已部署`：本工作区为 staging，`h5/data/news.js` 当前为 **mock 阶段**（h5-news.js:14,40），尚未接入真实抓取；线上部署不在本工作区范畴。

## 7. 修订后的发布门槛（替换前序"B 类实体齐备即升 A"）

候选**同时满足**以下条件方可建议进入发布审核（注意：是"建议进入审核"，不等于"批准发布"）：

1. 核心事实有可靠、可追溯证据（官方/媒体原文，非推断）；
2. 与 MCU Atlas 当前内容收录范围一致（含 #9/#70 等边界待策划决定项须先裁定）；
3. 具有独立信息价值（非清单/纯周边堆砌/无意义的营销图）；
4. 不属于重复、明显过期或无意义内容（同事件已发布则去重，如 S006 #15 vs news-2026-10-15-001）；
5. 标题/摘要不把推测写成已确认事实（传闻须标 `rumor`/`unverified`，不写 official_confirmed）；
6. 剧透风险已正确标注（如 #14 高剧透，须 spoiler 标记且默认不发布）；
7. `credibility` 符合现有定义（`high/medium/low`，仅源分级；且不写入发布记录）——`verification_status` 按 8 态由判定器/R8.3 赋值；
8. `related_*` 经实际 idSpace 校验，**或**明确接受空关联的产品损失（缺实体时不阻断，但失去跨链）；
9. 符合现有 schema（`candidate-item.cjs` 35 字段、`category` 6 值、`ai_suggested_status` 8 态）、gate 与 persistence 规则；
10. 最终差异经策划审核。

**哪些由代码自动强制 vs 仅人工保证**（不得声称系统已自动执行未实现规则）：
