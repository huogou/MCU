## 3. 真实交付链路逐环节核查表（§P2）

链路：`真实候选 → delivery-converter.toDeliveries → delivery-preview.json → id-map.json → 人工审核记录 → approved-manifest.json → publish-news.cjs`

| # | 环节 | 实际入口 / 文件 | 输入 | 输出与 ID 对应 | 是否真实调用 | 是否同批 | 失败是否阻断 | 不一致风险 |
|---|---|---|---|---|---|---|---|---|
| 1 | 真实候选 | `gate-review.cjs` approve → `review-history.json` | 待审候选（含 `candidate_id`） | 候选级（35 字段，含 `candidate_id`） | **当前无真实调用**：12 条全 `operator=simulated-g7-reviewer` | — | approve 不阻断交付（仅留痕） | 无 |
| 2 | 转换 | `delivery-converter.cjs:toDeliveries` | 已批准候选数组 | `{items(33字段), report.id_assignments:[{from_candidate,to_delivery}]}`；id=`news-YYYY-MM-DD-NNN` | 历史上由冻结 `run-g9-write.cjs` 调用；现可由 `deliver-and-map.cjs` 调用 | 与 preview/map 同源（见下） | **缺日期 → `MISSING_TIME` fail closed** | 无（确定性） |
| 3 | 交付预览 | `deliver-and-map.cjs`（新）写 `deliveries/<runId>.delivery-preview.json` | `toDeliveries.items` | 33 字段 items + `run_id`/`generated_at` | 新增工具，未接生产 | 同 `toDeliveries` 一次调用 | 转换失败→**不写 preview** | 见 §3 风险 A |
| 4 | 候选↔news 映射 | `deliver-and-map.cjs` 写 `deliveries/<date>.id-map.json` | 同一次 `toDeliveries` 的 `id_assignments` | `{candidate_id, news_id, title}`，`status:ok` | 新增工具，未接生产 | 与 preview **同源单次转换**（P2-B1.3 已加固） | 转换失败→写 `status:failed` 诊断映射 | 见 §3 风险 A |
| 5 | 人工审核记录 | `review-history.json`（candidate 级） | gate approve 动作 | `{review_id, candidate_id, operator, action, reviewed_at, before/after}` | **当前全 simulated**（非真实人工） | 与候选同批 | reject/modify 在导出被排除 | 无 |
| 6 | 批准清单 | `export-approval-manifest.cjs --history/--records + --map + --allowlist` | 审核记录 + 映射 | `approved-manifest.json`（**news-id 级**条目 + `reviewer_trust` + 逐条证据） | 工具可用，未接生产 | 记录(candidate)经 map→news | `status:failed` 映射/白名单缺失/映射重复·冲突/缺映射→**阻断** | 见 §3 风险 B |
| 7 | 发布入口 | `publish-news.cjs --manifest`（P2-A，非冻结） | 完整 news.js 源 + 批准清单 | 结构校验 + diff + 原子替换生产 | 未接真实发布（`--publish` 未执行） | 与源同文件 | 无证据/非白名单/纯 id 列表→**拒绝** | 见 §3 风险 C |

**关键事实**：
- `review-history.json` 以 **`candidate_id` 为键、无 `news_id`**（实测 12 条样本）。要把候选级审核转成 `publish-news.cjs` 要求的 **news-id 级**批准清单，**必须**经 `id-map.json`（`candidate→news`）。这正是 `deliver-and-map.cjs` 持久化映射的目的。
- `news-append-writer.cjs` **只消费 preview（33 字段）、不含 candidate/map**，因此它本身**无法产出**映射——映射只能由 `deliver-and-map.cjs`/`delivery-id-map.cjs` 在转换侧产生。

### §3 三处真实风险（均非冻结件问题，而是软链 + 数据缺口）
- **风险 A（已缓解）**：preview 与 map 若分两次转换可能不一致。→ `deliver-and-map.cjs` 已改为**同源单次 `toDeliveries`** 派生两者（P2-B1.3 加固，P4 T1 双射验证通过）。
- **风险 B（已缓解）**：映射缺失/重复/冲突/失败。→ 导出工具在 `loadMap` 与 `runExport` 全链路阻断（P4 T2/T3/T4/T5/T6 验证）。
- **风险 C（未缓解，需策划决策）**：`h5` 软链→`mcu-h5`（同一 inode），`publish-news.cjs` 的 `PROD_SOURCE` 与 `PROD_TARGET` 是**同一文件** → diff 恒为 0，其审批门禁在软链现实下**被架空**；而真正写生产的是 `news-append-writer.cjs`，它**不校验批准清单**。因此若直接走 `news-append-writer`，P2-B1.2 加固的发布门禁可被绕过。→ 见 §4 接线方案的两种改法。

## 4. 不修改冻结 G9 的接线方案及其限制（§P3）

### 4.1 可行性
- 冻结件 `run-g9-write.cjs` 仅负责"内部调用 `toDeliveries` 生成 preview + 写工作区"，其职责可由**非冻结**的 `deliver-and-map.cjs`（preview+map）+ `news-append-writer.cjs`（写盘）+ `export-approval-manifest.cjs`（approved-manifest）+ `publish-news.cjs`（门禁+替换）组合覆盖。**无需改 G9、Scheduler/Orchestrator/Provider/Gate/测试/H5/news.js。**
- 调用顺序（建议）：
  1. `deliver-and-map.cjs --candidates <approved>.json --run-id <id>` → 产出 `deliveries/<id>.delivery-preview.json` + `deliveries/<date>.id-map.json`（同源）。
  2. `news-append-writer.cjs --preview <preview> --operator <授权人>` → 写生产（经软链）。
  3. `export-approval-manifest.cjs --history review-history.json --map <id-map> --allowlist trusted-reviewers.json --source <生产> --out approved-manifest.json` → news-id 级批准清单。
  4. `publish-news.cjs --manifest approved-manifest.json --publish` → 门禁 + 原子替换。

### 4.2 接口 / 字段 / ID 一致性（已验证）
- `deliver-and-map.cjs`：`--candidates/--preview-out/--map-out/--run-id/--now`；preview 用 `out.items`、map 用 `out.report.id_assignments` 派生 → **同一 `toDeliveries` 结果**，ID 必然一致（P4 T1 双射 PASS）。
- `news-append-writer.cjs`：`--preview --operator(必填) --expect-sha(可选)`；消费 33 字段 items，要求 `--operator`（发布授权人），有 SHA 前记录 + `--expect-sha` 基线比对（fail closed）+ 双备份 + 字节级 + vm + 幂等。
- `export-approval-manifest.cjs`：`--records/--history --map --allowlist --source --out --check`；输出 news-id 级条目 + `reviewer_trust` + 逐条证据。
- ID 一致性保证：preview 与 map 同源单次转换 → 预览中的 `news_id` 恰为 map 的 `to_delivery`，导出经 map 把 candidate 级审核 join 到该 news_id，publish 门禁再核对每个新增 news_id 是否命中批准集合。

### 4.3 必须解决才能接线闭环的两项（非冻结，待策划拍板）
- **改法一（推荐，改 `news-append-writer.cjs`）**：让真实写生产的 `news-append-writer.cjs` 也要求并校验 `--manifest`（复用 `publish-news.cjs` 的 `loadApprovedIds` 门禁）。这样无论软链与否，写盘即受批准约束，P2-B1.2 门禁不再可绕过。改动范围：`news-append-writer.cjs`（非冻结）增加 `--manifest` 入参与校验，不触碰 G9。
- **改法二（改 `publish-news.cjs`）**：把 `publish-news.cjs` 设为唯一生产写者，新增可配置 `--source/--target`，先落 staging news.js 再替换生产；需先处理软链（断开软链或让 staging 与 production 分离）。改动范围：`publish-news.cjs`（非冻结 P2-A）增加 source/target 参数。

> 两项均**不修改冻结 G9**，但都涉及"真实发布路径"的改动，按纪律须策划验收后再实施（§5 待批准项）。

### 4.4 阻塞原因小结
- 接线**设计已验证可行**且工具齐备，但**尚未接入生产**（真实 G9 仍冻结、写入器未接门禁、软链使门禁架空）。
- 更根本的阻塞是**数据/证据缺口**：无真实 `review-history`（全 simulated）、无 `trusted-reviewers.json`、无真实 G9 候选——即便接通，也没有可发布的真实批准记录。
