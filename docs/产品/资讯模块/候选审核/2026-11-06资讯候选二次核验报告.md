## 三、来源覆盖问题分析（S004 / S006 为何未进入候选）

### 归档实测（`captures/20261106.captures.json`）

### 代码检查结论

| 检查项 | 结论 | 证据 |
|---|---|---|
| 脚本是否只读取 S002 | **否**（代码层完全没有来源选择）；但实际效果等同只读 S002 | 服务器 `tools/captures-to-candidates.cjs` 中 `grep -n registry_id` **无任何输出**；`:85 const batch = captures.slice(0, limit)` |
| S004 / S006 是否被过滤 | **否** | 全链路无 `registry_id` / 来源白名单判断；`capture-store.cjs:90,98` 原样 push；`candidate-item.cjs:175` 只用 `source_name` 查 `owner_group`；`candidate-store.cjs` 去重键含 `registry_id` 但不因来源跳过 |
| 是否存在来源数量限制 | **否** | 采集默认源 `DEFAULT_CAPTURE_SOURCES=['S002','S004','S006']`；`LIVE_ALLOWED`（`base-collector.cjs:205`）包含三者；本日 130 条三源齐全 |
| 是否存在条数限制 | **有，且是根因** | `tools/captures-to-candidates.cjs:65` `Math.min(Math.max(a.limit || 3, 1), 20)` 硬顶 20；`:85` 取数组**前 20 条** |
| 关键词 / 分类过滤导致官方资讯遗漏 | **无条目级过滤** | `dashscope.cjs:47-59` 的 system prompt 无「只保留 Marvel」类指令；`candidate-item.cjs:151-154` 仅校验 category 6 值合法性（6 类全放行） |
| 采集顺序为何固定 | 分组串行 | `base-collector.cjs:205,231-251` 按固定源顺序逐源采集、逐段落盘；归档实测 S002 恒在最前 |

**根因判定**：`--limit 20` 恰好等于首个 S002 段长度（20 条），前缀截断使 S004（index 20..29）与 S006（index 30..129）**从未进入 AI 环节**。这不是过滤 bug，而是「按数组位置取样 + 小批量护栏」与「按来源分组落盘」叠加产生的覆盖盲区。

### 补充：信息层面的遗漏风险（非条目过滤）

`ai-provider/projection.cjs:16` 出域白名单只有 `['title_raw', 'raw_excerpt']`，`source_name` / `source_url` / `published_at` / `url_level` 全在 FORBIDDEN 中；`dashscope.cjs:55` 仅要求 `related_*` 为「字符串数组、未知用 []」。因此 AI：

- 看不到来源名称，**无法区分迪士尼官方公告与 The Direct 媒体稿**；
- 看不到发布时间，**无法判断公告是否为旧闻**；
- 看不到 URL，**无法核实官方出处**。

这不会让条目被丢弃，但会系统性降低官方资讯的识别质量，并与 S006 历史列表叠加放大旧闻风险。

### 根因链（不是"实体缺失"）

2. AI 只能输出自然语言名称（如 `Avengers: Doomsday`、`VisionQuest`、`Thanos`、`幻视`、`托尼·斯塔克`）。
3. `candidate-item.cjs:106-118` 的 `intersect()` 用 `space.has(v)` 对**项目内部 id**（如 `doomsday`、`visionquest`）精确匹配 → 自然语言名全部落入 `discarded`。
4. `candidate-item.cjs:209-231` 仍完整产出 35 字段条目，`id-space.cjs:13` 明确「不存在 → 删除关联、不删条目」。因此**只影响关联字段，不影响候选条数**。
