## 1. 实施前现状核查结果（只读）

1. **现有审核链路**：`pipeline/tools/gate-review.cjs` 是人工审核唯一操作入口 → `pipeline/review/review-actions.cjs`（`applyDecision`）→ 追加写 `pipeline/review/review-history.json`。审核动作仅 `approve/reject/modify`，**必须人显式输入**（`gate-review.cjs:13-18`）。
2. **review-history.json 真实结构**：`{ schema_version, entries[], updated_at, count }`；每条 `entries[i]` = `{ review_id, event_id, candidate_id, operator, action, before, after, reason, created_at }`（review-actions.cjs:97-108）。
3. **publish-news.cjs 当前 `--manifest` 解析逻辑**（`loadApprovedIds`）：接受 `approved_ids` 数组，或 `entries[]`/`顶层数组` 中 `action==='approve' || status==='approved' || approved===true` 且带 `id`/`news_id`/`delivery_id` 的记录。
4. **候选 ID 与最终 news- ID 生成/映射**：
   - 候选 id（`candidate_id`，如 `cand-…`）由采集/签名层生成；最终 id（`news-YYYY-MM-DD-NNN`）由 `delivery-converter.cjs` 在转换时生成（`delivery-converter.cjs:9-12, 130-154`）。
   - **关键缺口**：`candidate_id` 是管道禁入字段，**不进入 DeliveryItem，也不写回 news.js 记录**（`delivery-converter.cjs:23-25, 50-59`）；其映射仅短暂存在于转换器返回的 `report.id_assignments`，**未被任何环节持久化**。news.js 记录本身**不携带 candidate_id**。
   - 因此：系统**未持久化 candidate→news 映射**，自动化地从候选级审核记录导出 news-id 键清单在当下不可行，必须显式提供映射。
5. **可复用的审核记录/入口/导出工具**：`gate-review.cjs` 的 `decisions` 子命令可导出 `approved` 候选决策（`gate-review.cjs:208-220`），但其输出仅含 `candidate_id`，**无 news- id**；`review-history.json` 是唯一留痕，但当前内容为 **2026-09-23 模拟数据**（`operator: simulated-g7-reviewer`，12 条：1 reject / 1 modify / 10 approve），**非真实人工批准**。

## 3. 批准清单格式与 ID 映射规则

### 3.1 人工审核记录最小字段（输入）
- `candidate_id`：选填，用于追溯（若系统仅有候选级证据）。
- `news_id`：**必填**，最终资讯 id，须匹配 `^news-\d{4}-\d{2}-\d{2}-\d{3}$`。
- `action`：**必须 `approve`**（reject/modify/pending 一律不进入清单）。
- `reviewer`（或 `operator`）：**必填、非空、且为可验证人工来源**——不得是 `simulated*` / `ai_*` / `rule_*` / `system` / `auto` / `g7-reviewer`（即 `simulated-g7-reviewer` 类）。
- `reviewed_at`（或 `created_at`）：**必填**，ISO 时间。
- `source` / `record_version`：选填，用于可追溯。

### 3.2 ID 映射规则（强制明确，禁止猜测/静默匹配）
- `news_id` 为权威键；若记录已显式带 `news_id` 且格式合法，直接使用。
- 若记录仅带 `candidate_id` 而无 `news_id`，**必须**通过 `--map` 提供显式 `candidate_id → news_id` 映射文件；解析不到即视为“映射不明确”，**阻断导出**。
- 既不带 `news_id` 也无 `--map` → 阻断导出。

### 3.3 导出清单格式（输出，兼容 publish-news.cjs）
```json
{
  "schema_version": "1.0",
  "generator": "export-approval-manifest",
  "generated_at": "<ISO>",
  "generated_by": "<运行者>",
  "note": "批准清单导出≠发布授权。须经 publish-news.cjs --manifest 经人工确认后发布。",
  "entries": [
    { "id": "news-…", "candidate_id": "cand-…", "action": "approve",
      "reviewer": "…", "reviewed_at": "…", "source": "…", "record_version": "…" }
  ]
}
```
`publish-news.cjs` 通过 `entries[].action==='approve'` + `e.id` 识别，与自检中真实调用 `loadApprovedIds` 验证一致。

## 4. 测试场景、实际结果和失败案例

`--self-test`（独立临时目录，不碰生产）**12/12 PASS**，退出码 0。关键场景：

| 场景 | 预期 | 实际 |
|---|---|---|
| 有效人工批准（2 条，显式 news_id） | 导出 2 条、退出 0 | PASS |
| 导出清单能被 publish-news.cjs `loadApprovedIds` 真实解析并命中 2 条 | 命中 | PASS（真实 require 调用） |
| 模拟审核（`simulated-g7-reviewer`） | 不进入清单 | PASS（排除） |
| reject | 不进入清单 | PASS（排除） |
| 缺失审核人 | 阻断（退出 2、不写文件） | PASS |
| 缺失最终资讯 ID 且无法映射 | 阻断（退出 2） | PASS |
| 重复 news_id | 阻断（退出 2） | PASS |
| 格式错误 news_id | 阻断（退出 2） | PASS |
| 空清单 → 发布将因无批准被拒 | 命中 | PASS |
| 导出不触碰生产 | 成立 | PASS |

**真实数据 `--check` 跑测**（默认读取真实 `review-history.json`）：12 条全部被排除（1 reject、1 modify、10 模拟 approve），**可批准 0 条**，退出 0，**未写入任何文件**。这实证了缺口：现有审核证据不能构成正式批准清单。

## 5. 真实人工审核证据是否已具备

**未具备。** 证据：
- `review-history.json` 12 条全部 `operator: simulated-g7-reviewer`（2026-09-23 模拟演练），非真实人工。
- 系统未持久化 `candidate_id → news_id` 映射，且 news.js 记录不含 `candidate_id`，无法自动把候选级审核对应到最终 news- id。
- 因此导出工具在真实数据上产出**空批准清单**——这是正确的“fail closed”行为，而非伪造通过。

## 6. 目前仍有的上游阻塞项

1. **真实人工审核记录缺失**：须由人工审核环节以真实 `operator`（非 `simulated-*`）运行 `gate-review.cjs approve`，使 `review-history.json` 出现可验证的人工 `approve` 条目。
2. **candidate→news 映射未持久化**：`delivery-converter.cjs` 的 `id_assignments` 未被落盘；news.js 记录不含 `candidate_id`。须补充机制：或在批准步骤记录 `news_id`，或由交付步骤持久化 `id_assignments` 供 `--map` 使用。
3. **正式批准清单产出物缺失**：须由人工审核环节产出显式 `approval-records.json`（每条带 `news_id`/`reviewer`/`reviewed_at`），或确保审核记录自带 `news_id`。
4. 上述 1–3 齐备后，方可运行 `export-approval-manifest --records/--history+--map` 得到非空 `approved-manifest.json`，进而由 P2-A 的 `publish-news.cjs --publish --manifest` 发布。

## 8. 下一阶段开展真实首发候选准备的必要条件

1. 真实 G9 产出（工作区 `news.js` 含真实候选、并已分配最终 `news-` id）。
