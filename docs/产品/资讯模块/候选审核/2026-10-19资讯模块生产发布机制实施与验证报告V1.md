## 2. 发布脚本设计与安全边界

脚本 `publish-news.cjs` 以 Node.js 实现，覆盖需求 A 全部 13 项：

| 需求 | 实现要点 |
|---|---|
| 1/2 固定源/目标 | `PROD_SOURCE`/`PROD_TARGET` 硬编码；生产模式不接受任意路径参数（仅 `--manifest` 可选） |
| 3 发布前预检 | `parseNewsFile` 用 vm 沙箱提取 `window.MCU_NEWS_META` 与 `window.MCU_NEWS`；缺失即报错 |
| 4 结构校验 | `validateStructure`：33 字段存在性、`id` 格式 `^news-\d{4}-\d{2}-\d{2}-\d{3}$`、全局 id 唯一、`verification_status` 8 态、`related_phases∈1-6`、`reported_by`/`pinned` 等类型；**实际修正**：真实已发布记录的 `chain_steps_hit` 为**字符串**（如 `'Step 1'`）而非数组，脚本已改为接受 `string|array` |
| 5 结构≠事实审核 | 每次校验后打印"结构校验通过（≠事实审核通过，需独立审核清单）" |
| 6 审核证据 | `loadApprovedIds`：默认读取 `review-history.json`，但实测其为 2026-09-23 模拟审核产物（`operator: simulated-g7-reviewer`），且以 `candidate_id` 为键，不能直接作为发布批准清单；**正式 `--publish` 必须显式提供以最终 `news-` id 为键的 `--manifest`**，否则拒绝 |
| 7 差异与默认禁止删改 | `diffRecords` 列出新增/删除/变更；默认**禁止删除/修改既有线上记录**，检测到即停止等待人工批准 |
| 8 唯一备份 | `backupTarget` 生成 `<target>.bak-pub-<ISO时间戳>` 并验证可读 |
| 9 原子替换 | `writeTmpAndReplace`：同目录写 `.tmp` → 继承目标权限 → `renameSync` 原子替换 |
| 10 生产校验 | `verifyTarget` 比对记录数与 id 集合 |
| 11 失败回滚 | 替换后校验失败 → `rollback` 恢复备份并验证 |
| 12 dry-run | `--dry-run` 只读/校验/差异，不备份、不写入、不发布 |
| 13 退出码/日志 | 退出码 0/1/2；日志含时间戳+级别；版本标识 `pub-<时间戳>-<N>rec`；不记录任何密钥 |

## 3. 审核证据核对方式

- 发布输入为 G9 产出的 `news.js`，其中 `judged_by`（human_confirmed/rule_validated/ai_suggested）**不能替代人工发布审批**。
- 流水线现有 `pipeline/review/review-history.json` 为对象结构 `{schema_version, entries[], updated_at, count}`，`entries[].action` 多为 `reject` 且为模拟数据，**不可直接消费**。
- 因此脚本要求：正式发布时由人工审核环节产出**独立批准清单**（文件，含 `approved_ids` 或 `entries[].action==='approve'` 且以最终 `news-` id 为键），经 `--manifest` 传入；每条新增记录必须命中批准清单，否则拒绝发布。

## 5. nginx 配置变更、语法检查、reload 与响应头验证（Task B）

- **变更内容**（三份 vhost 完全一致）：在 443 主站 server 块内、通用 `.js` 缓存规则**之前**插入：
  ```
  location = /data/news.js {
      add_header Cache-Control "no-cache, must-revalidate";
      add_header Expires "0";
      add_header Strict-Transport-Security "max-age=31536000" always;
  }
  ```
  `=` 精确匹配优先级高于 `~*` 正则，仅命中 `/data/news.js`，不动全站 JS 缓存。
- **备份**：三份 `.bak-pub-<时间戳>` 已生成并可读。
- **语法检查**：`nginx -t` 通过（`syntax is ok`；预存的 `conflicting server name` 警告与本变更无关）。
- **reload**：`nginx -s reload`（非 restart）成功。
- **响应头实测**：
  - 变更前（线上生效中）：`Cache-Control: max-age=604800, public`；`Expires` 为 7 天后。
  - 变更后：`Cache-Control: no-cache, must-revalidate`；`Expires: 0`（两域名 `mcu.yaokaixin.top`、`mcuatlas.xyz` 均验证）。
  - 结论：定向缓存规则**已生效**，资讯数据文件不再被缓存 7 天。

## 10. 发布操作说明（RUNBOOK）

详见同目录 `发布操作说明RUNBOOK.md`，要点：

1. **发布前**：确认 G9 已生成目标 `news.js`；确认已产出批准清单 `--manifest`；确认工作区与生产基线一致。
2. **dry-run（必做）**：`node publish-news.cjs --dry-run` —— 只读校验+差异，确认无删除/变更、新增均在批准清单内。
3. **差异审阅与人工确认**：审阅 dry-run 输出的新增/变更清单，确认无误后授权。
4. **正式发布（需授权）**：`node publish-news.cjs --publish --manifest <批准清单路径>`；脚本自动备份→原子替换→校验，失败自动回滚。
5. **发布后验证**：访问三页面确认新资讯出现；`curl -ksI https://<域名>/data/news.js` 确认 `Cache-Control: no-cache, must-revalidate`。
6. **回滚（两类，操作不同）**：详见 RUNBOOK 第 6 节。资讯数据文件回滚：`cp <target>.bak-pub-<时间戳> /www/wwwroot/mcu-h5/data/news.js`，**无需 nginx reload**（缓存已 no-cache，刷新即取新值）；nginx 配置回滚（撤销缓存规则）须先 `nginx -t` 再 `nginx -s reload`。
7. **日志/备份位置**：日志随脚本输出；数据备份位于 `mcu-h5/data/news.js.bak-pub-<时间戳>`，nginx 配置备份见 RUNBOOK 第 6.2 节。
8. **严禁**：全量复制 `mcu-atlas-news/h5` 到 `mcu-h5`；未授权直接 `--publish`；绕过批准清单。
