【一】三处必须纠正的前提（本次最关键）

1. 资讯状态是 **8 态，不是 5 档**。
   R1-R5 封版原文「状态数由 5 增至 8」；前端硬编码 8 个标签。
   你列的「业内人士称 / 有消息称」是**报道措辞**（写在标题里），
   对应状态文案实为「传闻 · 爆料」「信息待核实」。
   5 档没有 conflicting / 官方已否认 / 来源已更正 的位置 → 回退会让 3 条已通过的断言直接 FAIL。

2. **R1.1 已封版选型 C**，本次要求比较 CloudBase / 独立 API 属「修订封版」。
   且原反对理由已过时：实测**站点已有后端**
   （h5/assets/js/forum.js 有 15+ 处 /api/ 调用；index.html 第 441 行 fetch /api/topics）。
   → 真实代价应表述为：审核闸门弱化、可追溯性变化、通道单点。

3. **「三端复用」当前不存在**：微信端 / 抖音端**零资讯代码**（全仓检索命中 0），
   且已明确排除（不建 shared/data/news.js、不复制到小程序端）。
   → 若小程序端要显示资讯，**静态方案技术上不成立**（随包发布，每次更新需发版审核），
     必须切 CloudBase；另：抖音 V1.2.0 曾因「文娱-资讯」类目被驳回，资讯进抖音端有类目风险。

【二】六节结论

一、数据结构（长期 API 协议）
  33 字段分四级：
    契约 24 个（语义冻结，改名即破坏 UI 零改动）
    派生  1 个（independent_group_count，**禁止写入**，必须运行时算）
    审计  8 个（只增不改，缺失则状态变更不得入库）
    待批  6 个（event_key / ingested_at / raw_excerpt / registry_id /
                 reviewed_by·at / ai_model）→ **只留管道层，不进交付数据**
  前端 8 条硬约束（新增数据前必照）：
    summary 必须纯文本；publish_time 与 first_seen_at 至少一个非空（否则**静默消失**）；
    日期只渲染 YYYY-MM-DD；source_url 必须 http(s)；
    **卡片无图片区 → 新增封面/视频字段不会被渲染**；
    related_* 未命中真实 id 一律丢弃（不报错）；owner_group「待核」不计独立组；
    corrected 是报道级、事件级独立重算。

二、数据流
  来源 → 采集 → AI整理 → 判定 → 人工审核 → 入库 → 前端展示
  核心设计：**证据与状态物理分离** —— AI 只写「建议值」，状态由规则算，人不写状态只复核证据。
  ★ 建议**判定器优先于采集器**：现有 15 条数据的状态全是人写的，仓库里没有可执行判定器；
    判定器纯函数、零网络、可离线回归，风险最低且换通道后可 100% 复用。

三、来源等级
  先拆开三个被混用的轴：来源分档（R6.1）/ 来源角色（R2.6）/ 信息状态（8 态）。
  建议新增管道层 `source_registry`：tier T1-T4 + registry_id + crawl_policy + health。
  硬约束：tier 不渲染进页面；tier 不得映射为状态；独立证据组只认 owner_group。

四、存储方案（三端复用视角）
  | 维度 | ①文件（现状） | ②CloudBase | ③独立API |
  | file:// | 保持 | 破坏 | 破坏 |
  | git 可追溯 | 完整 | 断裂 | 断裂 |
  | 审核闸门 | 物理强制 | 靠纪律 | 靠纪律 |
  | 小程序端 | 不成立 | 原生支持 | 需白名单 |
  | 运维 | 最低 | 低 | 最高 |
  推荐：**维持①，Phase2 仅在触发条件成立时切②**；
  触发条件新增第 4 条「小程序端出现真实资讯展示需求」。

五、风险（7 项）
  假消息 / 版权（AI 摘要可能构成实质性替代；THR·EW·Collider 的 robots 反 AI 须固化进
  crawl_policy —— **此段非法律意见**）/ 来源可靠性（两个主力发现器的 owner_group 至今待核）/
  AI 误判 / **数据重复**（id 形如 news-日期-序号，跨天无法识别，需 event_key）/
  **通道单点**（切动态通道后 file:// 与故障时资讯整块消失 → 须保留静态兜底快照）/
  采集静默失败。

六、推荐（不开发）
  不推荐：现在就上独立 API 服务；把状态回退 5 档；登记表补齐前启动采集。

【三】待拍板 S-1 … S-8（开发侧建议，未拍板前不施工）

  S-1 判定器优先于采集器            → 建议 是
  S-2 先补齐来源登记表 + registry_id → 建议 是（阻塞项）
  S-3 新增 6 个管道字段              → 建议 是（仅管道层）
  S-4 三端复用边界：仅H5 / 结构可转换 → 建议「仅 H5 + 结构可转换」
  S-5 存储：维持文件 / 切 CloudBase   → 建议 维持文件
  S-6 是否修订 R1.1 封版结论          → 建议 不修订
  S-7 状态体系：维持 8 态 / 回退 5 档 → 建议 维持 8 态
  S-8 AI 摘要红线（字数上限+禁引原文）→ 建议 采纳

【四】置信度
  现状事实：**高（~85%）**（本轮实读 + 全仓检索，可复核）
  推荐维持静态通道：**中（~65%）**（依赖「三端复用本期不成立」这一产品判断；
                    若 S-4 选「小程序端要显示资讯」，该推荐立即失效）
  每日 5-10 条 / 人工 10-30 分钟：**低（~35%）**（单日快照推算，未连续 7 天实测）
