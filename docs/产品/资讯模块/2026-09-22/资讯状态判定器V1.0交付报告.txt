1. 一、判定器设计
============================================================

■ 1.1 定位与形态

  判定器是一个**纯函数规则引擎**：输入「证据 + 语义标记」，输出唯一 verification_status。
  它不采集、不联网、不读文本语义、不写文件。

  ┌────────────┬──────────────────────────────────────────────────────────┐
  │ 属性        │ 实现方式                                                  │
  ├────────────┼──────────────────────────────────────────────────────────┤
  │ 纯函数      │ 不读环境变量、不读外部状态；时间由调用方注入（now 参数）        │
  │ 零网络      │ 源码仅 require 本地模块（实测：无 http/https/net/dns/        │
  │            │ fetch/axios 等任何网络依赖）                               │
  │ 零 AI 依赖   │ 不调用任何模型接口                                          │
  │ 零副作用    │ 不写文件、不改全局；输入 item 只读，不被修改                  │
  │ 可重入      │ 同输入两次运行输出逐字节一致（测试已断言）                     │
  │ 确定性      │ 八步链短路判定，无随机、无排序依赖                            │
  └────────────┴──────────────────────────────────────────────────────────┘

■ 1.2 模块结构（两个文件，职责分离）

  ┌──────────────────────────┬────────────────────────────────────────────┐
  │ 文件                      │ 职责                                        │
  ├──────────────────────────┼────────────────────────────────────────────┤
  │ news-judge-rules.cjs     │ 纯数据与常量：8 态枚举、判定步骤标识、         │
  │                          │ 可靠 tier 集合、owner_group 未确认取值、      │
  │                          │ 爆料词表、source_registry 最小子集、          │
  │                          │ 官方来源登记表（含 allowed/excluded paths）、  │
  │                          │ path 校验策略开关。**无任何逻辑**             │
  ├──────────────────────────┼────────────────────────────────────────────┤
  │ news-judge.cjs           │ 判定逻辑：URL 校验、派生计数、判据函数、       │
  │                          │ 八步判定链、输出契约组装与校验                 │
  └──────────────────────────┴────────────────────────────────────────────┘

  规则与逻辑分离的目的：将来 G2 落地 source_registry 数据文件时，
  只需替换 rules 模块的数据源，判定逻辑一行不动。

■ 1.3 ★ 三个关键设计决策

  【决策 1】判定器不读文本、不做语义判断
    官方确认 / 官方否认 / 互斥表述这三类判断属语义任务，
    由第一层 AI 建议 + 人工复核后以**结构化标记**传入（I9）。
    判定器只做确定性计算：计数、字符串匹配、比较、短路。
    唯一的例外是 Step 7 对 `original_source` 一个字段做爆料词表匹配
    —— 该字段是人工/AI 填写的最小封闭字段，且 R8.3 Step 7 的判据本身即
    「原始来源是否属爆料」。**对 title / summary 一律不做匹配。**

  【决策 2】双计数：independent_group_count 与 reliable_group_count
    · `independent_group_count` —— 仅按 owner_group 去重（**与 components.js
      口径逐字符一致**），用于输出字段与 A2 验收；
    · `reliable_group_count` —— 额外要求 tier ∈ {T1,T2,T3}，用于 Step 5 / Step 6
      的「可靠来源」判据（R3.2 原文要求「来源质量不低」）。
    · 二者分离的原因：R3.1 只定义了 owner_group 去重，未定义 tier 过滤；
      若把 tier 过滤直接并入独立组计数，会与前端现算值产生口径差。
    · 实测：现有 15 条下两值**逐条相同**（诊断项已断言），
      差异仅在 B9 / B10 这类「已确认组但来源为 T4」的边界出现。

  【决策 3】path 校验策略做成开关，默认沿用现行宽松规则（★ E-1）
    · `PATH_POLICY.mode` 默认 `'legacy'` —— 允许 `/news`、`/news/`
      与 `/articles/{movies|tv-shows|live-events}/`（栏目/目录页），
      与 test-news-rules.cjs 现状断言一致；
    · `'article-level'` —— Q-5 冻结的严格规则：路径须至少含一级 slug
      （`/news/{slug}`），即文章级 URL。
    · 默认 legacy 的原因：E-1 已确认「规则冻结立即生效、历史数据整改延后至 G8」。
      若在 G1 直接启用严格模式，001 / 009 / 013 的官方 URL 将无法通过
      Step 1 / Step 2，与「黄金用例必须复现现有状态」直接冲突。
    · 测试已断言该开关的双向行为（legacy 通过 / article-level 不通过）。

■ 2.1 输入：结构事实 + 语义标记（物理分开）

  ┌────┬────────────────────────┬──────────┬──────────────────────────────────┐
  │ #  │ 输入                    │ 类别      │ 说明                              │
  ├────┼────────────────────────┼──────────┼──────────────────────────────────┤
  │ I1 │ item.reported_by[]      │ 结构事实  │ source_name / source_url /        │

  │ I3 │ URL（官方确认 / 否认 /    │ 结构事实  │ 仅做 host + path 字符串校验        │
  │    │ 来源文章）               │          │ （**不做联网探测**）               │
  │ I4 │ 独立证据组数             │ —        │ ★ **由判定器自算，禁止作为入参**     │
  │ I5 │ item.report_corrections[]│ 结构事实 │ 更正记录（含 source_name）          │
  │ I6 │ item.conflict_statements[]│结构事实 │ 冲突各方表述                       │
  │ I7 │ item.original_source    │ 结构事实  │ **唯一允许文本匹配的字段**          │
  │ I9 │ 语义标记（第二入参 input）│ **语义** │ 见 2.2                            │
  └────┴────────────────────────┴──────────┴──────────────────────────────────┘

■ 2.2 语义标记（I9）—— 判定器不自行判断，由外部传入

  ```
  input = {
    official_confirm:  { url: string, reviewed: boolean },   // Step 1
    official_denial:   { url: string, reviewed: boolean },   // Step 2
    conflict_verified: { verified: boolean }                 // Step 4
  }
  ```
  三项均可缺省。缺省时对应步骤**不成立**（一律降级，绝不升格）。

■ 2.3 调用签名

  ```
  judge(item, input, opts) -> result
  judgeAll(items, inputsById, opts) -> result[]

  opts = {
    now:            string   // ISO8601，时间注入（默认当前时间）
    pathPolicy:     string   // 'legacy' | 'article-level'（默认 legacy）
    previousStatus: string   // 状态历史 from 字段（默认 null）
    judgedBy:       string   // 覆盖判定层级（默认按命中步骤派发）
  }
  ```

■ 2.4 输出契约（7 项必填，缺一即抛错，不静默返回默认值）

  ┌──────────────────────────────┬────────┬────────────────────────────────┐

  ├──────────────────────────────┼────────┼────────────────────────────────┤
  │ verification_status          │ enum(8)│ 8 态之一，**不得第 9 态**         │
  │ chain_steps_hit              │ string │ 'Step 1' … 'Step 8'            │
  │ judged_by                    │ enum(3)│ 见 2.5                          │
  │ status_changed_at            │ string │ 本次判定时间（= opts.now）        │
  │ status_change_reason         │ string │ 与 chain_steps_hit 对应的依据说明 │
  │ status_change_evidence_url   │ string │ 证据 URL（必须可回链）            │
  │ status_history_entry         │ object │ {from,to,at,reason,evidence_url}│

    rule_version / path_policy / independent_group_count / reliable_group_count

  异常处理：item 为空、缺 id、或产出状态不在 8 态枚举内 → **显式抛错**。

3. 三、规则实现方案
============================================================

■ 3.1 派生计算（I4：自算，禁入参）

  独立证据组数：
    A 逐项取 owner_group
    B 丢弃 owner_group ∈ {「待核」,「未确认」,「unknown」} 或空白 的项
    C 按 owner_group 去重计数
    D 输出（0 起）
  边界：reported_by 空数组 → 0；全部待核 → 0。
  ★ 与 components.js 的 isGroupConfirmed / calcIndependentGroupCount 结果一致
    （A2 验收已逐条比对通过）。

■ 3.2 R7.4 的 Step 1–3 机器校验（本阶段实现范围）

  校验项（全部为字符串处理，零网络）：
    ① URL 存在且为 http(s)
    ② host 不在 non_official_domains（disney.com / disneyplus.com）
    ③ host 命中 OFFICIAL_SOURCES.allowed_domains
    ④ path 命中 allowed_paths，且不落在 excluded_paths
    ⑤ path 策略：legacy（栏目页可） / article-level（须含一级 slug）
  未在 G1 实现的：Step 1 的 HTTP 可达性（属 G3）、Step 4「内容对应当前事件」
  （属语义判断，由 I9 承载）、Step 5 人工复核（由 I9 的 reviewed 位承载）。

■ 3.3 八步判定链（短路执行，顺序即优先级）

  ┌──────┬────────────────────────────────────────────┬──────────────────────┐
  │ 步骤  │ 实现判据                                    │ 输出状态              │
  ├──────┼────────────────────────────────────────────┼──────────────────────┤
  │Step 1│ official_confirm 存在 且 url 过 ①–⑤          │ official_confirmed   │
  │      │ 且 reviewed = true                         │                      │
  │Step 2│ official_denial 存在 且 url 过 ①–⑤           │ officially_denied    │
  │      │ 且 reviewed = true                         │                      │
  │Step 3│ report_corrections 非空，且 reported_by 的    │ corrected            │
  │      │ **每一项**均能在更正记录中找到同 source_name  │                      │
  │Step 4│ conflict_verified.verified = true           │ conflicting          │
  │      │ 且 conflict_statements.length ≥ 2           │                      │
  │Step 5│ reliable_group_count ≥ 2                   │ multi_source_reported│
  │Step 6│ reliable_group_count = 1                   │ single_source        │
  │Step 7│ ①原 source 命中爆料词表 或 ②唯一来源 tier=T4 │ rumor                │
  │      │ 或 ③唯一来源 owner_group = 'unknown'         │                      │
  │Step 8│ 以上皆不成立                                 │ unverified           │
  └──────┴────────────────────────────────────────────┴──────────────────────┘

  三条顺序性硬约束（均已实现并有测试覆盖）：
    · Step 4 必须早于 Step 5 —— 存在互斥时「各来源表述一致」前提已破。
      测试 B4 / B4b 用同一组数据（2 个跨集团独立组）对照证明：
      核准互斥 → Step 4；未核准 → Step 5。
    · Step 3 只施加于「被更正的报道」—— 若仍有未更正的报道，事件级不得落
      corrected，须继续后续步骤。测试 B8 覆盖（1 条被更正 → 落 Step 5）；
      黄金用例 011 亦为同一形态（报道级更正、事件级 multi_source_reported）。
    · Step 6 要求「可靠来源」—— 独立组 = 1 但该来源为 T4 时**不得**判
      single_source。测试 B9 覆盖。

■ 3.4 降级矩阵（缺数据一律降级，绝不升格）

  ┌────────────────────────────────────┬──────────────────────────────────┐
  │ 缺失情形                            │ 实现行为                          │
  ├────────────────────────────────────┼──────────────────────────────────┤
  │ owner_group 缺失 / 待核 / unknown    │ 不计入独立组；组数 0 → 落 Step 7/8 │
  │ official_confirm 缺失               │ Step 1 不成立，继续后续            │
  │ official_confirm.url 未过校验        │ 同上（host/path/reviewed 任一失败） │
  │ official_denial.url 未过校验         │ Step 2 不成立，继续后续            │
  │ report_corrections 为空             │ Step 3 不成立，继续后续            │
  │ conflict_statements < 2 或未核准     │ Step 4 不成立，继续后续            │
  │ reported_by 为空                    │ 组数 0 → 落 Step 7 或 8           │
  │ original_source = 'unknown'         │ Step 7 不成立 → unverified        │
  │ 来源未在 registry 登记               │ tier 默认 T4（保守），不计入可靠来源 │
  └────────────────────────────────────┴──────────────────────────────────┘

■ 3.5 红线自查（实现层对应关系）

  ┌──────────────────────────────────────────┬────────────────────────────┐
  │ 红线                                      │ 实现层保障                  │
  ├──────────────────────────────────────────┼────────────────────────────┤
  │ 1 不得接受外部传入独立组数                  │ judge 签名无该参数（测试断言）│
  │ 2 不得因来源权威 / tier 高而破格升格         │ tier 仅参与「是否可靠」判定， │
  │                                          │ 不产生任何升格路径            │
  │ 3 不得因多家转载判为 multi_source_reported  │ Step 5 只认 owner_group 去重  │
  │ 4 不得假设未确认来源的独立性                 │ 待核/unknown 一律不计组       │

■ 6.2 【发现·待产品定义】judged_by 的权威口径尚未定义
  诊断输出显示：现有 15 条中有 6 条与「按命中步骤自动派发」的结果不同：
    · 5 条数据记为 `ai_suggested`（004 / 006 / 007 / 012 / 015）→ 判定器产出 `rule_validated`
    · 1 条数据记为 `human_confirmed`（011）→ 判定器产出 `rule_validated`
  两种读法都能自圆其说：
    a) judged_by = 「谁最终确认了这条状态」（数据现状写法，含 AI 建议未升级的情形）
    b) judged_by = 「本次判定的层级」（判定器写法，由命中步骤决定）
  → 该字段是**审计字段**，语义必须唯一，否则将来统计「AI 建议采纳率」会失真。
  → 属规范待明确项，**不阻塞 G1 交付**（判定器已支持 opts.judgedBy 覆盖两种用法）。
  → 建议在 G2 之前由产品给一个字的结论。
