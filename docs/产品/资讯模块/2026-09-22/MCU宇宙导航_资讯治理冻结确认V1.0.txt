■ 2.2 Q-2｜publish_time 策略 —— 【已冻结】

  冻结值（双时间语义，封版规范此前未定义，本次补齐）：
  ┌────────────────┬──────────────────────────────────────┬──────────────────────┐
  │ 字段            │ 语义                                  │ 格式与约束            │
  ├────────────────┼──────────────────────────────────────┼──────────────────────┤
  │ publish_time   │ **来源文章的发布时间**                 │ YYYY-MM-DD；前端只展示 │
  │                │ （不是入库时间、不是采集时间）           │ 日期部分              │
  ├────────────────┼──────────────────────────────────────┼──────────────────────┤
  │ first_seen_at  │ **系统首次见到该内容的时间**             │ ISO8601 带 UTC        │
  │                │（用于排序回落与延迟统计）                │（如 2026-09-22T01:10Z）│
  └────────────────┴──────────────────────────────────────┴──────────────────────┘

  配套规则：
    1. 两字段**至少一个非空**；两者皆缺的条目会被 sortNews Step 0 静默剔除。
    2. 排序口径：publish_time 优先，缺失回落 first_seen_at（既有实现，不改动）。
    3. 延迟口径：延迟 = first_seen_at − publish_time，**仅用于内部统计**，
       **禁止对外展示**（不得出现「N 小时前」「刚刚」类表述，R4.1）。
    4. 每篇报道（reported_by 项）的独立发布时间 **published_at 只存管道层**，
       **不进入交付物**（交付物保持 33 字段，见第 3 节）。
    5. 现有 15 条中 `news-2026-09-17-015` 的 publish_time = null 属测试夹具，
       在 G8 数据替换时按既有清单迁移。

  依据：查 R1–R8 全文，双时间语义**从未定义**，属规范空白；
        不定义则 R1.3「延迟以天计」无法测量、排序口径不稳定。
  影响面：管道侧 + 排序口径；**零 UI 影响**。  回退成本：低。
  权威性：开发侧直接冻结。

■ 2.3 Q-3｜related_* 关联范围 —— 【待签】

    · related_phases 只能为 1–6 整数

■ 2.5 Q-5｜source_url 路径规则 —— 【已冻结，但推迟生效（见 E-1）】

  冻结值：**强制文章级路径**。
    1. `reported_by[].source_url` **必须为文章级 URL**
       （即该篇报道的文章页链接；若来自 feed，必须取条目 `<link>` 指向的原文地址）
       禁止：feed 端点（如 /feed/、/rss）、栏目页、站点首页、目录页
    2. `official_source_url` **必须为文章级 URL**
       禁止：`https://www.marvel.com/news`（栏目页）、
             `https://www.marvel.com/articles/live-events/`（目录页）
    3. R7.3 的 `allowed_paths` 同步收紧：官方路径**必须至少含一级 slug 段**
       （即 `/news/{slug}` 形态），并在登记表中显式列举
    4. `feed_url`（source_registry）继续保存 feed / 栏目入口，
       **feed 级 URL 从此只允许出现在 registry，不得出现在交付数据**
    5. 例外：无法提供文章级 URL 的来源（社交爆料等）按 R7.5 处理，
       必须附**原始发布链接**；缺失则不得构成 official_confirmed
    6. 同步动作：test-news-rules.cjs 的 path 断言（L182）收紧为要求文章级 slug
       —— **该动作被推迟，见 E-1**

  依据：实测 **15/15 条**的 source_url 与 official_source_url 均非文章级；

        栏目页即可构成「官方确认」；详情页「查看原文」点进去是栏目而非报道。
  影响面：交付数据质量 + R7.4 有效性。  回退成本：中。
  权威性：开发侧直接冻结（收紧本身），**生效时点需负责人确认**。

  提醒语同步冻结（components.js NEWS_NOTICE，8 条）。

■ 4.3 措辞红线冻结
  禁真实性 / 可信度百分比；禁绝对化措辞；禁实时性措辞；
  官方确认也不得暗示「永远不会变化」。

■ 4.4 排序规则冻结（R5.2 五步，现状实现，不改动）
  过滤 → 置顶有效性 → 分层 → 置顶组内（pinned_order 升序）→ 并列打破（状态序 → id 升序）
  ★ 官方确认**不自动置顶**；verification_status **不参与主排序**，仅作并列打破器。

■ 4.5 状态语义冻结（R8.8）
  **状态不是永久事实标签。** verification_status 表示「截至当前已获得的证据和来源层级」，
  而不是对某条消息的终局判定。任何新证据进入后，都必须重新执行完整判定链。

■ 4.6 三条状态处理规则冻结
  · officially_denied：**保留不删除**；默认不进首页列表（除人工置顶并填理由）；
    卡片与详情页显著展示。
  · corrected：保留原始报道与更正记录，以 supersedes_id / superseded_by_id 互链；
    列表合并展示为一条；corrected **不得直接升级为 official_confirmed**（除重新判定命中 Step 1）。
  · conflicting：**不判断谁对**，并列展示各方表述；解除后从 Step 1 重跑判定链。

6. 判定器原则冻结

■ 6.1 输入契约冻结（I1–I9）

  ┌────┬────────────────────┬────────────────────────────────────────────────────┐
  │ #  │ 输入                │ 性质与要求                                          │
  ├────┼────────────────────┼────────────────────────────────────────────────────┤
  │ I1 │ 来源证据            │ reported_by[]（source_name / source_url / owner_group）│
  │ I2 │ owner_group 映射     │ 来自 source_registry；「待核/unknown/未确认/空」视为不可用│
  │ I3 │ 官方确认证据         │ official_source_url + 通过 R7.4 前 3 步机器校验      │
  │ I4 │ **独立证据组数**      │ ★ **由判定器自行计算**，禁止外部传入                 │
  │ I5 │ 更正记录            │ report_corrections[]                               │
  │ I6 │ 冲突记录            │ conflict_statements[]                              │
  │ I7 │ 原始来源            │ original_source + original_source_url              │
  │ I8 │ 关联 id 集合         │ MCU_CONTENT / MCU_CHARACTERS（用于入库前校验）        │
  │ I9 │ 语义标记（人工确认）  │ ★ 见 6.2 —— 官方否认 / 冲突成立 / 官方确认的最终核准   │
  └────┴────────────────────┴────────────────────────────────────────────────────┘

■ 6.2 ★ 关键原则：**判定器不读文本，不做语义判断**

  冻结规则：
    · 判定器**不得**从 title / summary 文本推断「官方否认」「存在冲突」等语义；
    · 这类判断属第一层（AI 整理）的**建议**，经人工复核后以**结构化标记**传入（I9）；
    · 判定器只做**确定性计算**：计数、匹配、比较、短路。
  可自动推导 vs 必须外部传入：
    可自动：Step 3（更正是否覆盖全部有效报道）、Step 5 / 6（独立组计数与一致性）、
            Step 7（原始来源是否属 T4 / 爆料词表）、Step 8（兜底）
    须外部：Step 1（官方确认成立与否）、Step 2（官方否认成立与否）、
            Step 4（互斥表述是否成立）

■ 6.3 派生计算冻结（独立证据组数）
  逐项取 owner_group → 丢弃「待核/未确认/unknown/空」→ 按 owner_group 去重计数 → 输出。
  · **禁止人工填写**，**禁止 AI 提供**。
  · 边界：reported_by 空数组 → 0；全部待核 → 0。
  · 交付数据中的值必须与该计算一致（既有断言已覆盖）。

■ 6.4 判定链冻结（8 步，首个成立即输出并终止）

  Step 1 官方确认（过 R7.4）        → official_confirmed
  Step 2 官方明确否认（须回链官方）   → officially_denied
  Step 3 全部有效报道均被更正        → corrected
  Step 4 可靠来源间互斥表述          → conflicting
  Step 5 独立组 ≥2 且表述一致        → multi_source_reported
  Step 6 独立组 = 1（可靠媒体）      → single_source
  Step 7 原始来源属爆料              → rumor
  Step 8 以上皆不成立                → unverified

  · 短路口径即优先级，**不得调换**；Step 4 必须早于 Step 5。
  · Step 3 只施加于「被更正的该条报道」；若仍有其他有效证据，
    事件级**不得**在 Step 3 终止，须继续 Step 4 及后续。
  · 「可靠来源」定义冻结为 **tier ∈ {T1, T2, T3}**；**T4 一律不构成可靠来源**。

■ 6.5 输出契约冻结（7 项，缺一不得入库）
  verification_status / chain_steps_hit / judged_by / status_changed_at /
  status_change_reason / status_change_evidence_url / status_history 追加项

■ 6.6 重新判定原则冻结
  · 任何状态变更**从 Step 1 重跑完整判定链**，不得局部改字段；
  · 人工**不得指定目标状态**；人工只有两项职责：提供证据、复核判定结果；
  · 人工认为判定有误 → 唯一合规做法是**补充或修正证据后重新触发判定**；
  · conflicting 解除：满足①官方表态 / ②一方更正或撤稿 / ③新证据使一方失效 之一
    → 落库 conflict_resolved_at 与 conflict_resolved_by_evidence_url（均必填）→ 从 Step 1 重跑；
  · 明确禁止 conflicting → single_source / multi_source_reported 的人工硬编码转换。

■ 6.7 缺数据与异常处理冻结：**一律降级，绝不升格**

  owner_group 缺失 / 待核 → 不计组；组数 0 → unverified
  官方 URL 不可访问 / 未命中 host 或 path → Step 1、2 不成立并回落；
    path 未命中时状态**最高只能到 multi_source_reported**
  report_corrections / conflict_statements 为空 → 对应步骤不成立，继续后续
  reported_by 空数组 → 组数 0 → 落 Step 7 或 Step 8
  original_source = 'unknown' → Step 7 不成立 → unverified
  related_* 未命中 → 丢弃该关联（不影响状态）

■ 6.8 判定器红线冻结（10 条禁止）
  1 不得接受外部传入独立组数  2 不得因来源权威/tier 高而破格升格
  3 不得因多家转载判为 multi_source_reported  4 不得假设未确认来源的独立性
  5 不得制造来源或补齐不存在的事实  6 不得输出真实性 / 可信度百分比
  7 不得新增第 9 种状态  8 不得覆盖写 status_history
  9 不得以主观判断覆盖判定结果  10 不得跳过判定链直接改 verification_status

■ 6.9 三层职责边界冻结
  AI 层：只出建议（抽取、关联、摘要、ai_suggested_status）→ 不得认定官方确认
  规则层：计算状态、R7.4 机器校验、独立组去重 → 不得被覆盖
  人工层：提供证据 + 复核结果 → 不得指定目标状态
  必须人工介入：official_confirmed / officially_denied / conflicting /
    original_source 无法确定的 multi_source_reported / 涉及 supersedes 链的记录
