2. 二、A 项裁定：event-merger 与 supersedes_id / superseded_by_id 的关系
============================================================

■ 2.1 事实基线（双方机制各自是什么）

  ┌──────────────┬──────────────────────────────────┬──────────────────────────────────┐
  │ 维度          │ event-merger（G4）                │ supersedes 链（R8.5）             │
  ├──────────────┼──────────────────────────────────┼──────────────────────────────────┤
  │ 所在层级      │ **管道层**                        │ 数据层 + 展示层                    │
  │ 处理对象      │ **多条报道**（来自不同来源）         │ **同一发布方的前后两个版本**         │
  │ 判定依据      │ event_key + 时间窗口              │ 发布方更正声明                     │
  │ 触发原因      │ 同一事件被多家报道                  │ 某条报道被其发布方更正              │
  │ 处理结果      │ 归并为一个「事件对象」（管道内部）     │ 保留两条数据 + 互链 + 展示合并为一条 │
  │ 是否改交付数据 │ **否**                            │ 是（新增一条 + 写入互链字段）        │
  │ 是否改状态    │ 否                                │ 否（状态由判定器重算）              │
  └──────────────┴──────────────────────────────────┴──────────────────────────────────┘

■ 2.2 裁定条款（建议稿）

  **A1**　event-merger 是**管道层事件聚合机制**，唯一用途两项：
         ① 减少候选条数（把同一事件的多条报道聚成一条候选）
         ② 组装事件级来源证据（`reported_by_union`）
         除此之外**不得**用于任何其他目的。

  **A2**　event-merger **不替代** supersedes_id / superseded_by_id 机制。
         两套机制管辖范围不同（见 2.1 对照），**并行存在、互不替代**。

  **A3**　event-merger **不修改交付数据**：
         不写文件、不产出 news.js、不修改任何条目的任何字段。
         （当前实现已符合：`reports` 不裁剪、`records_deleted` 恒 0、输出不含任何状态字段。）

  **A4**　当同一对条目**同时命中两套机制**时（现有 010 / 014 即此情形）：
         **以 supersedes 为准**。event-merger 只做归并标注，
         **不得**据此删条、不得把两条压成一条、不得改动互链字段。

  **A5**　落库阶段（G6）红线：交付数据**仍须保留 supersedes 双条与互链**；
         展示层的「合并为一条」照旧由前端处理（R8.5 语义不变）。
         事件归并结果**只用于**候选池组织与来源证据组装。

  **A6**　可验证性要求：G6 引入落库逻辑时，必须有一条断言证明
         「supersedes 双条都在交付数据中且互链成对」——
         用以防止事件归并逻辑侵蚀 supersedes 链。

■ 2.3 为什么必须在 G5 之前定这一条

  · G5 采集器会产出候选；G6 会把候选写入交付数据。
  · 若此边界不定，实现者很可能「顺手」把事件归并的结果直接落库，
    导致 010/014 变成一条 —— **链式引用丢失、可追溯性破坏**（违反 R8.5 与 R8.3）。
  · 本阶段未写任何交付数据，因此**现在定成本最低**。

3. 三、B 项裁定：event_key 使用边界
============================================================

■ 3.1 裁定条款（建议稿）

  **B1**　event_key **不是数据库唯一主键**。
         它是「事件签名指纹」，**同一签名可对应多个时间上分离的 occurrence**。
         实测证据：E2b 用例（标题与实体完全相同、时间相距 79 天）
         → 同一个 event_key 产出 **2 个 hold 事件**。
         这是「不自动合并不同事件」的正确行为，但也说明 key 不具备唯一性。

  **B2**　event_key **不作为报道实体 ID**。
         报道实体 ID 是交付数据的 `id`（`news-YYYY-MM-DD-NNN`）。
         两者**不可互换、不可互相替代**：
         · `id` 标识「一条报道」，进交付数据、进 URL 参数；
         · `event_key` 标识「一个事件签名」，**只在管道层使用**。

  **B3**　event_key **不得**用于以下四种场合：
         ① 写库 / 落文件的主键
         ② 对外 URL 查询参数
         ③ 任何用户可见的展示内容
         ④ 跨端（H5 / 微信 / 抖音）数据关联键

  **B4**　主键方案建议（**二选一，待裁定**）

  ┌────────┬──────────────────────────────────────┬──────────────────────────────────────┐
  │ 方案    │ 定义                                  │ 优缺点 / 实现影响                     │
  ├────────┼──────────────────────────────────────┼──────────────────────────────────────┤
  │ **B-i**│ 组合主键                              │ 优点：**零代码改动**（merger 已输出     │
  │ 组合键 │ `event_key + '@' + first_publish_time`│ first_publish_time）                  │
  │        │                                      │ 缺点：字符串较长；含时间语义，易被     │
  │        │                                      │ 误当作「事件时间」对外使用             │
  ├────────┼──────────────────────────────────────┼──────────────────────────────────────┤
  │ **B-ii**│ occurrence 序号                      │ 优点：稳定、短、语义清晰；             │
  │ occurrence│ `occurrence` = 同 event_key 下按     │ 缺点：需改 merger（**新增 1 个输出字段**）│
  │（倾向）│ first_publish_time 升序，从 1 编号    │                                      │
  │        │ 主键 = `event_key + '#' + occurrence` │                                      │
  └────────┴──────────────────────────────────────┴──────────────────────────────────────┘

  **B-ii 的实现要点（若批准，必须先明确这三条）**：
    ① 编号必须**在同一批次内全量排序后**生成 ——
       因为 occurrence 依赖「同批处理里该 key 的全部条目」；
       若分两批处理，编号会冲突。→ 要求 **单批次全量输入**。
    ② 新增字段只出现在 merger 的**输出**中，**不得写回输入数据**。
    ③ 需同步新增断言：同 key 下 occurrence 从 1 连续编号、无重复；
       且 `event_key + '#' + occurrence` 在输出内唯一。

  **B5**　event_key 的既知口径限制（重申，不属缺陷但必须知悉）
    · **不区分状态**（刻意）：事件身份须跨状态稳定（R8.8）；
      副作用是「已确认」与「传闻」两条不同报道共享同一 key → 不能用于报道层级筛选。
    · **无实体时识别力弱**：实体为空时退化为文本指纹，
      「同事件不同标题」不会被识别为同一事件（宁可不合，不可误合）。
    · **时间窗口 3 天未校准**：建议 G5 实测后回调。

  ★ **本轮未实现 B-i / B-ii 任何一项**（任务要求为「建议」）。
    若批准 B-ii，属 **G4.2 小补丁**：新增 1 个输出字段 + 2 条断言，
    不触碰 G1 / G2 / G3，不影响既有 95 条断言。

    · 规范层补一句：**judged_by 表示「本次判定的层级」，不表示「最终确认者」**
