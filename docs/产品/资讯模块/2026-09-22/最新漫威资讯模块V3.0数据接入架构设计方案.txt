  b. R1-R5 变更清单第 721 行原文：「状态数由 5 增至 8

  · 本方案按「先不写死、不承诺小程序端」处理，并在 S-4 / S-5 把

■ 2.3 作为长期 API 协议必须冻结的字段（结论）

  建议把 A 类 24 个 + C 类 8 个 = **32 个字段整体冻结为 V1 版协议**，

  1) **只增不改**：V3.0 之后允许新增可选字段（D 类），

  4) **可选性冻结**：现有 15 条**全部字段齐全**，这是当前协议的隐性
     强约束。若未来引入可选字段，必须同步在 test-news-rules.cjs 里
     区分「必填」与「可选」两套断言，否则 78 条断言会误报。

============================================================
3. 二、真实资讯数据流设计
============================================================

■ 3.0 一句话架构

  把「证据采集」与「状态判定」**彻底分离**：采集层只产出证据，
  状态由确定性规则计算，AI 只做抽取与文案，人不写状态、只复核证据。

  这直接继承 R3.5（三层判定）与 R8.2（重新判定原则），
  V3.0 的实质增量**不是「加 AI」，而是「把判定链从人工执行变成可执行代码」**。

■ 3.1 全链路（6 环节）

来源  →  采集  →  AI 整理  →  判定  →  人工审核  →  入库  →  前端展示
         (S1)      (S2)       (S3)      (S4)        (S5)      (S6)

  ┌──────────────────────────────────────────────────────────────────────┐
  │ S0 来源                                                               │
  │   输入：R6 已实测的 11 个来源出口（A 档自动 6 / B 档人工 3 / C 档不用 2）│
  │   硬前提：来源登记表必须补齐 owner_group（The Direct、ComicBook 当前  │
  │          仍为「待核」）。**未补齐则整条流水线的独立组计数不可信。**      │
  │   产出：可抓取出口清单 + robots 合规状态 + 探活记录                     │
  ├──────────────────────────────────────────────────────────────────────┤
  │ S1 采集                                                               │
  │   动作：每日 1 次，顺序 官方(marvel.com /news、thewaltdisneycompany)    │
  │         → 发现器(The Direct /rss、ComicBook /category/marvel/feed/)     │
  │         → 验证器(Variety、Deadline)                                    │
  │   产出：**原始条目池**（title / url / 时间 / 来源 / 原文摘录）            │
  │   纪律：只落证据，不落状态；不判定真伪；不抓封面图；不存全文             │
  │   失败：连续 3 次失败 → 自动降级为「暂停」并告警（R6.2）；              │
  │         **解析失败必须告警，禁止静默产出空结果**（R6.2 第 1 项）          │
  │   已知陷阱（必须写进代码注释，否则必然踩）：                             │
  │     · The Direct 的条目时间在 <dc:date>，读到 pubDate 会全部为空         │
  │     · ComicBook 必须用 /category/marvel/feed/，/marvel/feed/ 会静默回落  │
  │     · marvel.com **没有 RSS**，只能用 /news 列表页 HTML 解析 + JSON-LD   │
  │     · marvel.com /news 约 75% 是 comics/games，须做影视类过滤            │
  ├──────────────────────────────────────────────────────────────────────┤
  │ S2 AI 整理                                                            │
  │   允许做（R3.5 第一层）：抽取 reported_by 与候选 original_source、      │
  │     判断疑似转载/转引、判断是否同集团、抽取关联实体、相似新闻合并建议、  │
  │     生成纯文本摘要与提醒文案、提出 verification_status **建议值**        │
  │   硬禁止（R3.5 第一层 + R8.1）：不得自行认定 official_confirmed、       │
  │     不得制造来源、不得把传闻写成确定事实、不得因多家转载就认定真实、     │
  │     不得在 owner_group 未确认时假设独立性、不得输出真实性百分比          │
  │   关键设计：**AI 的输出只能是「建议」，且必须与「状态」物理分离** ——      │
  │     建议值写入候选文件的 ai_suggested_status（管道字段），              │
  │     最终 verification_status 由 S3 计算，AI 无权直接写。                │
  ├──────────────────────────────────────────────────────────────────────┤
  │ S3 判定（★ V3.0 的第一个真交付物）                                      │
  │   动作：对每条候选执行 R8.3 八步判定链，输出唯一 target_status           │
  │   输入：reported_by、owner_group 登记表、official_source_url、          │
  │         report_corrections、conflict_statements、original_source       │
  │   输出：verification_status + chain_steps_hit + judged_by:'rule_validated'│
  │   性质：**纯函数、零网络依赖、可离线跑、可回归** → 直接可被              │
  │         test-news-rules.cjs 复用（见 3.4）                             │
  │   禁止：任何人工指定目标状态（R8.2）；任何「看起来合理就填」的做法       │
  ├──────────────────────────────────────────────────────────────────────┤
  │ S4 人工审核（唯一的上线闸门）                                            │
  │   人工只做两件事（R8.2 边界）：a. 提供证据（官方链接、更正声明、撤稿）   │
  │                              b. 复核判定链输出是否符合证据事实           │
  │   必须人工介入的状态：official_confirmed / officially_denied /          │
  │     conflicting / 任何 original_source 无法确定的 multi_source_reported /│
  │     任何涉及 supersedes 链的记录（R3.5 第三层）                          │
  │   成本：R1.3 实测口径 1–2 分钟/条，10–30 分钟/日（须连续 7 天校准）      │
  │   产出：审核通过的候选文件                                             │
  ├──────────────────────────────────────────────────────────────────────┤
  │ S5 入库                                                               │
  │   当前纪律（R1.2-5）：**唯一入口是人工提交 git**。                      │
  │     · 产线在仓库之外运行，产出候选文件                                 │
  │     · 人工复核通过后覆盖 h5/data/news.js 并提交                        │
  │     · 运行时只读静态 js，不发任何请求                                  │
  │   附带动作：同步更新 MCU_NEWS_META.stage（'mock' → 'live'）、          │
  │     built_at、以及新增 pipeline_run_id（若采纳 S-3 决策）               │
  │   校验：入库前必须跑 test-news-rules.cjs，FAIL 则不得提交               │
  ├──────────────────────────────────────────────────────────────────────┤
  │ S6 前端展示                                                           │
  │   **零改动**。前端继续只读 window.MCU_NEWS，排序/文案/跳转全部复用     │
  │   现有 components.js 的 v2.sortNews / newsCard / newsDetail            │
  │   验收硬指标：V2.2 的 78 + 55 + 11 条断言必须继续全绿                   │
  └──────────────────────────────────────────────────────────────────────┘

■ 3.2 延迟与节奏（沿用 R1.3，不作美化）

  每日一跑 → 平均延迟约 12 小时，最坏约 24 小时。
  任何文案不得暗示实时性。这不是实时资讯系统，本方案不改变这一点。

■ 3.3 七个通道纪律（建议写入 V3.0 规范正文）

  1. 采集层不产出状态，只产出证据。
  2. 状态由确定性规则计算，AI 与人工都不能直接指定。
  3. 任何状态变更都必须完整重跑判定链，禁止局部改字段。
  4. 旧条目不得因状态变化而删除（尤其 officially_denied）。
  5. 来源登记表是独立组计数的唯一依据；owner_group 未确认一律不计组。
  6. 入库唯一入口是人工提交 git（若采纳动态通道，须另立等价闸门）。
  7. 交付给 H5 的字段结构冻结为 33 字段；管道自有字段不进入交付物。

■ 3.4 为什么「判定器」应该是第一个交付物（工程判断）

  事实：现有 15 条数据的 verification_status / independent_group_count /
  chain_steps_hit **全部是人工写的**，仓库里**没有**任何可执行判定器。
  R8.3 目前是「写在规范里、由人照着执行的流程」。

  判断：在接入真实来源之前先落地判定器，收益明显高于先写采集器，理由三条：
    a. 它**不触碰 UI、不触碰数据文件结构、无网络依赖**，风险最低；
    b. 它可以被 test-news-rules.cjs 直接驱动 —— 用现有 15 条数据
       作为**黄金用例**回归（其中 003 伪多源、005 待核、008 冲突、
       009 官方否认、010/014 更正链 都是天然的边界样本）；
    c. 它把 R8.3 从「人肉流程」变成「可复现资产」，
       未来换存储通道时这段逻辑可以整体搬运，零重写。
  → 建议在 S-1 决策中把判定器列为 V3.0 的第 1 步。

4. 三、来源等级体系设计
============================================================

■ 4.1 先把三个不同的「轴」分开（这是本节的核心纠正）

  当前规范里同时存在三个常被混为一谈的概念：

  ┌────────────┬──────────────────────────────────────────────┬──────────────┐
  │ 轴          │ 取值                                          │ 出处          │
  ├────────────┼──────────────────────────────────────────────┼──────────────┤
  │ ① 来源分档  │ A 档自动抓取(6) / B 档人工(3) / C 档暂不使用(2) │ R6.1          │
  │ （能不能抓）│                                              │              │
  ├────────────┼──────────────────────────────────────────────┼──────────────┤
  │ ② 来源角色  │ 发现器 / 验证器 / 公告核实器 / 受阻·建议移出   │ R2.6          │
  │ （用来干嘛）│                                              │              │
  ├────────────┼──────────────────────────────────────────────┼──────────────┤
  │ ③ 信息状态  │ 8 态（official_confirmed … corrected）        │ R3.2 / R8.1   │
  │ （可不可信）│                                              │              │
  └────────────┴──────────────────────────────────────────────┴──────────────┘

  另有三个辅助属性（R2.2 登记表）：source_type（官方/权威媒体/MCU 垂直媒体/
  公告平台）、official_or_media（official | media）、owner_group（所属集团）。

  ★ 本次任务里的「官方已确认 / 多家媒体报道 / 单一来源报道 / 业内人士称 /
    有消息称」**不是独立的第四套体系**，它就是 ③ 号轴的一个**早期 5 值版本**，
    且只覆盖了 8 态中的 3 个（前者）与 2 个措辞（后者）。见 1.1。

■ 4.2 5 档 → 8 态的映射（供对照，不作为方案依据）

  ┌──────────────────────┬────────────────────────┬────────────────────────────┐
  │ 任务描述中的 5 档      │ 8 态中的对应            │ 差异说明                    │
  ├──────────────────────┼────────────────────────┼────────────────────────────┤
  │ 官方已确认            │ official_confirmed      │ 一致（文案即「官方已确认」） │
  │ 多家媒体报道          │ multi_source_reported   │ 一致（文案即「多家媒体报道」）│
  │ 单一来源报道          │ single_source           │ 一致                        │
  │ 业内人士称            │ rumor                   │ 文案实为「传闻 · 爆料」；     │
  │                      │                        │ 「业内人士称」是报道措辞     │
  │ 有消息称              │ unverified              │ 文案实为「信息待核实」；     │
  │                      │                        │ 「有消息称」是报道措辞       │
  │ —（无对应）            │ conflicting             │ 5 档无承载位                │
  │ —（无对应）            │ officially_denied       │ 5 档无承载位                │
  │ —（无对应）            │ corrected               │ 5 档无承载位                │
  └──────────────────────┴────────────────────────┴────────────────────────────┘

■ 4.3 V3.0 真正需要补的：一张可执行的来源登记表（tier），而非新状态

  真实接入后暴露的不是「状态不够用」，而是 **「来源登记表不可执行」**：
  现在的 owner_group 是写在文档表格里的中文，代码里靠字符串匹配，
  且 The Direct / ComicBook 两个**主力发现器**仍是「待核」。

  建议设计 `source_registry`（管道层的数据文件，非前端字段），字段如下：

  ┌────────────────────┬──────────────────────────────────────────────────┐
  │ 字段                │ 说明                                              │
  ├────────────────────┼──────────────────────────────────────────────────┤
  │ registry_id        │ 稳定编号（S001…），替代 source_name 字符串匹配     │
  │ source_name        │ 展示名（须与 news.js 的 reported_by.source_name    │
  │                    │ 完全一致，否则来源卡显示与登记表脱节）             │
  │ owner_group        │ **必填且必须已确认**；未确认一律 writing「待核」    │
  │ source_type        │ 官方 / 权威媒体 / MCU 垂直媒体 / 公告平台           │
  │ official_or_media  │ official | media                                  │
  │ tier               │ ★ 建议新增：来源可信等级（见下）                    │
  │ discovery_role     │ 发现器 / 验证器 / 公告核实器 / 人工                │
  │ feed_type / feed_url│ rss | atom | html-parse | none（必须实测通过）    │
  │ crawl_policy       │ allowed / named-ai-ban / notes-against-ai / blocked│
  │ allowed_domains    │ 仅 official 来源填写，用于 R7.4 校验               │
  │ allowed_paths      │ 同上，必须显式列举，**禁止通配整个域名**            │
  │ health             │ ok / degraded / paused（连续 3 次失败自动置 paused）│
  │ notes              │ 解析陷阱、探活日期                                 │
  └────────────────────┴──────────────────────────────────────────────────┘

  关于新增的 `tier`（★ 这是本节唯一的实质新增设计）：
    · 它服务**两个确定用途**，且都发生在管道层，不触碰 UI：
      a) 采集过滤：低 tier 来源的条目可直接不入候选池；
      b) 判定链加固：Step 6（single_source）要求「1 个**可靠**媒体来源」，
         现在「可靠」全凭人判断 → 有了 tier 就能机器判定。
    · tier 的取值建议（4 级，与状态完全不重叠，避免概念污染）：
          T1 官方            —— Marvel / Disney 登记出口
          T2 权威行业媒体      —— Variety / Deadline / THR 等有采编体系的
          T3 MCU 垂直媒体      —— The Direct / ComicBook / Collider 等
          T4 社交 / 未具名爆料 —— X、论坛、匿名消息人士
    · **硬约束：tier 不得渲染进 H5**。理由：现有 UI 无此字段的展示位
      （卡片结构见 R4.3，只有状态标签 / 标题 / 摘要 / 来源行 / 日期 / 关联），
      一旦渲染就等于改 UI，违反「展示层零改动」。
    · **硬约束：tier 不得直接映射为 verification_status**。
      例如 T2 不等于 multi_source_reported；tier 只是 Step 5/6 的输入之一。

■ 4.4 与 8 态的接线规则（三条，防止两套体系打架）

  1. tier 是**输入**，status 是**输出**；禁止「来源权威所以破格升级」
     （R7.4 已明确：媒体写「Marvel confirms」不构成官方确认依据）。
  2. 独立证据组的计数**只认 owner_group**，不认 tier。
     两家 T3 但同属一个集团 → 仍计 1 组（即 003 号伪多源用例）。
  3. 状态枚举冻结 8 个。若将来确实需要新语义，走「新增可选展示字段」
    （如管道层标记），**不得新增 verification_status 取值**（见 2.3-2)。

5. 四、数据存储方案比较（三端复用视角）
============================================================

■ 5.0 三端复用的事实基线（必须先明确，否则整节无从比较）

  实测结论（见 0 节索引与 1.3）：
    · 微信端、抖音端：**0 行资讯代码**，0 个资讯页面。
    · 资讯数据的复用已被明确排除：「唯一权威源 = h5/data/news.js，
      不建 shared/data/news.js、不复制到小程序端」（09-22 拍板）。
    · 三端统一复用的既有范式是 `shared/data/*.js`（module.exports），
      由 shared/sync_data.sh 复制 → **物理副本 + 构建期同步**。
    · 「三端复用」在本期**是候选需求，不是既有约束**。
    · 抖音端引入资讯内容存在**类目风险**（V1.2.0 因「文娱-资讯」被驳回，
      现以「工具-实用工具-信息查询」通过）。

  → 因此下表的「三端复用」列按三种假设分别标注：
     ［假设甲］仅要求结构可转换（将来能复用）：**选型不受影响**
     ［假设乙］本期小程序端就要显示资讯：**静态方案不成立**（见 5.3）
     ［假设丙］仅 H5 使用：**静态方案最优**

■ 5.1 三方案对比（10 维度）

  后端**已经存在**（论坛 /api/），所以「引入后端」不是新增成本，
  但「把资讯也搬到后端」会增加该服务的责任面与可用性要求。

■ 5.2 逐方案详述

  ① JSON / JS 文件（现状：h5/data/news.js）
     优点：
       · 唯一同时满足 file:// 可运行 + git 可追溯 + 零运维 + 零运行时依赖
       · 审核闸门是**物理强制**的：没提交就是没上线，不存在「绕过审核写库」
       · 与现有 test-news-rules.cjs 的 78 条断言天然对齐（读文件即测）
       · 成本最低：产线只需产出候选文件，不需要任何服务端
     缺点：
       · 更新需「提交 + 部署」；延迟以天计（R1.3 已如实写明）
       · 小程序端**每次更新都要发版审核** → 若小程序要显示资讯，这是致命的
       · 数据量增长后单文件体积上升（按 5–10 条/日的量级，
         一年约 2000–4000 条，单文件约 1–3 MB —— 量级尚可，但需评估）
     适用：仅 H5 使用（假设丙）或仅要求结构可转换（假设甲）

  ② CloudBase 数据库（环境 mcu-d6gw0brqoa9521b58 已存在）
     优点：
       · **三端同一份数据，且小程序端免发版更新** ← 这是它相对 ① 的唯一
         决定性优势
       · H5 已有 stats/feedback 匿名写实践，SDK 接入路径已跑通
       · 微信小程序原生支持 wx.cloud，鉴权与域名配置成本低
     缺点：
       · 破坏 file:// 硬验收项（R1.2-3 已明确列为硬冲突）
       · 数据可追溯性从 git 转到数据库，需要额外建设审计（版本历史/回滚）
       · 审核闸门变弱：库里存在的数据即可被读走 → 必须靠
         「只写 approved 状态文档」的纪律来替代物理闸门
       · H5 侧安全域名白名单曾失效（09-16 才恢复），说明该路径有运维脆弱点
       · 抖音端对腾讯云 CloudBase 的支持度**未经本方案核实**，
         不构成事实判断，需实测
     适用：小程序端确需显示资讯（假设乙）时的首选

  ③ 独立 API 服务（服务器自建 Node + Nginx /api/ 反代）
     优点：
       · 三端统一取数；可实现审核后台（候选池 → 审核 → 发布）
       · 可做服务端缓存、限流、鉴权，后续可扩展更多动态能力
       · **基础设施已存在**（论坛后端已在跑，Nginx 反代已配）
     缺点：
       · 责任面最大：进程守护、数据库备份、安全加固、故障排查
       · file:// 同样破坏，且**无静态兜底时资讯模块会整体消失**（见 6.6）
       · 需要额外的审核后台才算真正闭环，否则闸门比现状更弱
       · 审核后台本身是一个新产品的开发量，与「资讯接入」不是同一件事
     适用：需要审核后台 / 多来源运营管理 / 未来资讯量级显著上升时

■ 5.3 三端复用专项结论

  1. 若按 ［假设丙］（仅 H5，即现状拍板口径）→ **方案 ① 最优，无需比较**。
     方案 ②③ 的收益（免发版、实时）在这个假设下全部不成立，
     代价（file:// 破坏、运维、闸门弱化）却是即时的。
  2. 若按 ［假设甲］（只要求不被写死）→ 仍选 ①，
     但须在 S-5 决策中固化一条纪律：**news.js 的字段结构按协议冻结，
     未来换通道时只替换数据通道、不动结构、不动 UI**（R1.2-11 已有此要求）。
     现有结构已满足该要求，增量成本≈0。
  3. 若按 ［假设乙］（小程序端要显示资讯）→
     · 方案 ① **技术上不成立**：小程序数据随包发布，
       每日资讯需要每日发版审核，微信侧约 1–7 天审核周期，不可行。
     · 应在方案 ②③ 之间选，**② 优先**（小程序原生支持、无自建服务责任）；
       ③ 仅在同时需要审核后台时选。
     · 该选项会连带触发三条封版纪律的修订（R1.1 选型、R3.4 单一源、
       file:// 硬验收）→ 必须先做规范修订，不能先改代码。
  4. 与抖音相关的独立提醒：**资讯内容进入抖音端存在类目合规风险**
     （V1.2.0 已被「文娱-资讯」类目驳回）。若未来要在抖音端展示资讯，
     必须先做类目预判，不能默认「微信能做抖音就能做」。


============================================================
6. 五、风险分析
============================================================

■ 6.1 假消息进入系统（最高优先）

  事实：现有防线是三道 —— ① 采集只取已登记来源；② 判定链只认
  owner_group 独立性与可回链官方 URL；③ 文案禁止真实性百分比、
  禁止绝对化措辞（R4.1，且已被 78 条断言中的措辞红线覆盖）。

  残余风险与缓解：
  · 风险：单来源爆料（rumor）本身就会进列表，用户可能只看到卡片不看标签。
    缓解：现有设计已让非官方状态强制带「尚未获得 Marvel / Disney 官方确认」
    提醒语（R4.2），这是**结构性缓解**，不建议再弱化。
  · 风险：**真实接入后，official_confirmed 的判定压力会集中在人工身上**。
    缓解：R7.4 六步校验必须代码化（Step 1–3 机器可判，Step 4/5 人工）。
  · 残余：无法消除。任何聚合型资讯产品都存在该风险，本方案只做**可控化**
    （状态可追溯、可重判、可回滚），不承诺准确性。

■ 6.2 版权

  现状已采取的措施（R4.6 + R3.4）：不存全文、不抓第三方封面图、
  AI 自撰摘要、详情页回链原文、第一阶段统一自绘占位图。

  V3.0 新增风险点（真实接入后才出现）：
  · **AI 摘要若改写不足，可能构成实质性替代**（reproduction 风险）。
    建议：摘要设长度上限（如 ≤ 120 字）、禁止引用原文连续片段、
    禁止输出原文段落。
  · **来源方 ToS / robots 明确反对 AI 使用**：THR 已具名封禁 AI 爬虫
    （robots 真 Disallow）；EW 返回 402 且注释禁止 RAG；Collider 注释禁止
    AI 与数据集建设。R6.3 已把三者移出自动抓取、降级为人工录入。
    → V3.0 应把这一条**固化进 source_registry.crawl_policy**，防止
    将来有人「顺手加个源」。
  · 事实性信息（谁出演、何时上映）通常不受版权保护，但**表述**受保护。

  ★ 明确声明：以上是工程层的风险控制措施，**不构成法律意见**。
    授权边界问题需要专业判断，本方案不下法律结论。

■ 6.3 来源可靠性

  · 最大现实问题：**两个主力发现器的 owner_group 至今「待核」**
    （The Direct、ComicBook）。R3.1 已实测：ComicBook、The Direct 归属未证实。
    后果：即便它们报道了同一件事，系统也只能计 0 个独立组 →
    落到 unverified（现有 005 号用例就是这个形态）。
  · 次生问题：source_name 目前是字符串匹配，来源改名或换 feed 路径会
    **静默失配**（不报错，只是登记表失效）。
  · 缓解：S-2 决策要求先补齐登记表并引入 registry_id（见 4.3）。

■ 6.4 AI 误判

  · 现有防线（R3.5）：AI 只能提建议，硬禁止自行认定 official_confirmed、
    禁止制造来源、禁止把传闻写成事实、禁止因转载认定真实。
  · 缓解设计：**AI 建议值与最终状态物理分离**（见 S2 环节），
    并以 judged_by 字段区分 ai_suggested / rule_validated / human_confirmed
    —— 该字段现已存在，可直接用于统计「有多少条是 AI 建议被采纳」。
  · 新增缓解建议：落 ai_model + pipeline_run_id（2.5 第 6 项），
    以便模型更换后回溯误判批次。
  · 残余风险：提示词或模型变化导致判定漂移。缓解：判定器（S3）
    与 AI 解耦——状态永远由规则算，AI 只影响摘要与关联抽取。

■ 6.5 数据重复（工程上最容易被低估）

  事实：现有 id 形如 `news-YYYY-MM-DD-NNN`，**只在同日内有序**，
  跨天重复入库无法识别；且没有 event_key / 标题指纹字段。

  真实接入后的重复来源有三类：
    a. 同一媒体同一文章被两个出口抓到（如 ComicBook 主 feed 与分类 feed）；
    b. 多家媒体转引同一原始报道（★ 最需处理，且与「伪多源」是同一问题的两面）；
    c. 同一事件在数日内分阶段报道（新进展 vs 旧消息）。

  缓解设计（建议进入 S-3 决策）：
    · event_key = 归一化标题指纹 + 关联实体 + 时间窗（如 72h）
      —— 注意：**不能只靠标题**，MCU 资讯标题模板化严重。
    · 转引识别：若多条候选的 reported_by 指向同一 original_source_url，
      合并为一个事件，reported_by 取并集 → 由判定链自然算出独立组数。
    · 跨天合并：event_key 命中则更新既有条目，追加 status_history，
      不新增条目。
    · 入库前强制去重校验，并纳入 test-news-rules.cjs 新断言。

■ 6.6 通道单点（本方案新增识别的风险）

  · 若未来切到方案 ②/③，H5 在两种情况下会**资讯模块整体消失**：
    file:// 本地打开时、后端/云服务故障时。
  · 现有先例的风险等级不同：论坛预览 `/api/topics` 失败时是**静默隐藏一小块**
    （index.html 第 458 行 catch 静默），影响面可接受；
    但资讯模块若整块消失，首页会出现结构空缺。
  · 缓解（若采纳动态通道）：必须保留**静态兜底快照**
    （如 data/news.snapshot.js，构建期写入，取数失败时回退），
    否则不允许切换通道。这一条建议写成硬约束。

■ 6.7 采集静默失败

  · 事实：R6.2 已明确要求「页面结构变化导致的解析失败必须告警，
    不得静默产出空结果」；marvel.com 无 RSS、只能 HTML 解析，结构变动风险实在。
  · 缓解：source_registry.health 字段 + 连续 3 次失败自动 paused + 告警。
  · 残余：告警渠道本身未定义（邮件 / 企微 / 待办），需在 S-3 一并决定。


============================================================
7. 六、推荐方案（★ 不开发，仅建议）
============================================================

■ 7.1 推荐：两阶段，先加固、后演进

  **第一阶段（V3.0-A）· 推荐立即做**
    目标：把「数据从哪来」变成「数据怎么判」，交付可复现的判定资产。
    内容：
      1. 补齐 source_registry（先把 The Direct / ComicBook 的 owner_group 定下来）
      2. 实现 R8.3 判定器（纯函数、零网络、可离线跑、可被现有测试脚本驱动）
      3. 实现 R7.4 官方来源校验（Step 1–3 机器化，Step 4/5 保留人工）
      4. 实现去重键与转引合并
      5. 实现采集脚本：产**候选文件**（不直接覆盖 news.js）
      6. 人工复核后覆盖 h5/data/news.js 并提交 git（沿用 R1.2-5 唯一入口）
    保持：存储形态不变（方案 ①）、file:// 不变、H5 与 CSS 零改动、
          78 + 55 + 11 条断言继续全绿。
    理由：这是唯一「零 UI 风险 + 零运维增量 + 可逆」的路径，
          且它的产出（判定器、登记表、去重键）在换通道后可 100% 复用。

  **第二阶段（V3.0-B）· 仅在触发条件满足后启动**
    目标：若确需三端复用或更低延迟，把数据通道换成 CloudBase（方案 ②）。
    前置：必须先完成规范修订（R1.1 选型 / R3.4 单一源 / file:// 硬验收），
          并实现静态兜底快照，否则不启动。

■ 7.2 升级触发条件（客观、可验证，满足任一即启动第二阶段评估）

  直接沿用并替换 R1.2-11 的旧阈值（旧阈值缺一条「三端」条件）：
    a. 单次人工复核耗时稳定超过 30 分钟/日；
    b. 待审候选稳定超过 40 条/日；
    c. 出现「日级延迟不可接受」的产品需求（如首映实时追踪）；
    d. ★ **小程序端出现真实的资讯展示需求**（本期不存在）——
       这条一旦成立，静态通道立即失效，无需再比较。

■ 7.3 明确不推荐的做法

  1. **不推荐现在就上方案 ③（独立 API 服务）**。
     理由：收益（实时、免发版）在 5–10 条/日的量级下不成立；
     代价（运维责任、审核闸门弱化、需另建审核后台）是即时的。
     ※ 注意：反对理由**不是**「会引入后端」——后端已经在了（见 1.2）。
  2. **不推荐把资讯降到 5 档状态**。会与 8 态封版规则和前端文案表冲突，
     并使 78 条断言中的 3 条直接 FAIL。
  3. **不推荐在完成来源登记表补齐之前启动采集**。owner_group 待核
     会让独立组计数持续失真，等于在错误输入上跑判定链。
  4. **不推荐把 tier / raw_excerpt / event_key 等管道字段写入交付数据**。
     会与设计规范 R12.2 产生口径差，并可能被误当渲染字段使用。
  5. **不推荐在抖音端引入资讯内容**而不先做类目预判（V1.2.0 驳回前例）。
