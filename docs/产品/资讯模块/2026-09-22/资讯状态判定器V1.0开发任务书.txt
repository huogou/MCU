3. 输入契约（I1–I9）
============================================================

  判定器接收「结构事实 + 语义标记」两类输入。**两类必须物理分开传入**，
  不得从同一条数据的文本里自行推断语义。

  ┌────┬────────────────────┬──────────┬──────────────────────────────────────────┐
  │ #  │ 输入                │ 类别      │ 要求                                      │
  ├────┼────────────────────┼──────────┼──────────────────────────────────────────┤
  │ I1 │ reported_by[]       │ 结构事实  │ 每项 source_name / source_url / owner_group │
  │ I2 │ owner_group 映射     │ 结构事实  │ 来源 → 集团；「待核/unknown/未确认/空」不可用 │
  │ I3 │ official_source_url │ 结构事实  │ 仅做 host / path 字符串校验（**不做联网**）  │
  │ I4 │ 独立证据组数         │ —        │ ★ **由判定器自行计算**，禁止作为入参         │
  │ I5 │ report_corrections[]│ 结构事实  │ 更正记录（含 source_name 用于覆盖判定）      │
  │ I6 │ conflict_statements[]│ 结构事实 │ 冲突各方表述（长度 ≥2 才有意义）            │
  │ I7 │ original_source     │ 结构事实  │ 受限字段，**唯一允许做文本匹配的字段**       │
  │ I8 │ 关联 id 集合         │ 结构事实  │ MCU_CONTENT / MCU_CHARACTERS 的真实 id     │
  │ I9 │ 语义标记             │ **语义**  │ 由第一层 AI 建议 + 人工复核后传入，见 3.2     │
  └────┴────────────────────┴──────────┴──────────────────────────────────────────┘

■ 3.1 I4 为何禁止入参（必须写进代码注释）
  R3.1 已重定义：multi_source_reported 的判定基准是 **owner_group 去重后的组数**，
  不是「报道网站数量」。反例：现有 003 号用例 3 家报道（Variety + Deadline + THR）
  同属 Penske Media Corporation → 独立组 = 1 → 只能判 single_source。
  若接受外部传入「媒体数量 = 3」，会得出错误的 multi_source_reported。

■ 3.2 I9 语义标记的字段定义（三项，均含核准位）

  ┌──────────────────────┬──────────────┬────────────────────────────────────────┐
  │ 标记                  │ 结构          │ 用途                                    │
  ├──────────────────────┼──────────────┼────────────────────────────────────────┤
  │ official_confirm     │ { url,       │ Step 1 用。url 仍需过 host/path 校验；   │
  │                      │  reviewed }  │ reviewed 表示人工复核已通过               │
  ├──────────────────────┼──────────────┼────────────────────────────────────────┤
  │ official_denial      │ { url,       │ Step 2 用。同样需过 host/path 校验 +     │
  │                      │  reviewed }  │ reviewed；媒体转述不得填入                │
  ├──────────────────────┼──────────────┼────────────────────────────────────────┤
  │ conflict_verified    │ { verified } │ Step 4 用。表示「互斥表述」已经人工核准    │
  └──────────────────────┴──────────────┴────────────────────────────────────────┘

  ★ 冻结规则（重新强调）：
    判定器**不得从 title / summary 文本判断**「官方否认」「存在冲突」。
    这类判断属第一层 AI 的**建议**，经人工复核后以结构化标记传入。
    判定器只做确定性计算：计数、字符串匹配、比较、短路。

■ 3.3 唯一允许的文本匹配
  仅 Step 7 允许对 **original_source**（受限字段）做词表匹配，原因：
  R8.3 Step 7 的判据本身就是「原始来源是否属于爆料 / 消息人士 / 社交爆料」，
  该字段是人工/AI 填写的最小封闭字段，非自由正文。
  **禁止**对 title、summary 做任何匹配或推断。

4. 核心算法规格（★ 本任务书的实现主体）
============================================================

■ 4.1 独立证据组数计算（必须与 components.js 口径一致）

  输入：reported_by[]
  步骤：
    A 逐项取 owner_group
    B 丢弃 owner_group ∈ {「待核」,「未确认」,「unknown」} 或空白 的项
    C 对剩余项按 owner_group 去重计数
    D 输出计数（0 起）

  边界：reported_by 为空数组 → 0；全部 owner_group 待核 → 0。
  ★ 与 components.js 的 `isGroupConfirmed` / `calcIndependentGroupCount`
    必须**逐条结果一致**（验收 A2 会拿现有 15 条逐条比对）。

■ 4.2 八步判定链（首个条件成立即输出并终止）

  执行顺序即优先级，**不得调换**。

  ── Step 1 → official_confirmed ────────────────────────────────────────
     条件：official_confirm 标记存在
           且 official_confirm.url 非空
           且 host 命中 source_registry.allowed_domains
           且 path 命中 source_registry.allowed_paths
           且 official_confirm.reviewed = true
     │ G1 范围内只做 host / path 字符串校验；
     │ URL 可达性（HTTP 200）与「内容对应当前事件」由 I9 标记承载，
     │ 联网探测归 G3。**不得因此放宽校验**。

  ── Step 2 → officially_denied ────────────────────────────────────────
     条件：official_denial 标记存在
           且 denial.url 非空
           且 host / path 校验通过
           且 denial.reviewed = true
     ※ 媒体写「Marvel 官方否认」不构成该条件。

  ── Step 3 → corrected（事件级）────────────────────────────────────────
     条件：report_corrections 非空
           且 **reported_by 中每一项** 均能在 report_corrections 中找到
              同 source_name 的更正记录（即全部有效报道均被其发布方更正）
     ★ 若仍有其他未被更正的报道 → Step 3 **不成立**，继续 Step 4 及后续
       （R8.5 事件级语义；011 号用例即此情形，最终应落 multi_source_reported）。

  ── Step 4 → conflicting ─────────────────────────────────────────────
     条件：conflict_verified.verified = true
           且 conflict_statements.length ≥ 2
     ★ 「互斥」的语义判定由 I9 承载，判定器只校验「已核准 且 ≥2 条」。
     ★ 本步必须早于 Step 5：存在互斥时「各来源表述一致」的前提已被破坏。

  ── Step 5 → multi_source_reported ───────────────────────────────────
     条件：独立证据组数 ≥ 2
     ※ 走到本步时，已核准的互斥不存在（否则 Step 4 已终止）
       → 「表述一致」视为成立，无需额外标记。
     ※ 参与计数的来源 tier 必须 ∈ {T1, T2, T3}（T4 不计入「可靠来源」）。

  ── Step 6 → single_source ──────────────────────────────────────────
     条件：独立证据组数 = 1

  ── Step 7 → rumor ─────────────────────────────────────────────────
     条件（三者任一）：
       a) original_source 命中爆料词表
       b) reported_by 唯一项在 registry 中 tier = T4
       c) reported_by 中存在 owner_group = 'unknown' 且该项为唯一来源
     爆料词表建议（可调整）：业内人士 / 消息人士 / 内部人士 / 爆料 / 未具名 /
       匿名 / 传闻 / 网传 / 据称 / allegedly / insider / unnamed

  ── Step 8 → unverified ─────────────────────────────────────────────
     条件：以上全部不成立（兜底）

■ 4.3 最小 owner_group 映射（D4，仅覆盖现有 15 条涉及的来源）

5. 输出契约（7 项，缺一不得入库）
============================================================

  判定器对每条输入输出：

    verification_status          8 态之一（必填）
    chain_steps_hit              命中的步骤（'Step 1'…'Step 8'，必填）
    judged_by                    'rule_validated'（必填）
    status_changed_at            本次判定时间（必填）
    status_change_reason         变更依据说明，须与 chain_steps_hit 对应（必填）
    status_change_evidence_url   证据 URL，必须可回链（必填）
    status_history_entry         {from, to, at, reason, evidence_url}
                                 （首次入库 from = null）

  规则：
    · 任一必填项缺失 → 该条**判定失败**，必须显式报错，不得静默返回默认值。
    · 输出**只读**：判定器不得写入任何文件，由调用方（G6 闸门）决定落库。
    · status_history 由调用方追加，判定器只产出「待追加的条目」，**禁止覆盖写**。

6. 幂等与确定性要求
============================================================

  1. **纯函数**：不读环境变量、不读时间以外的外部状态；时间必须可注入
     （便于测试固定时间、避免 flaky）。
  2. **可重入**：同输入连续运行两次，输出必须逐字节一致。
  3. **零网络**：运行期不得产生任何 socket / DNS 请求；依赖中不得含网络库。
  4. **零副作用**：不得写文件、不得改全局状态。
  5. **无 AI 依赖**：不得调用任何模型接口。
