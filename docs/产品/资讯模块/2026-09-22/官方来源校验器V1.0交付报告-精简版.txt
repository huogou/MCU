【一】设计

  定位：R7.4 官方来源六步校验中**可离线完成的那部分**，做成纯函数验证层。
  零网络 / 零副作用 / 确定性；域名事实全部来自 source-registry.json；
  path 策略复用 G1 的 PATH_POLICY（不另建第二套）。

  输入：{ source_url, source_name, registry_entry, claimed_event_id, official_confirm }
  输出（**恰为 4 个顶层键**）：
    {
      valid:        boolean,     // 六项全通过才 true
      checks:       object,      // 6 项，每项 { pass, detail }
      reason:       string,      // 结论说明
      rule_version: "V1.0"
    }
  ※ 契约取舍：任务书写 `checks:[a,b,...]`，本实现取 **checks 为对象**（键即检查名），
    理由：①调用方需按名取项　②detail 要承载证据　③顶层键严格保持 4 个。
    六项顺序由常量 CHECK_ORDER 显式给出，测试已断言键位顺序一致。

  六项检查：
    url_scheme       URL 非空 且 协议 http/https
    domain_allowed   host 命中 registry_entry.allowed_domains
    path_allowed     path 命中 allowed_paths 且不在 excluded_paths（legacy / article-level）
    domain_blacklist host 不在 non_official_domains（命中即失败）
    registry_match   官方资格：official_or_media=official **且** allowed_domains 非空；
                     另加条目真实性复核（source_name / registry_id 与登记表一致）
    review_required  official_confirm.reviewed = true，且 claimed_event_id 与
                     official_confirm.event_id 一致（若成对提供）

  ★ **级联语义（刻意不短路）**：六项全部计算，URL 不可用时依赖项一并失败。
    目的是让调用方一次看到全貌；reason 只报「按固定顺序最早失败的一项」，
    其余由 checks 全量呈现。这一条是首轮 5 个 FAIL 的根因（见三·4）。

  三项关键设计：
  ① 域名零硬编码（源码扫描 0 命中，机器可验证）
  ② 复用 G1 的 parseUrl / pathAllowed / PATH_POLICY，不复制逻辑；
     并用**交叉一致性断言**（8 组 URL×策略）防止两套实现漂移
  ③ 黑名单做成**独立守卫**：C5 用合成条目把 disneyplus.com 写进 allowed_domains，
     使 domain_allowed 通过，从而单独验证黑名单本身有效
     （即「有人误把黑名单域名登记进 allowed_domains 也拦得住」）

  本层**未覆盖**：R7.4 Step 1（HTTP 可达性，需联网）、Step 4 内容层比对（需抓正文，
  本层只校验 event_id 关联声明）、Step 5 人工复核（由 I9 的 reviewed 位承载）。
