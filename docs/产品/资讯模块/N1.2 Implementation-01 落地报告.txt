二、Adapter 接线架构
----------------------------------------------------------------
链路（runner.cjs · runAiProviderStage）：
  candidate(L1 桩)
    → registry.get(providerName)
    → runAdapter(provider, candidate)        [N1.1：validate → 标准 7 字段]
    → bridge.injectAiModel(7 字段, 受控 meta) [注入 ai_model → 8 字段]
    → ai-normalizer.normalize(candidate, 8 字段) [G5.5：产出增强 L1]
约束落实：复用 N1.1，禁止复制 validator、禁止绕过；Provider 原始输出不直接进 normalizer；validator/bridge 失败立即向上抛，不 catch 返回空对象、不静默删字段；不修改 seven 入参（隔离副本）。

----------------------------------------------------------------
三、ai_model bridge 实现（闭合 D1 断点）
----------------------------------------------------------------
bridge.cjs · injectAiModel(sevenFields, meta)：
  - seven 必须是不含 ai_model 的 7 字段（Provider 不得自带）；若含 → BRIDGE_UNEXPECTED_FIELD。
  - ai_model 只来自受控 meta（meta.model 必填非空），缺失 → BRIDGE_MISSING_MODEL。
  - 返回隔离副本（不修改入参）。
设计决策（须报告）：本阶段**未修改** N1.1 adapter.cjs 的 createProvider 签名，改为把受控元数据经 runAiProviderStage 的 opts.meta 注入。
  理由：冻结边界 §八只显式列「N1.1 validator 行为 / 7字段契约」，adapter.cjs 虽未列入，但为最大化冻结安全将其一并保持原状；
  该做法与 D5「ai_model 来自受控 Provider/Registry 元数据」完全等价，且更保守。
  注：此前《N1.2 最小接线设计说明》曾写「createProvider(name, impl, meta)」，本实现以 opts.meta 实现同一语义，属等价细化，不影响契约。

----------------------------------------------------------------
四、S001 manualCaptureLoader（D1 D+A）
----------------------------------------------------------------
manual-capture-loader.cjs · loadInbox(inboxDir, opts) → { captures, errors }：
  - 复用现有 L0 入参能力（raw-capture.cjs 的 RC.create 与校验）。
  - 仅接受 .json 投递（情形 A：已是合法 L0 → 直收；情形 B：人工最小结构 → 组装 L0 入参后 RC.create）。
  - 非 .json 类型 / JSON 解析失败 / 缺字段 → 明确进 errors（UNSUPPORTED_FILE_TYPE / JSON_PARSE_FAILED / CAPTURE_INVALID），不静默。
  - 默认 registry_id = S001（manual-only），source_name 取自登记表。
  - 无后台 UI、无常驻监听、不调用真实 AI；失败 fail-closed。
约束发现（已落实）：G5.2 parser.cjs 对 html-parse 返回 HTML_PARSE_NOT_IN_SCOPE（不在范围），故人工入口接收**结构化 JSON**（非原始 HTML），与 D1「复用现有 L0 入参能力」一致。
