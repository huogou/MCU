三、数据流（Step 4–8 的落地形态）
============================================================

  产线侧（Node，仓库内 workspace/news/，不部署）：

    A 档 6 来源（RSS feed / Marvel 官方 /news 列表页）
      ↓
    抓取与提取（原始条目 + reported_by + 候选 original_source / owner_group）
      ↓
    去重与事件聚合（同一事件合并为 1 条 news item）
      ↓
    判定引擎 rules.cjs
      ① independent_group_count：按 owner_group 去重；unknown / 待核 **不计入**
      ② R7 官方校验：host 命中 → path 命中 → 内容对应事件 → 人工复核标记
      ③ R8.3 八步判定链 → target_status（由引擎输出，非人工填写）
      ④ corrected 事件级语义：报道级标记，事件级继续跑判定链
      ↓
    人工复核位（仅以下五类需人工）：
      official_confirmed / officially_denied / conflicting /
      multi_source_reported 但 original_source 未确认 / 涉 supersedes 关系者
      ↓
    生成 h5/data/news.js（快照 + status_history + 证据 URL + 关联 id）
      ↓
    人工提交 git

  H5 侧（浏览器）：

    <script src="data/news.js"> → window.MCU_NEWS → 页面只读渲染
    （不判定、不请求网络、不写库）

四、三端数据单一源不被破坏的六条硬约束
============================================================

  1. news.js 内**禁止复制任何 MCU 内容字段**（片名 / 日期 / 阶段 / 简介），只存 id 引用。
  2. 写入前做 id 交集校验：related_* 必须命中 MCU_CONTENT 与 MCU_CHARACTERS 的
     现有 id 集合；未命中一律丢弃，并记入产出报告（不得留空串占位、不得静默新建）。
  3. related_phases 取值限定整数 1–6，与既有 phase 字段同域。
  4. 产线只读既有数据用于校验，绝不改写任何既有 data/*.js。
  5. 不引入第二套 MCU 内容数据；news.js 中不出现 mcTitle / mcDate 这类冗余镜像字段。
  6. 回归验收：新增后重跑现有页面，确认三项计数不变 ——
     MCU_CONTENT 59 / MCU_RELATIONS 92 / MCU_ROUTES 11。

  file:// 保真：news.js 为全局变量挂载，无 fetch、无 import；
  验收项包含「双击 h5/index.html 无控制台报错」与「file:// 下打开 news.html 渲染正常」。

五、规范冲突 / 待决策项（按 §十六 要求，先指出、不自行改规则）
============================================================

  S-1 资讯数据的权威源归属
      问题：V2.2 只允许 h5/data/news.js，但仓库现状是 shared/data 为三端权威源、
            h5 为机械适配副本。只建 h5 一份，会让资讯数据的权威源落在 H5 端，
            与既有架构不一致。
      选项：① 只建 h5/data/news.js（严格遵规范字面）
            ② 建 shared/data/news.js 为权威源 + h5 机械适配（与既有模式一致，
               但 shared/sync_data.sh 会把 news.js 一并复制到 wechat/douyin）
      开发建议：②，但需负责人决定是否接受小程序 data 目录多一个未引用文件。
      ⚠ 产品已定（2026-09-22）：选 ①。h5/data/news.js 为资讯数据唯一权威源，
        不建 shared/data/news.js、不复制到 wechat/douyin。此差异仅限资讯数据；
        其余数据仍以 shared/data 为三端权威源。已写入设计规范 R12.2 与开发交接书 0.4。

  S-2 §十四 Step 9「资讯页面 UI」
      问题：属设计 AI 职责。项目铁律「设计优先于代码，开发禁止自主设计」。
      ✅ 已解决（2026-09-22）：设计规范已交付并封版（V2.2 最终修复轮），可进入开发实施。

  S-3 判定引擎的落点
      选项：① 产出侧工具（workspace/news/，不进生产目录）
            ② 进 h5/data/news-rules.js
      开发建议：①。架构 C 下状态在产出时已固化，引擎若同时存在 H5 侧，
                会形成「页面重算 vs 数据快照」两处逻辑，存在长期不一致风险。

  S-4 资讯入口位置
      选项：① 只做首页 section 入口（同 community 的既有模式）
            ② 加进 app.js 的 NAV 第 5 项
      开发建议：①。NAV 改动会影响全站所有页面，且入口属于产品/设计范畴。

  S-5 12 个测试用例的模拟数据存放位置
      问题：若写入 h5/data/news.js 会污染生产（审核与外宣截图可能采到假资讯）。
      选项：① mock 仅放 workspace/news/，生产 news.js 一期为空数组或仅真实条目
            ② 先放 mock 上 H5 演示，上线前清空
      开发建议：①。

  S-6 status_history 是否需 H5 前台展示
      问题：§十一 要求保留 status_history，但未说明前台是否展示变更历史。
      选项：① 仅存数据、前台不展示  ② 前台展示（属设计范畴）
      开发建议：① 先存数据，展示与否交设计 AI 决定。
      ✅ 已解决（2026-09-22）：设计定仅展示最近一次状态变更的轻量提示（设计规范 D8），
         status_history 数据层保存，不展开完整时间轴。
