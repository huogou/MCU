【一】规范件一：资讯事件归并与 event_key 边界 V1.0（正式）

  A 组 · 事件归并边界（A1–A7）
    A1 event-merger 只做两件事：①减少候选条数 ②组装来源证据 reported_by_union
    A2 **不替代** supersedes_id / superseded_by_id（两套机制并行）
    A3 **不修改交付数据**（不写文件、不改任何字段、不决定是否入库）
    A4 同时命中两套机制时（010/014）→ **以 supersedes 为准**：
       不得删条、不得压成一条、不得改互链
    A5 G6 落库红线：交付数据**仍须保留 supersedes 双条与互链**，展示层合并照旧
    A6 G6 必须新增断言：「双条都在」+「互链成对」
    A7 【新增】输出隔离：不得含 6 项状态字段；不得做语义裁决（哪条更权威）；
       不得写入 h5/

  B 组 · event_key 使用边界（B1–B7）
    B1 **不是数据库唯一主键**（实测同 key 可产出多个 hold 事件）
    B2 **不作为报道实体 ID**（报道 ID 是交付数据的 id）
    B3 禁止四类场合：写库主键 / URL 参数 / 任何展示 / 跨端关联键
    B4 主键**规定 B-ii occurrence**（待 Z-3 最终确认）：
       occurrence = 同 key 下按 first_publish_time 升序从 1 编号；
       事件级稳定键 = event_key + '#' + occurrence
       ★ 三要点：①编号必须**在同一批次全量排序后**生成（分两批会冲突）
       ②新字段只在输出，**不得写回输入** ③新增 2 条断言
       备选 B-i 组合键 `event_key + '@' + first_publish_time`（本轮只出规范不落码）
    B5 既知限制：不区分状态（刻意，R8.8）｜无实体时识别力弱｜窗口 3 天未校准
    B6 【新增】`evt1-` 前缀即算法版本；改算法/词表**必须升版本号**，同版本内不得改成分
    B7 【新增】必须可由 explain() 解释；变更须同步更新回归断言；
       occurrence 在批准前**不得出现在任何产出**

  违规判定 9 条（第 1–3 条自 G6 起生效，第 5–9 条即日生效）：
    交付数据出现管道字段 / event_key / occurrence / capture_id / candidate_id；
    supersedes 双条缺一或互链不成对；merger 输出含状态字段；merger 写入 h5/；
    以 event_key 作主键·URL·展示·跨端键；同版本内改 key 成分；occurrence 提前出现

【二】规范件二：judged_by 字段语义 V1.0（草案，采用方案 b）

  正式语义（一句话）：**judged_by 表示「本次判定由哪一级做出」，
    不表示「这条状态最终由谁确认」。**
  判定规则：命中 Step 1–4 → `human_confirmed`（受控步骤须人工）
           命中 Step 5–8 → `rule_validated`
           `ai_suggested` **不由判定器产出**，保留为管道理历史中间态
  三条派生规定：①只由命中步骤决定，不依赖历史过程 → 保持幂等
              ②允许 opts.judgedBy 覆盖，但须在 status_history.reason 留痕
              ③AI 不得写入 judged_by（只能产管道字段 ai_suggested_status）
  字段定义**全不变**：仍是审计字段、必填、3 值枚举、不渲染；33 字段不变；8 态不变
  「谁确认的」分工：由 status_history（reason/at/evidence_url）+
    管道字段 ai_suggested_status / reviewed_by / reviewed_at 承载
  统计口径变更：「AI 建议采纳率」改由
    `ai_suggested_status vs verification_status` 比对得出
  迁移：**G8 改写 7 条**（003/004/006/007/011/012/015）→ 迁移后
    human_confirmed 6｜rule_validated 9｜ai_suggested 0（枚举不变）
    ※ 003 特别说明：其 human_confirmed 来自「人工复核发现伪多源」的历史过程；
      方案 b 下应改 rule_validated，该事实由 status_history.reason 保留，**信息不丢失**
    ※ 已核对：78/25/49/38/60/95 条断言**均不涉及 judged_by 取值**，迁移不破坏任何断言
  未采纳方案 a 的理由：①审计语义须唯一且确定性产出 ②「谁确认的」已有专属字段承载
    ③方案 a 会让纯函数判定器依赖管道历史，破坏 G1 幂等断言

【三】规范件三：候选数据 Candidate Schema V1.0

  四层模型（L0–L3 全在管道层，**不进 h5/**）：
    L0 RawCapture（采集器输出，单源单条，未经 AI 整理，P-01–P-16）
    L1 CandidateItem（AI 整理后；= L0 全部 + 标题/摘要/分类/关联/来源/AI 建议/
       capture_refs/gate_status 等）
    L2 EventCandidate（merger 归并输出）
    L3 DeliveryItem（33 字段交付物）← **转换只在 G6 闸门后发生，且严格单向**

  采集器输出（L0）关键字段：capture_id / pipeline_run_id / registry_id /
    source_name / source_url / **url_level**(article|feed|section) / **title_raw** /
    published_at_raw / published_at / fetched_at / feed_type / http_status /
    content_hash / raw_excerpt(≤200 字) / event_key / first_publish_time

  merger 输入契约（**只允许读 10 个字段**）：candidate_id / title / category /
    related_movies·series·characters / publish_time / first_seen_at / reported_by
    ★ **不得读** verification_status / judged_by / chain_steps_hit / status_history /
      ai_suggested_status / gate_status

  judge 输入契约：
    【item】**只允许读 6 个字段**：id / reported_by / report_corrections /
      conflict_statements / original_source / original_source_url
      ★ **不得读** title / summary（不读文本、不做语义判断）
    【input】I9 = official_confirm{url,reviewed,event_id?} /
      official_denial{url,reviewed} / conflict_verified{verified}
    【opts】now / pathPolicy(默认 legacy) / previousStatus / judgedBy
    【输出】7 项必填

  ★ 转换边界（第 6 节）：
    · 时点：**只能在 G6 人工审核闸门之后**；唯一入口 `gate_status === 'approved'`
    · 字段映射表：逐项列出候选 → 交付的对应关系，结果**恰为 33 字段**
    · **必须重算/生成的 6 项**：id（G6 生成 news-YYYY-MM-DD-NNN）、
      verification_status（判定器重算，候选的 ai_suggested_status 仅供参考）、
      official_source(_url)（须过 R7.4）、independent_group_count（运行时算，禁手填）、
      supersedes 链（受 A4/A5 约束）、审计 6 项 + status_history（判定器输出，只追加）
    · **禁止进入交付物：管道层 20 项**（原 12 + 新增 8：capture_id / candidate_id /
      gate_status / url_level / title_raw / published_at_raw / capture_refs / occurrence）
    · **单向性**：候选 → 交付物，**不得反向写回**
    · 转换后校验清单 9 条（含 supersedes 双条断言、字段集恰为 33）

  载体建议：`workspace\news\pipeline\`（captures / candidates / events 三个子目录），
    UTF-8 无 BOM，JSON

  ★★ **需负责人裁定的一处口径（见规范件 1.3 节）**：
    G0 冻结件的「管道字段 12 个」是**封闭清单(a)** 还是**禁止清单(b)**？
    本规范按 **b** 编制（管道层扩为 20 个）。若裁为 a，需删 8 个字段，代价：
    丧失采集证据追溯（capture_id/capture_refs）、**Q-5 合规状态暴露（url_level）**、
    原始标题留痕（title_raw）、**审核闸门的机器可读状态（gate_status）**。
    ★ 两种读法**均不影响** 33 字段交付物与 8 态体系。
