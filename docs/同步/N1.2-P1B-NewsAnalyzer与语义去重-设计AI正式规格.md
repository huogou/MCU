## 一、裁定一：扩展字段（credibility / recommend / confidence）呈现定位

### 1.1 本期边界
- credibility / recommend / confidence 均为**后端运行态数据**，本期不进前端、不进回流产物。
- confidence 仅作内部阈值信号，**永不外显**（产品规范禁「真实性/可信度百分比」，禁虚假精确感）。
- recommend 不做任何前端标签，仅体现为收录与排序结果。

### 1.2 未来回流原则（本期即冻结，防止后续阶段走偏）
- **不新造徽章体系，不把 3 级标签裸露给用户。** 用户侧可信度语言有且只有 8 态徽章一套（官方已确认 / 多家媒体报道 / 单一来源报道 / 传闻·爆料 / 信息待核实 / 信息存在冲突 / 官方已否认 / 来源已更正）。
- 理由：8 态语义是「截至当前已获得的来源层级」，文案与判定由产品规范封版；「high/medium/low」直接展示有绝对化观感风险，且与 8 态形成第二套可信度语言，互相打架。
- credibility 的正确定位：**8 态判定与推荐侧的证据输入信号**。既有 `ai_suggested_status`（带 8 态枚举校验，非 8 态值 → INVALID_SUGGESTED_STATUS）是 AI→8 态的唯一合法桥；扩展字段不得绕开它另起第三套表达。
- 若未来确需在用户侧体现 credibility，必须走「待决策」流程修改产品规范后由设计 AI 出规格，禁止实现侧自行添加。

### 1.3 扩展字段 schema（正式版，命名沿用开发侧草案）

```jsonc
{
  // —— 基础字段：7 字段契约输出，经 contract-validator 校验后原样透传，本规格零改动 ——
  // —— 扩展字段：NewsAnalyzer 在契约之外独立组装 ——

  "credibility": "high | medium | low",  // 三值枚举；生产侧可信度判断信号
  "recommend": true,                      // 布尔；是否进入推荐池
  "confidence": 0.75                      // 数值 [0,1]；仅内部，禁止外显/回流
}
```

判定规则（正式确认开发侧草案）：
- **credibility** = 来源 tier（T1 官方最高）+ `official_or_media` + 多来源印证（事件 report_count）+ 是否与 `officialSources()` 域名吻合 的组合信号。
- **recommend** = `credibility != low` **且** `confidence >= 0.6` **且** category 非空 **且** related_* 至少命中一个 MCU 节点。四条件缺一不可。
- **confidence** = 由 Provider 返回质量推导（JSON Schema 命中 / 字段非空率 / 有无 validator 警告）。
- 阈值 0.6 为中性起点，进配置可调；调整只影响 recommend 判定，**不得反向改写 credibility**。

## 二、裁定二：流水线状态流与 8 态的语义边界声明

- **不打通、不映射。** 流水线态（RAW→FETCHED→AI_ANALYZED→VERIFIED→PUBLISHED）= 生产进度，生命周期短、受众为生产侧；8 态 = 内容可信度，随证据长期演化、受众为终端用户。二者语义不同源，映射只会制造误读。
- 唯一交点：**PUBLISHED 是未来回流 H5 的前置条件**；回流后 8 态由既有判定器按既有规则独立计算，与流水线态无关。
- **明确禁止「VERIFIED = 高可信」类直觉映射**：gate approve 是质量底线判定，不是信任等级，不得与任何 8 态值挂钩或换算。

落地约束（进入验收基线）：
- `pipeline/status/` 的 schema 中**不得出现** `verification_status` 及任何 8 态相关字段/枚举；
- 8 态数据不得写入 `pipeline/status/` 的任何 JSON；
- 双向物理隔离，防未来阶段误并。

## 四、NewsAnalyzer 正式规格（pipeline/ai/news-analyzer.cjs）

### 4.1 定位与边界
- 定位：把 N1.2 U1「单次 Provider 验证」升级为「生产调用服务」。
- 边界：**不改 `contract-validator.cjs`**（7 字段契约冻结）；扩展字段在 validator 之外独立组装；不改 N1.1 adapter / N1.2 provider 本体；不改 G 系列冻结件。

### 4.2 处理链路（沿用开发侧草案，正式确认）

```
candidate
  → A.runAdapter(provider, candidate)    # 7 字段经 validator 校验
  → B.injectAiModel(seven, meta)         # 注入 ai_model → 8 字段
  → NM.normalize(candidate, eight)       # G5.5 ai-normalizer（只读调用）
  → newsAnalyzer.enrich(seven, candidate, providerMeta)  # 产出扩展字段
```

- 链路中任何一步不得改写 validator 输出的 7 字段内容。

### 4.3 异常与降级（设计要求）
- 单条候选处理失败（provider 异常 / validator 不通过等）：**不阻断批量**（与既有「单源失败不影响批量」语义一致）。
- 失败条目状态不推进到 AI_ANALYZED（维持 FETCHED），按状态层既有 ANOMALY 机制标注（独立字段，不进主链）。
- 失败原因计入 run-history 的 `fail_reasons`（P1-A 已扩展）。

### 4.4 扩展字段的消费边界
- 本期扩展字段**仅产出与随状态层/运行记录落盘**；gate 本体零改动。
- gate 是否/如何消费扩展字段（在其冻结边界内）属下一阶段决策，开发侧评估后如需设计侧出规格再流转。

## 五、语义去重正式规格（pipeline/dedup/）

### 5.1 定位
- L1 入库**前**的相似度预筛；只打标、不删除；**不覆盖 G4**（G4 event-merger 仍是事件级归并的唯一权威）。

### 5.2 dedup_hint schema（正式版，沿用开发侧草案）

```jsonc
{
  "kind": "title | content | event",   // 相似类型
  "similar_to": "<被相似项的 id>",      // 引用，不删除本项
  "score": 0.87                         // 相似度得分
}
```

### 5.3 唯一写入点（设计拍板）
- dedup_hint 唯一写入点是 **`pipeline/status/` 的 item-status JSON**（该结构已预留 `dedup_hint` 字段）。
- **不写「候选附属」第二处**：候选层（L1）属冻结数据结构；运行态标注的单一事实源在状态层，避免双写不一致。
- L0/L1/L2 三层主结构深扫不得出现 `dedup_hint`。

### 5.4 阈值（拍板值）

| 类型 | 算法 | 默认阈值 |
|---|---|---|
| 标题相似 | 分词 → n-gram(2-3) 集合 → Jaccard | ≥ 0.85 判相似 |
| 内容相似 | 字符 3-gram shingling → Jaccard | ≥ 0.80 判相似 |
| 事件相似 | 复用 G4 归并键（不重实现） | 交 G4 权威归并 |

- 取舍依据：在「只标注不删 + G4 权威归并」双重兜底下，预筛宁缺勿滥——hint 噪音消耗的是终审注意力；阈值进配置文件、按来源可调。
- 零依赖约束维持：不引入 embedding/重依赖；本地 embedding 余弦留作后续可选增强。

### 5.5 防误杀策略（正式确认开发侧五条）
1. **content_hash 精确去重为铁律**（沿用 candidate-store）；相似度只用于「疑似」。
2. **相似≠删除**：只打 dedup_hint，保留本项，交 VERIFIED 阶段终审裁定。
3. **事件进展保护**：同 event_key 但 publish_time 跨天或摘要差异超阈值（新增事实）→ 不判重，避免误杀「同一事件的不同进展」。
4. **不覆盖 G4**：dedup 是候选层预筛，G4 仍在 VERIFIED 后权威归并；similar_to 仅提示，不改变 G4 行为。
5. **阈值保守 + 可配**：写入配置文件，按来源质量调参；误杀风险靠「只标注不删」兜底。

## 六、验收基线（P1-B）

开发侧既定四条（沿用）：
1. NewsAnalyzer 单测：7 字段经 validator 通过、扩展字段齐全；
2. dedup 单测：精确重复→hash 去重，相似→标 hint 不删，同事件不同进展→不误杀；
3. 不破坏 G4 行为（G4 既有测试绿）；
4. 411 断言全绿。

设计侧补充断言（源自本规格裁定）：
5. validator 输出的 7 字段内容零改写（透传一致性断言）；
6. L0/L1/L2 深扫：`dedup_hint` / `credibility` / `recommend` / `confidence` 0 命中；
7. `pipeline/status/` schema 深扫：`verification_status` 及 8 态枚举 0 命中；
8. dedup 全流程零删除（候选数量只增不减断言）；
9. `confidence` 不出现在任何面向回流的产物结构中（本期即无回流路径，作约束声明）。
